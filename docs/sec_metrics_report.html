1 摘要

先看结论

这个系统做的事可以用一句话概括：先确认公司和报告期，从 SEC 下载并封存原始申报，再按指标定义选择结构化解析或 AI 表格抽取，经过口径检查、计算、审核和验证，最后由确定性代码生成 CSV 并整体发布。它不是「把十份年报交给 AI，让它写出一个表格」。

理解它的五个要点：

  1. 只有一条主干。十家公司共用同一套阶段和代码；行业差异体现在配置驱动的三个环节：指标是否适用、选哪条事实、用什么口径。生产代码里禁止出现「如果公司是某某」这样的分支。
  2. 能从结构化数据得到的事实不用 AI。39 个指标中 24 个的目标来源是纯确定性路径（SEC Company Facts 或 XBRL 实例 + 声明式公式）。AI 只在需要读表格时出现，而且只被允许提出「哪张表、哪一行、哪一列、什么期间、什么范围」，程序按这个坐标重读原始单元格验证，通过审核后才成为可用事实。
  3. 空值有五种不同含义。结构性不适用、主体不可比、可能披露但没抽到、需要人复核、扫描后确认为零，这些在结果里用不同状态区分，系统禁止把它们静默变成 OK，也禁止为了填满表格猜数。
  4. 每个数字都带证据。原始响应按内容哈希封存，请求账本只追加不覆盖；每个「公司 × 指标」的计算封装成一份可重放的证据包（Run）；CSV 的每一行都能回溯到具体的申报、文档和事实。
  5. 发布是整体版本。结果不是逐行写入的：先按公司名单和发布计划推导应有的完整批次，生成不可变的版本包，再原子切换指针。失败时不会用一半新数据覆盖正式结果。
截至 2026-09-04 的进度：新架构（仓库内称 vNext）已按三级发布 24 个指标，覆盖 240 个「公司 × 指标」坐标；其余 15 个指标的 87 行仍由旧路径生成并原样保留在 CSV 里。面向银行的表格类指标（financial 家族）处于上线前的资格认证阶段，尚无一行进入 CSV。当前代码检出点的验收快照检查未通过，因此它不能被称为一次完整验收后的状态；正式发布的 CSV 本身与其版本包字节一致，没有被改动。第 11 节单独整理了这个项目在工程上值得借鉴的做法。
2026-09-09 更新：正式发布仍是 R3，CSV 的 327 行没有变化。新增的是三件事：银行六指标的 R4 计划（issue_28 系列，累计 30 指标）以离线方式建成但没有激活，真实认证在 21 次模型调用后于 PR #34 停止，没有发布 credit；面向「年报更新后自动重算」的年度候选链（annual_* 模块，先做 Marriott 收入与入住率）已跑通一次真实验证，累计模型调用 2 次、SEC 调用 0 次，结果与 R3 一致；它的隔离演练版本已生成，正式采纳（issue_28_v7 与采纳政策 v2）等待负责人在 GitHub 上批准。项目的三个终极目标与各自进度见第 10.1 至 10.3 节；阶段去留、指标清单和 AI 抽取详解见第 2.1、4.6、4.7 节。

3.2 申报发现：四条写死的规则

submissions 只是目录，它不会告诉程序哪些文件有用。决定「需要哪些申报」的是项目里的四条规则，每条规则只看文件类型和两个日期：提交日期（filingDate）与报告期（reportDate）。

每家公司实际用到多少份申报

清单共 182 行：每家 2 份 10-K（当期、上期）、1 份 DEF 14A、6 到 25 份财年窗口内的 8-K；Southwest 与 Paramount 另有 10-K/A。8-K 的 item 从 hdr.sgml 读取，共 326 个命中。

两个容易忽略的细节

8-K 窗口按提交日期筛选。窗口是「上期年报报告期次日 → 当期年报报告期」，落在窗口内的是 8-K 的提交日期，不是事件发生日期。

「最新提交的年报」不等于「最新财年的年报」。旧路径选目标年报时只按提交日期排序；如果一家公司今天提交几年前年度的修订稿，它会被排在最前面。新架构的年度事实链按报告期排序，没有这个问题。这是一个已识别、尚未修补的缺口。

3.3 下载与证据账本

所有 SEC 请求都经过同一个客户端 SecHttpClient。它做的事情很具体：从环境变量读取联系邮箱作为 SEC 要求的请求身份，缺失或畸形就在联网前失败；只允许两个官方域名；每秒最多 5 个请求，失败最多重试 4 次，退避从 1 秒起；不跟随隐式重定向。每个响应的正文和头部都保存到以内容哈希命名的目录里，同一个 URL 第二次下载得到不同内容时，不会覆盖第一次的证据。请求账本 requests_log.csv 只追加不修改，目前 985 行；旁边的 manifest 记录整份账本的行数与哈希，追加前校验、追加后刷新。

3.5 Company Facts 与 XBRL 实例的区别

Company Facts 是 SEC 汇总的「公司级标准事实」接口：一个 CIK 一个 JSON，包含多年、多概念的数据，但没有维度（segment / axis）。Marriott 的这份文件有 3.27 MB、545 个 us-gaap 概念，仅 Revenues 一项就有 290 条事实，覆盖 FY2009 到 FY2026。程序整份下载后再按概念、单位、期间、申报编号筛选。资本比率要区分母公司与银行子公司、标准法与高级法，这些是维度事实，只能从某次申报里的 XBRL 实例（阶段 06）取；RPO（剩余履约义务）也在实例里。所以 A01/A02/B12 走实例路线，B01 到 B09 走 Company Facts 路线，两条路线都不调用模型。

4.1 适用性判断先于来源

7 发布机制

从 Run 到用户读到的 CSV

写出 CSV 文件并不等于发布。正式流程有固定顺序：

  1. 完整批次检查。从公司名单和发布计划推导应有的「公司 × 指标」坐标集合，不能从「已经成功的结果」反推范围。
  2. 只加载验证通过的 FROZEN Run。不接受调用者传来的内存对象。
  3. 投影成 CSV 行。每个字段按固定映射填写：公司与 CIK 来自名单，指标名与公式来自目录，值与单位来自结果和投影规则，状态由适用性、质量和发布状态映射，期间来自结果，申报信息来自证据。用 csv.DictWriter、固定字段序、UTF-8、LF 输出。
  4. 与冻结的旧版本逐字段比较。旧结果只是比较基准，不是新数值的来源。
  5. 组装完整版本。替换已迁移指标的行，保留未迁移的行，加入新的结构性坐标。
  6. 生成不可变的版本包。CSV、报告、校验和、provenance 一起闭合，状态为 PUBLISHABLE 才能继续。
  7. 原子切换指针。切换要求「当前指针指向的前一版本」仍是预期版本（CAS），否则拒绝；同时同步根目录的 CSV 镜像。
  8. 终态检查。在同一个固定的版本视图下验证 Golden、报告、指针、快照。

回滚只切换到已存在的前一版本并恢复镜像，不会重新调用模型，也不会回滚 SEC 请求账本。

9.1 新增公司、行业、指标各是什么工作量

新增同行业公司

设计目标是不改生产代码。仓库有一道机器门（tools/check_no_company_literals.py）扫描生产脚本，禁止出现公司名、CIK、ticker、固定申报号或固定日期的分支；另有一组按行业 profile 准备的模拟事实清单（tests/fixtures/eleventh_company_smoke），验证只改配置和 fixture 就能让抽取器工作。要注意它是模拟数据，不是真实下载并跑通的第 11 家公司。

现实限制：已发布的版本通过哈希绑定了当时的公司名单。修改名单会使旧的发布计划闭包失效，新公司必须经过新的计划、完整批次和新版本才算正式接入；不能因为 Marriott 能抽到入住率，就默认另一家酒店也能。

新增行业 / 新增指标

行业：先判断是否真的需要新能力。普通消费品公司的收入、现金流可以直接复用非金融路径；保险公司要算综合成本率，就需要新的口径与事实选择规则。配置入口是 SIC 区间到 profile 的映射、profile 的抽取器列表、profile 到 traits 的投影。行业名字不同不意味着要再写一套爬虫，业务口径不同才可能需要新代码。

指标：先定义公式、单位、期间、主体范围、适用行业和何时留空，再决定来源（标准标签、维度 XBRL、表格还是正文），最后定义正例和负例。要区分「实现现有 39 个中尚未完成的一项」和「新增第 40 个」：注册表要求恰好 39 个指标且与冻结的需求一致，第 40 个意味着扩大需求闭包。表格类新指标还要走第 8 节的资格认证。

可以实现「指定公司增量下载」而不必推翻系统，因为账本和内容寻址已经存在；缺的是把「发现新申报 → 只补缺失 → 只重算受影响 → 带来源版本发布」组织成入口。三件事要分开：增量下载最容易；增量计算涉及依赖（一份新的 10-K/A 可能修改旧年度，牵连同比类指标）；增量发布要让用户看得出各公司的数据时间不同，不能让「只更新了 Marriott」被误读成十家都刷新了。

这个项目做对了什么

前面各节描述的是「数据怎样流动」。这一节换一个角度，把仓库里值得借鉴的工程做法单独列出来。每一条都对应可以打开验证的代码、工具或产物；有机制存在但尚未在正式环境执行的，也如实标注。

11.1 证据先于结论：一切可追溯、可重放

  • 内容寻址贯穿始终。原始响应、Run、批次、发布计划、冻结收据、认证周期的标识都是 SHA-256 内容哈希，同一份输入永远得到同一个 ID；发布计划逐级引用父计划的哈希，去掉任何一个父坐标就会失效。
  • 严格的规范化序列化。所有记录用同一套规范 JSON：拒绝重复键、NaN / Infinity、孤立代理字符，文本统一 NFC；数字用定点 Decimal（最多 128 位有效数字、64 位小数、ROUND_HALF_EVEN），计算器、约束解释器、投影换算和 Golden 容差比较共用同一算术上下文，不继承进程的可变全局设置。这样同一份事实在任何机器上算出的哈希都相同。
  • 语义版本进入闭包。候选记录、审核渲染、投影等组件各有语义版本号，汇总成一个 semantic_runtime_versions_hash 写进需求闭包；任一组件语义变化都会让旧的批准、Run、批次和发布失效，而不是悄悄沿用。
  • 只追加的请求账本。SEC 请求账本 985 行，manifest 记录行数与哈希，追加前校验前驱、追加后原子刷新；验证时要求工作账本保留 Git HEAD 已审核账本的有序前缀。历史响应被覆盖且哈希对不上时，只能得到「缺失证据、未评估」，不能得到 PASS。
  • 离线重放。冻结的 Run 可以在不接受任何 AI 适配器的情况下重放结果与计算轨迹；确定性路径的 Run 明确记录模型调用次数为零。

11.2 把 AI 关进笼子：一个出口、一次调用、可审计

  • 唯一的模型出口。一道机器门（tools/check_provider_egress.py）用 AST 扫描 scripts 与 tools 下全部生产代码，规定只有 ai_adapter.py 里的一个函数可以打开模型请求，其调用方集合固定；动态金丝雀测试同时证明未授权入口的打开次数为 0。
  • 单飞（single-flight）与幂等。调用控制器用文件系统的 O_EXCL 预留一次出口，写下不可变的 egress / attempt / execution / response 收据；成功的精确响应按内容哈希复用，第二次以同样输入恢复时模型调用次数为 0。
  • 失败即停，不自动重试。HTTP 402（付费问题）一次调用后整批停止；结果未知（UNKNOWN_REMOTE_OUTCOME）不自动重试；429、超时、可恢复 5xx 至多允许编排器追加一次独立尝试。仓库不设金额硬上限，成本只作可观测量，但每个请求都受 200,000 token 的上限、8 MiB 载荷上限和资源硬边界约束。
  • AI 输入是可逆的压缩表示。表格网格先完整物化，再编码成紧凑格式发送；测试要求 11 组样本 decode(encode(x)) 逐字段相等，篡改样本必须被拒绝。银行家族的分片把「分片集合 ID、序号、总数、范围、检查过的表 ID」一并绑进候选、证据、审核和 Run，缺片、重复、乱序、有候选后提前停止都直接失败。
  • 测量响应永远不能变成证据。为了估算上下文而发出的一次性测量请求，其响应被明确禁止复用为资格认证或发布证据；SYSTEM 自动审核的记录写明「不冒充人工批准」。
  • 语义审计。另一道门（tools/check_vnext_semantics.py）解析 vNext 可执行代码的 AST：业务语义字面量只允许出现在目录、需求快照和测试里，出现在可执行代码中即失败；AI 适配器被禁止直接导入 SEC 传输、shell、子进程、文件系统或广义网络模块。

11.3 失败即关闭：默认拒绝，而不是默认通过

  • 缺输入不会变成空通过。验证门要求把关键缺口写成 WORKSPACE_INCOMPLETE 或 NOT_EVALUATED_MISSING_EVIDENCE，不能由空列表形成 PASS；报告写入失败时验证清单保持 IN_PROGRESS，不允许留下「成功清单 + 旧报告」的终态。
  • 未知即错误。必需字段缺失、未知状态、未知运算、未知 guard 或质量等级、依赖环、公式 AST 超过 32 层或 256 个节点，都在解析阶段直接失败。
  • 对不可信输入设预算。年报 HTML 的字节数、表数、每表行列数、rowspan/colspan 属性长度、实体引用长度都有集中声明的上限，调用方不能通过公开参数放宽；银行年报的完整物化在 512 MiB、120 秒、无网络的硬边界下完成并留下基准收据。

11.4 验收与治理：把「谁批准了什么」也变成可校验的字节

  • 三轮终态验证。正式刷新不是「跑一次成功就算」：切换新版本、回滚到前一版本、再恢复，每一轮都在一个固定的版本视图下依次执行 Golden、报告读回、发布验证、快照发布与校验；任何一步都不能重新打开指针、调用模型或修复数据。
  • 离线验收有操作系统级围栏。记录式验收在 macOS 上用 sandbox-exec 对整个子进程树施加「拒绝一切网络」的配置，并保护正式指针、镜像和快照不可写；Python 审计钩子只是第二道防线。缺少这个原语时验收直接失败，而不是退化成「大概等价」的实现。
  • 决策有编号并进入哈希。需求快照、决策记录、功能设计、issue 正文的哈希都写进批次清单；负责人的每次批准绑定确切的提交与闭包，换一个提交就要重新批准。文档中 150 多个「能力锚点」注释由 tools/check_capability_contract_alignment.py 机械校验：锚点唯一、引用的文件与 Python 符号必须存在。
  • 可扩展性是被检查的属性。生产代码里不得出现公司名、CIK、ticker、固定申报号或固定日期的分支，由 tools/check_no_company_literals.py 扫描并写出审计表；这就是「新增同行业公司不改生产代码」能被相信的原因。
  • 测试规模与政策。tests/ 下共 860 个测试函数，其中 vNext 部分 57 个模块、约 4 万行；快速入口并发执行短小的确定性用例（每例 30 秒上限），并明确规定「PASSED_FAST_LOCAL_ONLY 不等于 CI、live 或完整验收」。

  • 经济意义优先于公式可算。负权益下的债务权益比、非正营业利润下的利息覆盖倍数、后继主体 stub 期的年度指标，都标为「不可比」而不是输出一个数。
  • 口径边界写进 notes。RPO 不等于 ARR、融资子公司债务不能与制造主体混算、「and other」项不计入折旧摊销、重建的营业利润标为近似——这些都随结果一起交付给读者。
  • 证据表与主表分离但可关联，每条证据行带 URL、仓库相对路径、内容哈希、申报号、文档名与抽取方法，读者可以从任何一个数字回到原始字节。
  • 面向不同读者的文档。除架构与测试文档外，还有业务用户指南、CSV 交付设计、验收快照说明，以及三份可交互的机制讲义（信任升级、读表证据链、发布事务）。

12 容易误读的地方

十二个常见误读与实际情况

  1. 这是「把年报交给 AI 生成 CSV」。
    CSV 由确定性代码生成。AI 只出现在读表格这一步，只能返回坐标与原文，程序重读单元格验证，审核通过后才成为事实。24 个指标的目标路径完全不用 AI。
  2. confidence 列是模型的正确概率。
    它是按状态固定的投影值：直接事实 0.95、派生 0.90、酒店 AI 表格 0.85 等，同一状态下所有公司相同。
  3. 看 MDA_OK 或 parser_version 就能知道这行是不是新架构生产的。
    这些是兼容字段。240 行由新架构生产，但证据表里只有 2 行标着 vnext_projector_v1。生产者只由发布计划决定；JPMorgan 的 A11 虽然是 MDA_OK，却是旧路径结果。
  4. Bank of America 也在公司名单里。
    它和 Citigroup 只是银行家族资格认证的对照来源（第二版式与 holdout），不在十家生产名单里，CSV 中没有它们的行。
  5. 事件指标的 0 就是「没发生」。
    0 只能在完整来源集合证明窗口内所有 8-K 都扫描过之后形成，状态是 NOT_AVAILABLE_SEC，与普通 OK 零值不同；漏下载材料时不允许写 0。
  6. Run 冻结（FROZEN）就等于已发布。
    冻结只是封存。验证失败或结果被扣留的 Run 也能冻结以便审计，但发布会拒绝它们。
  7. 最新提交的年报就是最新财年的年报。
    旧路径按提交日期排序，晚提交的旧年度修订稿会排在前面；新架构的年度链按报告期排序。这是一个已识别的缺口。
  8. 系统会自动采用修订稿里更正的数字。
    旧路径把修订稿选为目标后立刻绕回原始 10-K，新架构根本不看修订稿。修订稿更正财务数字时，两条路径都沿用原始数字。
  9. 只计算最新一年，所以只下载最新一年的数据。
    Company Facts 是整份多年聚合文件（Marriott 的收入事实覆盖 FY2009–2026），下载后再筛；submissions 也补充历史分片。
  10. 已经支持按公司增量更新。
    只有历史分片存在即跳过这一处复用；没有条件请求，没有指定公司只补缺失的入口，没有增量计算和增量发布。底层能力允许实现，但尚未组织成流程。
  11. 仓库里的「第十一家公司样本」证明新公司已经跑通。
    它是按行业 profile 准备的模拟事实清单，证明不改生产代码也能让抽取器工作；不是真实下载并发布的第 11 家公司。
  12. 快照检查失败说明 CSV 被改过。
    根目录 CSV 与正式版本包字节一致。失败的原因是 8 月 28 日之后为银行家族新增的下载、认证周期和账本行不在旧的验收绑定里，即当前检出点没有重新完整验收。

术语、方法与来源

13.1 术语表

SEC / EDGAR
美国证监会及其电子申报系统；本项目只访问 www.sec.gov 与 data.sec.gov 的公开接口。
CIK
SEC 给每个申报主体的编号。一个逻辑公司可以有多个 CIK（如 Paramount 的前身与后继主体）。
accession
某一次申报的唯一编号，形如 0001048286-26-000007。
submissions
按 CIK 提供的申报目录：文件类型、提交日期、报告期、主文档名等；不含正文。
Company Facts
SEC 汇总的公司级标准 XBRL 事实接口，一个 CIK 一份 JSON，多年多概念，无维度。
XBRL / iXBRL
机器可读的财务标签。iXBRL 内嵌在 HTML 里，数字可带 scale（数量级）与 sign 属性，解析时必须处理。
10-K / 10-K/A
年度报告 / 对年度报告的修订或补充。修订稿不一定包含完整财务报表。
DEF 14A
股东大会代理声明，包含董事会与高管薪酬信息。
8-K 与 item
重大事件报告及其条目编号（如 5.02 高管变动、1.03 破产、4.02 重述）。
profile / traits
行业分类及其投影出的业务特征，决定指标是否适用、挂哪些抽取器。
vNext
仓库内对新架构的称呼：Run、证据检查、审核、投影、版本包等机制。
Run · FROZEN
一个「公司 × 指标」的完整证据包；冻结表示封存，不表示可发布。
ReleasePlan · R1/R2/R3
发布计划，内容寻址、逐级继承；它是「哪些指标由新架构生产」的唯一权威。
Publication · CAS
不可变的整体版本包；切换指针时要求前一版本仍是预期版本（compare-and-swap）。
资格认证（qualification）
AI 表格链上线前在开发、第二版式、holdout、fresh 来源上的验证流程。
Stage-A 快照
在不重写历史验收快照的前提下，把当前源码树与冻结收据绑定的覆盖层。

13.2 本报告的核对方法

  • 读取并统计仓库文件：config/、catalog/、outputs/ 下的主表、证据表、覆盖表、申报清单、事件表，三份发布计划，投影清单，冻结收据与 Stage-A 快照，R3 的 20 个 Run 记录，银行家族认证周期的 provider 账本，evidence/ 下的 submissions 与 Company Facts 原文。
  • 逐个打开关键函数确认行为：申报发现与排序、8-K 窗口、修订稿备用规则、指标取目标、审计师例外、历史分片限制、下载客户端、条件请求（无）、新架构的年度事实链。
  • 实际运行：只读的验收快照检查（失败，输出见第 10 节）；两个单元测试套件（20 个用例通过，无网络）；根目录 CSV 与版本包的 sha256 对比（一致）；热力图配色的可访问性校验（明暗两套主题通过）。
  • 没有做：调用 SEC 或模型接口；修改任何代码、CSV、账本或快照；重跑任何阶段；逐家核对修订稿正文。
  • 报告中的示例数值是流程示例，不是重新验收后的结论，也不构成任何投资或财务判断。
