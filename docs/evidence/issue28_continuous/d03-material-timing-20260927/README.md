# D03 recorded material: measured repeat authentication and bounded repair

Current pushed CI `36279090167` failed because `D03RecordedResponseStoreTest` returned 124 after 300.109 seconds, while its other saved-source shard succeeded. This is a per-selector timeout, without a business assertion failure. The earlier 240-second timeout remains separate history. No timeout is increased here.

`before.log` runs the exact existing positive material test with phase wrappers on local Python 3.14: 116.660 seconds total, six complete source rebuilds taking 113.688 inclusive seconds. The original test prepares source and a simulated model request once each; packet **record** builds and authenticates the same candidate twice, and independent packet **replay** also builds and authenticates it twice. The validation and grouping costs are included in those inclusive figures, so their totals must not be added to wall time. Two initial measurement attempts stopped before the target because the script lacked the repository import root and offline `uv` chose Python 3.9, which lacks this test's `enterContext`; their error logs are preserved.

The repair lets `validate_candidate_response()` build and authenticate one request, then optionally return that exact request together with its checked result. Existing callers with an explicit request still receive the same result shape and must match the rebuilt request. `record_offline_response()` snapshots its in-memory source/request and authenticates once before writing exact bytes; it rejects mutation of the caller inputs. `replay_offline_response()` authenticates independently once from disk, compares the saved candidate request, and still checks every packet file, identity, raw response, unresolved status and tampering. No previously computed source check is trusted across record and cold replay.

`after.log` executes the same complete positive and tamper test: 80.409 seconds, four source rebuilds taking 78.205 inclusive seconds. Record fell from 37.655 to 19.055 seconds; the substantive cold replay fell from 36.909 to 18.686 seconds. The total local reduction is 36.251 seconds (31.1%). The `RegulatoryFactReviewTest` directed suite passed 2 tests, retaining default output and testing the opt-in authenticated-request return. After adding an unknown-module-hash rejection, `final-material-tests.log` records both D03 packet tests passing in 80.510 seconds, including the complete original-source, independent replay and tamper branches. These local timings do not guarantee a hosted runner's duration; new-head CI must decide that.

The previously saved version-1 offline packet keeps its original creator module SHA and packet ID. `historical-cold-read.log` replays the original packet in an independent process with network and subprocesses forbidden: original packet ID `sha256:4bac51a935deadda11f456ba39f6976647fe2d5cd05fe194f89fbc7ef7ce02d6`, 1350 raw-response bytes including U+037E, two unresolved items, no native Result/Run and zero calls. The old packet is not re-signed. This compatibility path does not create provider execution credit or authorize D03 calls.

The first exact-SHA [limited review](independent-review/conclusion.md) found that accepting either old or current creator-module SHA based only on the packet's self-computed ID did not establish its creator: an allowed SHA could be swapped and the ID recomputed. It also noted a pre-existing file check/read race. The follow-up binds the old SHA to the **one known historical packet ID**, lets cold readers supply an external expected packet ID, and hashes/parses each stored file from the same byte read. This strengthens the offline identity claim; a newly self-authored packet still requires an external expected ID if a caller needs identity with a prior artifact. It does not become a provider execution receipt. `historical-expected-cold-read.log` confirms the original packet ID, raw response and two unresolved items with network and subprocesses forbidden. `repair-material-tests-final.log` records two complete material tests passing in 78.737 seconds, including unknown SHA, different packet claiming the old SHA, wrong expected ID, credit rewrite and file tampering. The initial repair test failure is retained in `repair-material-tests.log`: its proposed negative was byte-identical to the actual old packet and therefore legitimately reproduced the old packet ID. The first review's `NEEDS_FIX` remains historical for its original SHA.

The exact-SHA [follow-up review](independent-review-followup/conclusion.md) is **PASS_WITH_BOUNDS** for that repair. It confirms the old SHA is paired only with the exact old packet ID and that each payload is parsed from its checked byte read. It does **not** claim a new self-authored packet proves which process wrote it, or that arbitrary current-SHA re-signing is detectable without an external expected ID. The earlier `NEEDS_FIX` remains the conclusion for its original SHA. Hosted CI and D03 native/business completion are separate gates.
