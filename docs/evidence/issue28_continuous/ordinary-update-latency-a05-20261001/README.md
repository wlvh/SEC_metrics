# Salesforce ordinary-update latency: bounded A05 measurement

The earlier Salesforce FY2026 private 36-metric update took 22,744.446 seconds. `prior_timing.py` read its already saved terminal times and file modification times without rerunning it. Eighteen successive terminal intervals exceeded 900 seconds. The long wait appears at different points relative to saved Run records and public rows, so the old timestamps alone do not identify a single slow function or prove a 900-second software timeout.

The local macOS `pmset` log supplies the missing explanation for most of that wall time. `sleep_correlation.py` paired system Sleep with the next Wake/DarkWake and intersected those intervals with the already saved terminal times. Across 35 successive terminal intervals, **19,484 of 21,780.828 seconds overlapped logged system sleep** (about 89.5%); all 18 long intervals crossed sleep. One exact example: A03 completed at local 05:46:06, the host entered sleep at 05:46:06, resumed at 06:01:06, slept again at 06:01:51, resumed at 06:16:51, and A04 completed at 06:16:52. This is strong evidence that the six-hour wall clock mostly reflects a sleeping host, not a fixed 900-second application wait. It does not measure active CPU time or exclude other computation cost.

The first A05 profile attempt (`run.log`) failed before processing: the previously installed source copy was bound to an older mutable V14 requirement identity. That is an expected rejection after the B13 change, not an A05 execution result. The repaired `profile_a05.py` used the existing authenticated #28 acquisition root to create and verify a new private processing copy for the current V14 closure. Creation of that copy took 3.867 seconds. The normal `tools/vnext_normal_update.py --process --company salesforce --metric A05` entry then returned `CANDIDATE_READY` in **152.841 seconds under cProfile**, with 116 old semantic production exports disabled and sockets, DNS and HTTP blocked. The original claims, source request log, and formal active pointer had the same hashes before and after. No provider, paid or SEC request was made. This is one private diagnostic Run, not a new fiscal-year update or a new 390-coordinate acceptance.

`profile.txt` shows repeated, nested work in this one Run: `prepare_case` ran nine times, current-source proof verification 31 times, acquisition-checkpoint validation 32 times, and requirement loading 11 outer calls. These are cumulative profile times and overlap; summing them would double-count. The run did **not** reproduce an individual 900-second stall even with profiler overhead. There is measurable active computation cost, but no evidence here that it caused the prior six-hour wall time or that source authentication and cold-read checks should be bypassed. No production code or resource limit was changed.

Evidence: `prior-timings.json` (old saved timestamps), `sleep-correlation.json` (reduced local power-state events and overlap, without unrelated system messages), `result.json` (current V14 one-metric result), `profile.txt` (function costs), `run-final.log` and `run-final.exit` (execution), plus the retained initial failure. The earlier 36-metric output remains intact. A future optimization should first reproduce a specific costly operation while the host stays awake, with unchanged source and authority checks, then test both legitimate completion and tamper rejection. Do not replay the six-hour 36-metric run merely to obtain another wall-clock number.
