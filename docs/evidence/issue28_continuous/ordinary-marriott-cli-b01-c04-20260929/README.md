# Marriott B01 + C04 in one normal update CLI call

This checks an integration gap left by the separate Marriott B01 and C04 demonstrations: whether the **normal update entrypoint itself** can create both metrics in one invocation, route C04 to its explicit four-form successor, and keep both histories stable on an identical-input repeat. It uses the existing authenticated #28 cumulative saved source, a new private state root, no network, and the current unfrozen V14 closure `sha256:7cf19f62e7c84656dc2d1fb2f06cbcaa7a1d501b90d9e9dd372c54a7148f6a5c` at code head `76ebe42e`. The processing source snapshot ID is `sha256:cd1cc2feff4cfa3347fac80c7b23248ed5026d71b87a0f240c563287ffdef228`.

`run.exit=0`, `create.log`, and `create.json` record `tools/vnext_normal_update.py --process --metric B01 --metric C04` returning company `UPDATES_READY` and **both metrics `CANDIDATE_READY`**. The check disabled 116 old semantic producer exports. B01 Result ID is `e279b28d...`, the same as the earlier saved-source B01 candidate; C04 Result ID is `d41ffcee...`, the same as the real source-refresh C04 candidate. `check.py` does not select the filings, result values or C04 route for the CLI. It compares the original #28 claims, source log and active pointer SHA-256 before/after, requires zero provider/paid/SEC calls, and blocks socket, DNS and HTTP. A first detached shell launch created empty logs but no process or result; it is **not** counted as an execution. The persistent `nohup` command session produced the recorded run.

`read.log` and `read.json` come from a separate Python process. It reauthenticates the processing source and replays each installed native candidate and public row under the current verifier. B01 is `PUBLISHED/PASS`, FY2025 ending 2025-12-31, revenue value `26,186,000,000`; C04 is `PUBLISHED/PASS`, the same period, value `0`, with configuration route `C04_REGISTRATION_FOUR_FORM_UPDATE_V1`. Both Result IDs match the create record. The old producer exports remain disabled during read.

After the create/read pass, `repeat.exit=0`, `repeat.log` and `repeat.json` record one identical-input invocation of the same two-metric CLI. Both rows return `NO_SOURCE_CONTENT_CHANGE`; neither creates a candidate, and both `successful_attempt` pointers stay unchanged. This follows the actual history model: a repeat may record a new latest attempt while preserving the successful version. The original claims, source log and active pointer remain byte-identical, with real calls `0/0/0`. The extra repeat branch was added to `check.py` after the create/read execution; it did not change either earlier branch or the product code.

This removes the need to invoke B01 and the C04 successor separately for this **saved current-period source**. It creates no new complete company or 390 coordinate: both business results already existed. It does not prove old-current-to-new-current online discovery, an authentic historical pre-filing submissions response, all 36 metrics in one CLI call, B13/D03 completion, formal publication, or retirement of all old entrypoints. The private state under `/private/tmp/issue28-marriott-cli-b01-c04-20260929` is not a published installation or portable artifact. No #47 branch, ledger, snapshot or PR was operated.
