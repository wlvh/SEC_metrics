# Saved-source CI: three exact shards after a 35-minute cancellation

The [ba7b5f88 main CI](https://github.com/wlvh/SEC_metrics/actions/runs/36466326739) saved-source shard 1 was cancelled at the **35-minute job ceiling**: checkout ran 18:36:03–18:41:59 UTC (5m56s), then the source-material command ran 18:42:01–19:11:15 (29m14s) without a final selector JSON or business assertion failure. Shard 0 succeeded. This is distinct from the prior head's two 240-second B03 selector exits and from the separate program-role timeout. Its completed [job log](https://github.com/wlvh/SEC_metrics/actions/runs/36466326739/job/109077198596) contains no per-selector completion list because the runner writes that JSON when the command finishes.

The earlier [f415bd3e successful CI](https://github.com/wlvh/SEC_metrics/actions/runs/36433946153) gives an actual 82-selector timing sample: shard 0 completed its tests in 13m41s, shard 1 in 26m40s, with about 25 seconds of checkout in each job. `previous-success-timings.json` retains only selector names and elapsed seconds extracted from those successful job logs (job IDs 108966905276 and 108966905256), not large runner archives. The selector elapsed totals are 1,527 and 3,161 seconds under the **current** two-shard assignment; they are process-time sums and do not equal the concurrent two-worker job wall times. Six B03 selectors were added after that timing sample, three assigned to each two-shard part.

`schedule.py` imports the unchanged current `SOURCE_TESTS` list and proves that both the old and proposed modulo partitions contain each of the **88 current selectors exactly once**. With three shards, the *known* elapsed sums are 1,668, 1,405 and 1,615 seconds; two new selectors in each shard lack prior remote timing. This is evidence for a more even allocation, not a guarantee that all jobs will finish or that their assertions pass. `distribution.json` records exact selector assignments and untimed entries; `schedule.log` records the check.

The workflow change only sets `shard_index: [0, 1, 2]`, passes `--shard-count 3`, and renames the aggregate gate to “Require all complete source shards.” The aggregate still requires the matrix job's success. No test selector, runner body, per-selector limit, 35-minute job limit, model call or source is altered. A new-head CI must show **all three** saved-source shards and the aggregate passing before this cancellation can be considered repaired. The previous cancelled run is not upgraded to success, and this local scheduling proof is not a business-result validation.

No real provider/paid/SEC call was made; #47/PR52 and production were not operated. The shared workflow is additive for this branch and its impact is registered in the #28 execution state for the stacked consumer to evaluate independently.
