这是一项**零模型/零SEC调用**的资源预检，不是D03回答、模型准确性排名、原生Result/Run或新调用许可。代码根为本轮已推`cf23ab3d`，生产源码未改；使用 `/private/tmp/issue28_py314_venv/bin/python` 中的 `tokenizers==0.22.2`、仓库封存的DeepSeek v4.1 tokenizer和原4096输出令牌上限。`run.zsh`、`census.py`、`census.log`及原子写成的`census.json`保留执行过程，网络/SEC入口在进程内禁止。

`prepare_native_input()`重新构造十家公司当前完整D03来源及有效请求；每家来源ID与[此前130组输入普查](../d03-current-input-census-20260927/README.md)一致，组数仍为 **130**，全部源单元由准备函数核对。程序必评引用合计178项；逐组最大为33项、单元内23项，低于当前单元128条finding上限。三种**人为构造的紧凑JSON情景**分别是：仅必需字段的空单元结构；把程序必评引用列在context字段；以及每项一个极短占位finding。前两种不等于完成业务评估，第三种使用`OTHER_MEANING`等占位标签，也不是真实或已批准的语义答案。

在这三种情景下，130组都未达到4096令牌：当前全组最大分别为 **468、468、2032**。JPMorgan第0组是唯一含来源事实后继合同的组，根响应还要求`candidate_reviews`；初次全组情景没有计入该字段，不能直接称它完整。`successor-overhead.py`对这个组独立重建同一有效请求并补测该字段，`successor-overhead.json`记录其三个情景从253/313/2032增至**260/320/2132**；它仍未碰4096。因此，在这些最短输出形状上，**没有发现必然装不下的组**。这只解除一个结构性硬阻断假设：实际模型可能给出更多发现、更长理由、未决与冲突，仍可能在4096截断或语义失败；单元送入请求也不证明相关含义已被识别。

本次没有修改分组、删来源或必评项，亦没有执行响应验收和公司Result。若沿当前一组一次且无有效复用执行，D03首轮仍为条件性的130次，相对原账本provider/paid剩余97次至少差33次，尚未包括B13及补验；本核对不构成增额申请。下一道工程关口仍是将完整响应与实际执行身份、原生Review/Result/Run可靠相连，然后才能根据真实输出重新计量资源。原账本、#47及生产入口不变。
