# Southwest E01: item-code count conflicts with “M&A announcements”

The current #28 Southwest FY2025 private E01 Run is historically `PUBLISHED/EXACT` with value **2** and Result ID `sha256:476829da253cedc01e18608c87c3d98eb952e48f3180d2b0254e96c2f73ffff9`. It matches the retained 390 index's identity and value. `audit.py` follows its two `matched_verified_claim_ids` to their saved primary source references and independently checks each original body's SHA-256 against the accepted `RAW_BLOB` identity. Both selected claims are **Item 1.01**; no model or SEC request was made.

The first 8-K (`0001193125-25-029062`) reports an **amendment to Southwest's shareholder cooperation agreement with Elliott**, changing permitted economic exposure and ownership restrictions. The second (`0001193125-25-262544`) reports a **$1.5 billion debt securities offering** and its indenture. `audit.json` retains the exact Item 1.01 visible sections, their hashes, source URLs, original raw-body hashes, claim IDs and Run/Result identities. Those sections do not describe Southwest entering a merger or acquiring a business. This is a direct conflict between the currently displayed metric name **“M&A announcements”** and what its present **direct Item 1.01** route counts. It does not decide whether the product should instead be a broader “transaction lead” count.

The code-level 8.01 behavior is a separate implementation issue. With a valid `hdr.sgml` item list, `deterministic_router.py` constructs the brief `8-K item 8.01 parsed from hdr.sgml`; `match_event_claims()` tests the E01 aliases `merger`, `acquisition`, `combine`, `transaction` against that brief. The original primary body is authenticated and stored but its Item 8.01 text is not used for those alias checks. The exact synthesized brief contains none of the aliases, as `audit.py` confirms. `check_801.py`, `eight01.log` and `eight01.json` exercise the existing repository fixture whose authenticated primary **explicitly says “Item 8.01 The company announced an acquisition transaction”**: the adapter returns an 8.01 claim, while current E01 matching selects only 1.01. This is a function-level reproduction of the missing **body-to-keyword connection**; it does not assert any particular real uncounted 8.01 filing is an M&A announcement.

`delta.json` is a **one-coordinate difference against the existing 390 index**, not a new 390 table. It keeps the historical Southwest E01 Run, Result and value 2 intact while marking current “M&A announcement” business credit `UNVERIFIED_PENDING_ITEM_CODE_VS_CONTENT_DEFINITION`. The retained parent index has **six positive E01 company coordinates and 19 counted items**, but only Southwest's two selected items were semantically inspected here; the other 389 coordinates and other companies' E01 filings were not audited. The business decision is whether E01 remains an item-code transaction lead or requires issuer/subsidiary M&A confirmed by source content. Until resolved, neither silently replacing 2 with 0 nor calling the old 2 verified M&A is justified.

The first evidence-script attempt in `audit-first.log` failed because a later 8-K section referred back to “Item 1.01” and the section locator treated that cross-reference as a second heading. The corrected audit requires the actual `Item 1.01 Entry into a Material Definitive Agreement` heading and passed (`audit.log`). That is a test-script fix only. No product code, frozen route catalog, old Result/Run, real #28 ledger, active pointer or #47 artifact was changed. The real provider/paid/SEC increment is **0/0/0**; this audit does not prove current E01 correctness for all ten companies or complete 390 acceptance.
