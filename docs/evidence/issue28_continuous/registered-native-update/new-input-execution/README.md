## 已接与尚未接的场景

| 输入场景 | 补丁行为 |
| --- | --- |
| 原完整成功集合仍有效，或仅获取记录变化而完整输入等价 | 原 bridge 逐收据/当前内容检查，0 调用登记并进入原普通更新 |
| 当前确切来源只有部分请求成功，其余从未尝试 | 保留确切成功；本轮额度内执行尚未尝试请求；额度不足时留下原终态，下次只补未尝试项 |
| 新年报/新来源使所有待补请求的实质内容都变化 | 经原完整来源工厂、当前有限格式和原执行器补齐；具体原件还须通过已有源与分类能力检查 |
| 新修订使整体 source_id 变化、其中部分组仍与旧尝试实质相同 | **跨来源组复用仍未实现**；先核对全部待补组，命中旧摘要就整项拒绝新调用，不能换输出合同重抽。此项仍是开发责任 |
| 任一旧成功当前重放失败、来源/收据损坏、完整集合歧义、运行规则缺失 | 原异常继续传播；不进入“缺记录后执行”分支，不登记披露限制 |
| 旧请求 FAILED/UNKNOWN | 不自动尝试 BASE/INDEXED 另一版本；原失败保留。UNKNOWN 所属 provider 通道停止，其他零调用更新仍可继续 |
| B13 LIVE / D03 | 新入口 B13 LIVE 固定暂停，无参数可解除；D03 不启用。B13 仅隔离 recorded 接线测试 |

这张表说明处理路径与明确缺口，不代表新年报/修订已做完整真实验收。来源缺原件、业务输入不足、实现不支持及尚未完成验证继续分别记录。

## 最小改动

- 原 `capacity_update_input.prepare_registered_update` 追加内部可选 `allow_incomplete`：仅确知没有完整集合时返回当前受信请求。默认行为不变；歧义及所有内容/真实性异常仍抛出。
- 同模块追加 `ensure_native_update`。先合法复用，再检查 BASE/INDEXED 两种实质请求摘要有无历史尝试；仅必要且从未尝试的请求进入原 `execute_d04_assessment` / recorded B13 执行器。200000、8MiB、120秒、零重试、总账、原离线接线及 D-36 均沿原路径，不新建预算/历史系统。
- 原 `ordinary_refresh_cycle` 追加 `max_provider_requests=0`，仅依赖发现与本轮刷新完整时准备新原生请求；所有公司/指标共用这一个有限计数。其他指标仍走原 `run_company` 历史。没有 model 额度时维持原0调用行为和报告形状。
- CLI 新增 `--max-provider-requests`，默认0。报告将自身新增请求与整个固定总账增量分开；异常发生在 claim 之后仍按该请求原 ordinal 归属计数，无法核对则报告 UNKNOWN 并停止受影响 provider。
- 新测试文件随补丁提供：`tests/vnext/test_native_refresh_execution.py`。
