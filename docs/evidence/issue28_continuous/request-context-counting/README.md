# 完整请求计数与同一累计资源计划

本材料是离线工程测量；新增 provider/paid/SEC 为 **0/0/0**。计数、分组和原生接线测试都不代替真实公司—指标结果、独立审阅、生产采纳或调用许可。

## 本次确定的增量

`continuous_request_context.py` 只接受当前服务三元组 `deepseek / deepseek-flash / chat_completions` 和确定的两条纯文本消息、`json_object`、温度0、非流式、禁用thinking、4096输出格式。完整计算system、user中全部原文和共享字典、来源身份、导航、响应合同、最终request_id，以及服务格式的JSON提示、起始/角色/生成标记。输入计数加4096输出预留后检查原200000上下文；8MiB、120秒、零自动重试均保持。

固定官方分词文件和格式参考提交 `dba1be0a40aa45a94ad051997016db3960a90277`，固定 `tokenizers==0.22.2` 与两种部署平台的wheel哈希。原分词JSON 6,367,257字节以1,868,514字节gzip保存；使用前每次核对资源SHA，缓存仅省去重复解析。具体SHA、许可证和安装方式在 `config/tokenizers/deepseek_v41/` 与 `requirements-continuous-context.txt`。

格式不支持时明确拒绝。缺少确定版本的分词引擎时，独立计数可退回完整已渲染提示的UTF8字节上界；新分组必须有确定引擎，否则拒绝，避免同一来源在不同机器生成不同请求。LIVE实际input+output超200000报 `CONTEXT_LIMIT`；实际输入usage与本次完整参考计数不符报 `CONTEXT_REFERENCE_MISMATCH`，保留原始响应和usage，暂停受影响调用通道。记录响应里的合成usage不参加真实服务一致性认定。

新来源显式保存 `request_context_format=deepseek-v41-two-message-json-chat-1`；默认旧来源不新增字段，保存的旧请求保持原分组。D04/B13继续使用现有可完整恢复的表示，D03保持原始单元，不加入新压缩或语义提示。所有分组先构造带最终身份的完整请求，再逐个计算；不跨文档、不丢单元、不截断原文、不依导航缺少判无披露。每个不可再分的超限单元明确报错。
