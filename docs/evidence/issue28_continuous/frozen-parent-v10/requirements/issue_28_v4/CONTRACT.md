# Issue #28 v4 — ordinary annual B10 candidate execution

This revision adds S-ANNUAL-CANDIDATE to the exact issue_28_v3 parent. The
owner's current-task policy-content approval is captured in
`docs/evidence/issue_28_annual_candidate_policy.json`. This is development
policy authority, not exact-head activation, provider authorization or a
publication approval. The revision remains NOT_ACTIVATED.

An ordinary candidate uses Marriott B10 and the unchanged catalog task
lodging_occupancy_table_v2. Company, task and supported saved annual-source
rules belong to policy; fiscal year, accession, immutable request evidence,
complete-document request, code and isolated Run coordinates belong to the
plan. A new annual input needs a new plan and owner grant, never a fixture or
new Requirement version. Old R4 and qualification grants cannot authorize it.

One fresh owner grant permits at most one new provider execution, retry=0,
SEC=0, measurement=0. Reentry only reads the saved Run. Failure, unknown remote
outcome and incomplete local materialization never authorize a second call.
The existing successor WB-3 reservation/ledger/terminal controller is reused.

The UTF-8 byte estimator, payload/resource limits and model context ceiling
remain unchanged. For an independently reviewed exact request, actual usage
from its new provider response is a mandatory post-execution acceptance gate:
input <=200000; all usage counts must be present and internally consistent.
This is not a guarantee about actual input tokens before egress. Missing or
excessive usage or content failure stops the candidate. Historical usage is
reference only; there is no measurement or historical-response reuse credit.

Historical lodging qualification is evidence of the unchanged Reader under
its original code and source conditions. The capture binds the unchanged
Reader/parse/serialization/Spec/Evidence/Review/Calculator files. Changes only
to ordinary policy, permission binding and identity dispatch do not require
re-running historical qualification. This limited compatibility decision
applies only to the ordinary candidate path; old freeze and qualification
validators retain their old interpretation. It cannot cover Reader or
business-judgment changes, and it confers no new qualification credit.

The native SUCCESSOR_RUN records the new Requirement identity and retains the
existing Evidence, D-06 SYSTEM Review, Calculator and MetricResult semantics.
The execution binding is included in the existing Run artifact closure. The
candidate writes only to its plan-bound external directory. It has no
qualification or publication credit, cannot update active or root mirrors,
and does not resume PR34, migrate a new metric or finish automatic updates.
