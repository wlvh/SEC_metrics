# C04 一条SEC来源的受限续接

第193槽真实申报清单GET后，原有限刷新入口在下一次`max-sec-requests=1`调用会重新选择申报清单。新增的`--resume-report`只处理**单公司、单独C04、前次恰好一个成功SEC来源、此次最多一个新SEC请求**。调用前从原账本重读前次末槽的不可变`sec-plan`、收据和终态，并逐字节比对前次报告；再核对来源账本、同一C04更新状态和原结果前驱。前次报告不符、旧报告再用、换公司/指标、来源字节改变或下一个URL不在前次未完成集合及当前C04来源证明中，均不得取得续接信用。新请求仍经原`SecAcquisitionSession.capture`、官方URL、原许可、固定账本、实际计数与零自动重试，不打开B13/D03或生产路径。

`resume-material-v13-preserved.log`在全新测试账本用真实保存的Marriott申报清单和Company Facts字节完成两次**录制**获取。第一步总刷新未完成；第二步用已认证的前次报告跳过同一清单，选择Company Facts，刷新达到`UPDATES_READY`且C04有正常候选。篡改报告URL及重复消费原报告都在新申领前拒绝，测试账本只新增两个不同的录制SEC槽，真实调用0。短测`boundary.log`另拒绝把此续接交给B01、混合范围或多于一次的本轮SEC上限。`real-resume-preflight.log`在原真实账本**只读**验证第193槽、原C04状态、来源字节及下一URL：当前应选`https://data.sec.gov/api/xbrl/companyfacts/CIK0001048286.json`，它在当前C04来源证明和前次报告的待刷新集合中；原账本仍143／143／50。`final-wiring-after-real-preflight.log`核对现行绑定和接线收据，不代表第二条真实GET已经执行。

实现期间曾尝试把额外的来源账本比较放进共享SEC获取模块；那会改变普通V13父级身份，使第193槽之后的C04既有更新状态不能续跑。该尝试**没有提交**，当时的实验日志`resume-material.log`只作为过程记录。最终实现仅改未冻结的V14刷新协调器和显式CLI；普通V13需求身份维持`sha256:a573ed50d6a5e09e3477de53e5a8f83b01a600220379fdc8d73aba19bb32b3a2`，C04旧成功不重签。新增检查在调用获取器之前再次比较来源账本；它不是对任意外部进程并发改写的完整原子保证，故下次真实申领前仍需核对没有新的#28账本槽。

本目录不新增调用额度、不重开第191／192次或其他失败、不打包旧原件。新差异须完成精确SHA限定独审后，才可在既有#28许可内用前次真实报告作一次Company Facts业务GET；新来源再出现未知URL时重新核对，失败或用量UNKNOWN依原规则停止。
