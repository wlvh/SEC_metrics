# LIVE 类耗时剖析与缓存决定（2026-09-28）

所有者在 2026-09-28 批准的合同变更第 2 项（Issue #47 评论 5870869079，
`../../owner-decisions-2026-09-28/decisions.json`）要求：先逐步剖析 LIVE 类，再决定缓存什么；只缓存以全部输入字节摘要为键的纯计算，只在一个进程内，不跨进程、不跨注错、不落盘；任何被注错的检查都不能被跳过，也不能由缓存作答；业务模块里的缓存要有自己的注错。

本目录是剖析结果和据此做出的决定。零模型、零 SEC 请求。

## 测了什么

在一棵等于提交 `296ebf30`、两个补丁都已应用并重铸的运行树里，跑
`TheLivePathSendsThePlannedBytesOnceThroughTheControlledOpener` 的类夹具和一个用例
`test_the_planned_bytes_go_out_once_and_count_as_charged`（最小的一个 D04 请求走一次计数发送）。
先用 cProfile 跑一次，再不带剖析器跑一次校准时间。脚本是 `profile_live.py`，数字在 `measured.json`。
测量时另一核上的顺序封存仍在运行。

| | 不带剖析器 | 带剖析器 |
|---|---|---|
| 类夹具（建请求两次、准备授权） | 38 秒 | 90 秒 |
| 一次发送 | 90 秒 | 203 秒 |

剖析器开销约 2.3 倍；比例以带剖析器那次为准，绝对时间以不带的为准。

## 时间花在哪里

**一次发送从申报原件重建来源五次**：计划时一次（`build_plan`）、认领前一次、GitHub 复核前一次、
打开 socket 之前一次（`before_socket_open`）、适配器交出字节时一次（`transport_payload`）。
每一次都是审阅要求的检查点：独立审阅曾经改动一个单元的文字、重算全部编号，请求照样到了 opener——
内容寻址只证明来源等于它自己，把它和申报原件绑在一起的是重建（L3）。不带剖析器时每次约 17 秒：

- 约 12 秒重建来源（`prepare_historical_d04_semantic_source`）：年报是 inline XBRL，同一份 HTML
  在一次重建里过 HTML 解析器约 24 遍——XBRL 事实解析 7 次（每次两遍，`_parse_xbrl_parts`）、
  期间判断 3 遍（`annual_period`）、文本文档 2 遍、财年标签 2 遍、原生单元/绑定来源/引文范围各 1 遍；
  再加上逐单元的规范 JSON 与哈希；
- 约 5 秒重新分组（`pinned_requests` → `measured_groups`）：每往组里加一个单元，就用参考分词器把整组提示
  重新数一遍，一个来源 19 次；
- 授权文件重新哈希（`_check`，每次约 0.15 秒）与已存来源证明（约 0.2 秒）很便宜。

类夹具的 38 秒是同样的来源建了两次（提案算摘要的方式一次、调用路径建请求一次）加上准备授权。

## 决定：业务路径暂不加缓存

能称为“纯计算、输入全部是传进来的字节”的，只有分组时的分词计数、以及给定字节的 HTML/XBRL 解析；
它们都在冻结的 #28 代码里，由冻结的 #28 调用链调到。要缓存，只有两条路：

1. 在 #47 自己的调用点外面包一层（像 `historical_text_results.shared_source_preparation` 那样）。
   这些调用点在规则文件里（`historical_semantic_source.py`、`historical_semantic_results.py`、
   `historical_annual_input.py`，后者被所有历史路线使用），改动会移动 Requirement closure；
   被包住的冻结函数内部还会读文件（政策文件、分词器、XBRL 实例），键要覆盖“全部输入字节”，
   就得先测出每个函数内部读了哪些文件、声明下来，再用一条用例把实测读集和声明比对——否则键是否完整
   只能靠推断。每个缓存还要自己的注错。
2. 运行时替换冻结模块的函数属性。这是在已经过两次安全审阅的调用路径里加一个新机制，
   而且对已经 `from ... import` 过函数名的调用方无效，不可靠。

整份来源重建本身不是这种纯计算：它在冻结代码里按路径读文件，输入不以参数传入；
审计钩子能记下读过哪些文件，但记不下“检查过不存在的文件”，所以键的完整性证明不了。

并行副本（合同变更第 1 项）不碰被审阅的调用路径，就能把封存从 7–8 小时降到 1–2 小时，
所以先只做并行。如果所有者还要再快：按上面第 1 条做“声明读集＋实测比对＋各自注错”的调用点缓存，
估计每次重建从约 17 秒降到约 5 秒，LIVE 类再快约 2 倍；代价是改三个规则文件、移动 closure、
新增用例与注错，并且整套 78 个注错要重新证明仍由同一批具名用例抓到。这一步等所有者决定，
不在本轮做。

## 不主张

- 这是一个类、一个用例的剖析，不是整套的逐用例计时；每次发送的五次重建在各用例里相同，
  所以一次发送的分解代表其余发送。
- 带剖析器的绝对时间偏大；决定依据的是比例和“哪些计算的输入能完整列出”，不是绝对秒数。
