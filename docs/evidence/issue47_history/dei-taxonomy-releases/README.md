# 更早年份的 DEI 命名空间：冻结读取器的一个判断，按视图换答（2026-09-29）

## 发现：第一轮真实取数就撞上

第一轮真实 SEC 取数（许可 `[0,0,1354]`）里，十家公司每一家都在取完年报链之后停下，停在同一句：`DEI_MISSING_OR_AMBIGUOUS:DocumentType`。218 次请求全部成功、零失败，停下的是取数之后的规划步骤（`first-round.json`）。

原因在冻结读取器判断"这个事实是不是 SEC 的 DEI 事实"的那一句：它只认命名空间 `http://xbrl.sec.gov/dei/` 后面跟四位数字。这是 2022 年起 DEI 分类版本的命名方式；更早的版本在年份后面接完整日期，或接季度（`dei/2021q4`）。Enphase 的 FY2020 年报声明的是按日期命名的版本，FY2021 年报是 `dei/2021q4`，两份各有且只有一个 DocumentType 事实，冻结读取器却报"缺失"。本仓库此前保存的每一份申报都是 2023 年以后提交的，所以这个写法从来没遇到过；五年框架一伸到 2021、2022 年提交的年报，第一轮取数就把它撞了出来。

这个判断要保留的是它的用途：申报人自己扩展的、名字像 DEI 元素的概念不是 DEI 事实。所以只放宽版本后缀，只认版本实际用过的三种写法：没有后缀、季度（`q1`–`q4`）、年份后接月日。`2021q5`、`2021-1-31` 这类不是版本的写法照样拒绝。

## 影响范围：不是一个函数，是一类问题

冻结代码里有 11 个模块写死了这个判断：年度读取器、财年标签扫描、文本文档构建器、业务文本来源绑定、治理与薪酬表读取器、两个修订读取器、金融发行人检查、持续经营来源等。#47 通过别的冻结函数间接调用它们。第一版只修了年度读取器和财年标签两层（逐个函数换绑），随后按调用链测量：静态调用图里，#47 有 23 个函数直接调用了 20 个最终会走到这个判断的冻结函数（`static-frontier.json`）；Run 级探针又证实装入、建 Run 两步都会碰到。逐个手工换绑要列出几十个函数，还有函数内 import、模块属性调用、登记表这几种绑定方式，手写清单一定会漏。

## 修法：`scripts/vnext/historical_dei.py` 的 `release_aware`

冻结模块不改，因为 `issue_28` 各世代按字节记录它们。#47 在调用这些读取器的地方改为调用视图（12 个模块）：

- 视图每次被调用，都用**冻结函数自己的代码对象**，在**它所在模块当时的命名空间**里运行，只有两类差别。第一，该函数自己问 DEI 问题时，`re` 换成版本感知的 `re`。第二，它读到的名字、以及它在函数体内 import 的名字里，凡是本身会走到这个问题的对象（函数、类、模块、登记表），都换成那个对象自己的视图。其余一律不变。所以对 `dei/` 加四位数字的申报（本仓库此前的全部申报），视图的答案与冻结读取器逐字段相同；放宽后的写法在那些申报里不会多接受任何东西。
- 命名空间每次调用时从模块现读，所以测试对冻结模块打的补丁在这些路径上照样生效。
- 视图改不到的引用（默认参数、闭包单元、包装器），只要会走到这个问题，就按名拒绝（`HISTORICAL_DEI_REFERENCE_NOT_REBINDABLE`）。用 `re.fullmatch` 以外的方式问这个问题，也按名拒绝（`HISTORICAL_DEI_QUESTION_ASKED_THROUGH:re.*`、`HISTORICAL_DEI_QUESTION_NOT_ASKED_THROUGH_RE`）。一个在某处悄悄保留冻结答案的视图，读起来会像已经修好。
- 完备性检查 `unviewed_references` 列出 #47 自己每个函数直接引用、会走到这个问题、却没有经过视图的对象。现在只剩 `run_store` 的三个入口。理由是：#47 的 Run 在 `run_store` 里被转交给 #47 自己的代码重放（`historical_run.replay_case`、`validate_run_authority`、`prepare_text_contexts`、`historical_text_results.text_api`），`run_store` 只会经由其他世代的重放走到这个问题。这一点由 Run 级探针的冷读实测，见下。

## 验证

- `tests.vnext.test_historical_dei`，23 例全过（约 60 秒）。剖析一次视图调用时的全局变量，逐个核对：与模块原有命名空间相比，只有 `re` 和走到这个问题的对象换成了视图。对冻结模块打的补丁在视图路径上照样生效。在保存的 10 份 FY2025 年报上，年度读取器的答案逐字段相同；在其中 3 份上，文本文档逐字节相同。构造的旧版本：把 Enphase FY2025 年报里的 `dei/2025` 改写成季度或日期版本，冻结读取器全部拒绝，视图读出同样的期间，同样的块、章节，以及同样的 D04 语义单元与注册人名称绑定。这里覆盖两条路径：模块全局调用（持续经营来源，三处判断分在两个模块）和函数内 import（`text_results.prepare_text_sources`）。`2021q5`、`2021-1-31` 仍被拒绝。默认参数里的冻结读取器、以 `re.fullmatch` 以外方式问这个问题的写法，都按名拒绝。
- 视图注错 11 个（`view_injections.py`，结果在 `view-injections.json`），全部被为它写的用例抓到。每次注错都在独立的字节码目录里跑；运行它的轻量副本与主检出的 `historical_dei.py` 逐字节相同。
- 导出写入顺序的 2 个注错（`../acquisition-wiring/export_publish_injections.py`）都被 `test_a_write_that_fails_leaves_the_export_already_there` 抓到，已记入接线收据绑定的 `fault-injections.json`。
- 规划器：在恢复的 Enphase/Ford 数据上（`evidence/issue47_acquired/` 的前 18 行加基线），修复前在更早年份的年报处报 `DEI_MISSING_OR_AMBIGUOUS:DocumentType`；修复后给出完整声明，其中事件窗口的 8-K 依赖 Enphase 66 行、Ford 220 行，代理材料各 4 行。这些正是第二轮要取的东西。
- FY2021 的 Run 级探针（`run_probe.py`，汇总由 `summarize_probe.py` 生成在 `run-probe-fy2021.json`）：Enphase、Ford 各 39 个指标，每个指标走装入、建 Run、冻结、公共行、另起进程冷读，并在两个进程里都记录每一次 DEI 拒绝及其调用链，网络与 DNS 全程禁用。结果共 78 个位置，其中：
  - 69 个出了公共行，冷读全部 FROZEN、结果编号相同；**DEI 拒绝总数为 0**。
  - 19 个有数值：两家的 B01–B05、B07–B09、D02，以及 Ford 的 D01。
  - 32 个是结构性不适用。
  - 18 个按名扣留：12 个零 AI 事件、2 个 B06、2 个 C03、2 个 C04，都是缺事件 8-K、代理等来源，第二轮取数要补。
  - 9 个失败，都与 DEI 无关：B13 需要语义审阅（2 个）；C02 缺当年代理（2 个，点名了缺的 URL）；D03 不在零 AI 集合（2 个）；D04 没有登记评估（2 个）；Enphase 的 D01 超出条数上限（1 个，见下）。

  修复前，同样两家 FY2021 的每个位置都在装入这一步以 `DEI_MISSING_OR_AMBIGUOUS:DocumentType` 停下。

## 不保证什么

- 这个修复只让读取器认得更早的 DEI 版本，不补更早申报里本来没有的东西。某个 DEI 元素在较早版本里不存在时，用到它的路线照样按名扣留，这不是本修复要解决的。
- FY2021 探针里的扣留，大多是事件 8-K、代理材料等来源还没取（C01、C03、C04、B06、C02），第二轮取数要补。B13 需要语义审阅，与 DEI 无关。
- Enphase FY2021 的 D01 在建 Run 时停在 `DETERMINISTIC_TEXT_HEADINGS_EXCEED_BOUND`：这一年的风险因素标题超过了 D01 Spec 冻结的 64 条上限。这和 D02 当初遇到的是同一类问题，与 DEI 无关，要按修订机制处理，不绕过。
- 视图只覆盖 #47 的调用路径。普通路线（#28）的冻结读取器不变，遇到更早版本的申报照样拒绝；不从本任务改上游。
- 完备性检查是静态的：它按字节码里的名字和属性链判断。如果某个读取器是经由运行时拼出来的名字（例如 `getattr` 拼名）调用的，这个检查看不见；Run 级探针是这方面的实测补充。
