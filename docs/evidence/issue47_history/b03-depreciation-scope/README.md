# B03 的折旧摊销：什么时候按名扣留

## 已知错误（不变）

Salesforce FY2026 的 B03 把一句"固定资产折旧与摊销共 12 亿美元"（`DepreciationDepletionAndAmortization`，精度 -8）当成了全部折旧摊销，而现金流量表合计是 36.31 亿（`DepreciationAndAmortization`，脚注写明还含收购无形资产摊销与使用权资产的摊销和**减值**）。已批链条按顺序取第一个出现的直接概念、从不与后面的比较。该坐标作为已登记缺陷 `B03_SALESFORCE_2026_CHAIN_TAKES_FIXED_ASSET_DEPRECIATION_AS_TOTAL` 继续撤回——这是既有要求，不需要新批准。事实与普查见 `finding.json`、`da_census.py`。

## 上一版推荐为什么不够

`finding.json` 的选项 C 是"两个直接候选数值不等就扣留"。审阅指出：两个数不等本身不是范围判断——期间不同、一个是分部数、单位不同、或者只是报告精度不同，都会"不等"而并不矛盾。规则要回答的是：**所选数能否证明覆盖已批定义所要的范围，以及候选之间的冲突能否消解**。

## 规则（`scripts/vnext/historical_da_scope_candidate.py`；2026-09-26 起由历史 B03 路线读取，见下文"接入历史路线"）

按顺序：

1. **只比可能是同一个量的事实**：三个直接概念，目标年度的完整期间，无维度（不是分部数），美元单位。别的期间、分部成员、别的币种的事实，不论数值多少，都不算冲突。
2. **只在超出各自报告精度时才算冲突**：每个事实自己声明 `decimals`；"12 亿，精度 -8"和"12.34 亿，精度 -6"在申报能告诉我们的范围内是同一个数。
3. **全部一致**：取链条第一个——已批的选择，原样不变；申报里没有任何东西与它矛盾。
4. **有冲突时问申报自己的构成**：已批定义本身有一条构成路线（`Depreciation` + `AmortizationOfIntangibleAssets`）。若两者都为该期间标注，与它们之和相等的那个直接候选就是被证明覆盖了定义所说的折旧摊销——取它，即使它在链条里排第二。
5. **否则按名扣留**：`B03_DEPRECIATION_AMORTIZATION_SCOPE_UNPROVEN`，带上每个候选的概念、数值与精度。

**它从不加回任何东西，也从不因为一个数更大就取它**："更大"不是覆盖的证明——Salesforce 的合计恰恰含了定义不加回的减值。

## 在九份 B03 申报上的实测（`rule_candidate.py` → `rule-candidate.json`）

**只移动一个位置：Salesforce，由取 12 亿变为按名扣留。** 其余八个答案与已批链条完全相同：Enphase、Ford、Macy's、Pfizer 各只有一个直接候选；Southwest 只有 `DepreciationAndAmortization`；Lumen 两个概念同为 27.49 亿，一致；Marriott 两年没有直接候选，走已批构成。第 4 步（构成消解冲突）在这九份里**没有一次被用到**——Salesforce 没有无维度标注 `Depreciation` 或 `AmortizationOfIntangibleAssets`，所以冲突无法消解。

## 读法与注错

事实读取是冻结的 `_XbrlFactParser` 的子类，只在冻结代码已打开的事实上多记一个 `decimals`；用例在九份申报上要求它产出与冻结解析器**逐项相同**的事实（去掉 `decimals` 后）。

八个注错全部被抓（`fault-injections.json`）：忽略精度、无论冲突都取链条第一、冲突时取较大者、分部事实当候选、别的期间当候选、任何币种当候选、去掉构成消解、解析器漏掉冻结代码会打开的事实。**如实记录其中两个只被构造用例抓到**：任何币种当候选、去掉构成消解——本仓库九份申报里没有非美元的该类事实，也没有可由构成消解的冲突。其余六个同时被真实申报的用例抓到（分部数这一条尤其如此：若分部事实算候选，真实申报里就会冒出冲突）。

## 接入历史路线（2026-09-26）

外部审阅把 B03 归为"已知错误继续撤回是既有要求、不是新决定"，并要求提出"无法证明所选折旧摊销覆盖批准定义、且候选之间的范围或数值冲突不能消解时按名扣留"的规则。这条规则不改变已批含义：既有规则本来就禁止把小计当完整总额、要求无法证明时准确限制该指标，而候选全部一致时它保留已批链条的选择原样。所以它现在由历史 B03 路线读取（`historical_zero_ai_results.depreciation_scope`），模块成为本世代第 36 个规则文件；**普通路线（#28）仍取链条第一个概念，不从本任务改上游**。

接线要多回答一个问题：路线从 Company Facts 取值，规则读目标申报自己的 inline 事实，**两边必须说的是同一件事**。所以除了规则的三种答案，还有三种按名扣留：链条取了一个直接总额而申报在该期间没有标注任何直接总额；链条走了已批构成而申报标注了直接总额；链条取的数与申报的数超出申报自报精度。能由申报自身构成消解的冲突，改为让冻结选择器在去掉被否定的直接候选后的事实池里重新选——仍由冻结代码做选择。

**实测**（十个位置，与 12 期间批次逐位比较）：只有 Salesforce FY2026 由发布 0.2295 变为按名扣留 `B03_DEPRECIATION_AMORTIZATION_SCOPE_UNPROVEN`（仍带着它的 B01）；Enphase、Ford、Lumen、Macy's、Pfizer、Southwest 与 Marriott 2024/2025 的值逐位不变；Marriott 2023 仍是原来的 `ALL_BRANCHES_REJECTED`。用例 `tests/vnext/test_historical_da_scope_route.py`（6 例，44 秒）：Salesforce 扣留且带 B01；Enphase 与 Marriott 2025 的结果与关掉检查时完全相同；另四个形状是替换"申报的 inline 事实说什么"构造出来的，并如实标明。七个注错（`route_fault_injections.py` → `route-fault-injections.json`）全部被抓，**其中五个只被构造用例抓到**：构成消解（两个）、链条取了申报没标的总额、标了总额却走构成、数值超出精度——已存的十份申报里没有这些形状。

**定向原生 Run**（闭包 `sha256:3e0183f3…`，`targeted-runs.json`，由同目录 `compare_runs.py` 从两边各自的 Run 记录读出，含 B03 Run 里带着的 B01）：Salesforce FY2026、Enphase 2025、Marriott 2025 各走完装入→原生 Run→冻结→公共行→另一进程冷读，零调用。Salesforce 的 B03 由发布 0.2295 变为按名扣留，它带的 B01 结果编号与 12 期间批次**逐字节相同**；Enphase 与 Marriott 的 B03（0.16169…、0.17563…）与 B01 的结果编号都与批次相同。已登记缺陷 `B03_SALESFORCE_2026_CHAIN_TAKES_FIXED_ASSET_DEPRECIATION_AS_TOTAL` 按这一扣留结果与闭包释放；12 期间批次里已发布的旧值仍被撤回，这个坐标仍没有正确的值（合计含使用权资产的摊销与减值，定义不加回减值，而当年减值没有单独标注）。覆盖表按这个闭包读这三个 Run：Salesforce 的 B03 是扣留、缺陷不再撤回它；Enphase 与 Marriott 的 B03 仍被原有的内容接受覆盖——接受绑定的是值与业务身份，这两者都没变，所以不需要重读。这不是全量帧。

## 不主张

这条规则的构成消解分支没有真实正例；其余公司往年的申报没有读过（原件未保存）；这不是 B03 数值的内容验收。零调用。
