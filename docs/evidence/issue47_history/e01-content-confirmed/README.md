## 口径

2026-09-27 所有者决定（`../owner-decisions-2026-09-27/decisions.json`）：E01 采用"经内容确认的并购公告"；已有数值和接受记录不自动继承；新增真实模型调用仍需单独许可。

## 路线怎么答

后继路线 `catalog/r6/E01_content_confirmed_ma_v1.json` 用哈希点名它替换的已批路线（`catalog/event_routes.json` 的 E01，`ce19effe…`），保留已批定义的候选条目 1.01 / 2.01 / 8.01，去掉关键词规则，写明计数口径（本注册人或子公司参与的合并、收购、处置或业务合并，宣布、达成或完成）与不计口径（借款/票据/信贷等融资协议、对本公司证券的要约收购与回购、薪酬雇佣、募集资金用途、与股东的合作或和解协议、本公司不是当事方的交易）。冻结目录不改，普通路线与已冻结的 Run 仍用已批路线。

`scripts/vnext/historical_event_items.py`（规则文件）把窗口里每一个候选条目从主文件自己的文字里读出来——从该条目标题到下一个条目标题或签名，绑定字节区间与 SHA-256——但**不确认任何一条**。确认由 `scripts/vnext/historical_ma_confirmation.py`（第 42 个规则文件）定义契约、由登记的回答提供：

- 窗口里没有候选条目 → 由路线自己的匹配器答 0；
- 窗口里有候选条目、没有登记的确认 → 按名扣留 `HISTORICAL_E01_CONTENT_CONFIRMATION_NOT_REGISTERED`（类别 `CONTENT_CONFIRMATION_NOT_EXECUTED`），扣留结果逐条列出等待确认的条目区间；
- 有登记的确认、每一条都能从自己的文字判定 → 计数 = 被确认为报告了交易的条目数（匹配器只看见被确认的候选，被否定的候选对它不存在）；
- 有登记的确认、但有条目按其文字无法判定 → 整个窗口按名扣留 `HISTORICAL_E01_ITEM_TEXT_DOES_NOT_SETTLE_IT`，列出那些条目。只数能判定的会把下界报成计数；
- 条目文字定位失败 → 按名扣留 `HISTORICAL_EVENT_ITEM_TEXT_NOT_LOCATED`，从不静默少计。

后继路线有自己的哈希，所以 Spec 与 spec 闭包都是新的；绑在 Spec 上的旧接受记录不会落到新结果上——不是删掉旧记录，而是它们说的是另一个定义的值。

## 确认契约（`historical_ma_confirmation.py`）

- **一个窗口一个请求**：窗口里每个候选条目的文字原样放进请求，逐条用 SHA-256 绑定；请求带上后继路线的计数/不计口径和固定的系统提示。请求编号是内容哈希，文字、口径、提示或条目集合任何一处变化都是另一个请求。
- **回答只按形式检查，从不按意思检查**：恰好回答请求里的每个条目一次；决定只能是三种之一（`REPORTS_A_TRANSACTION` / `DOES_NOT_REPORT_A_TRANSACTION` / `CANNOT_TELL_FROM_THE_ITEM_TEXT`）；引文 20–600 字符、必须是该条目自己文字的精确子串。意思是模型被问的东西，程序能要求的是：回答说的是这些条目、用的是这些条目自己的话。
- **`CANNOT_TELL_FROM_THE_ITEM_TEXT` 是回答不是失败**：多数候选条目引用附件，而附件一份都没保存；只指向附件的条目按自身文字无法确认，这时窗口按名扣留，而不是猜。
- **登记**：检查过的回答写入创建者日志（`.git/issue47-historical-assessments/<模式>/E01/<来源编号>/`，与 D04 同一个根），Run 安装时把登记副本装进数据根（`config/issue47_historical_ma_confirmation.json`），从数据根重建时读装入的副本、其模式就是该 Run 的模式。LIVE 副本必须在创建者日志里；RECORDED_TEST_ONLY 副本没有信用，只在调用方或装入副本点名该模式时才被消费——默认是 LIVE，所以测试登记永远进不了批次。每个消费者都在当前代码下从登记的原始回答重新推导一遍，结果必须与登记完全相同；改过数又重新封存的登记按名拒绝。无法判定而扣留的窗口同样装入它的登记，否则数据根重建会读成"未登记"。
- **本模块什么也不调用**。它构造问题、检查回答形式、说明检查过的回答算多少。

1. **只有表格标题的条目共享其后的正文**。Ford 把一次信贷协议修订写成"Item 1.01 标题 + Item 2.03 标题 + 正文"，1.01 自己只有 56 个字符的表格标题，正文全在 2.03 下。`historical_event_items` 现在对"标题后只有该条目 Form 8-K 表格名称、紧接着是另一个条目标题"的候选，沿用其后正文，并记录 `shares_the_body_of`。表格名称是一张封闭的表（Form 8-K 自己的，不是任何申报人的）。重跑候选普查：44 个候选里**只有 Ford 这两条变了**（56 → 6,536 和 56 → 2,885 字符，现在都引用附件），其余 42 条逐字节不变。

3. **Run 冻结不了**：修了第 2 处、让 `spec_paths` 指向 JSON 路线之后，Run 建出来了，冻结时 Run 存储以 "MetricSpec must begin with ---" 拒绝——它只从 Markdown 规格文件编译 Spec。没有在被各世代按字节绑定的 Run 存储里加特例，而是像普通集合的事件 Spec 一样把规格物化成文档：`catalog/r6/E01_content_confirmed_ma_v1.md`（第 43 个规则文件）由普通集合自己的文档写出器从路线生成，Run 输入要求它逐字节等于路线生成的文档、且编译回路线的 Spec；改一个字即按名拒绝（`HISTORICAL_SUCCESSOR_SPEC_DOCUMENT_IS_NOT_THE_ROUTE_S`）。

- **Ford 2025**（7 个候选，其中一条 8.01 `0000037996-25-000002#8.01@2268` 答"按自身文字无法判定"）：整个窗口按名扣留 `HISTORICAL_E01_ITEM_TEXT_DOES_NOT_SETTLE_IT`，Run `FROZEN`（result `sha256:3fa51513…`），公共行 0 条证据；登记随 Run 安装，删掉创建者日志里的那一份之后冷读仍得到同一个扣留结果。

两次都在带注册补丁的运行树里跑（闭包 `sha256:3a42764a…`，运行树的铸造值，与仓库树只差注册补丁条目），三条通过条件全部成立，零 provider / paid / SEC 调用。这两个结果证明的是"检查过的回答 → 计数 → Run → 公共行"这条路径，**不是这两份申报说了什么**。

行上另有一句历史渲染器给每个钉定期间行都加的注释——"当前值来自选中的申报、上期值来自上期选中的申报"。它对事件计数不成立（值来自窗口内的 8-K，也没有上期值），是所有历史行共用的既有缺陷，不是 E01 引入的，单独修。

**这不是交付**：有候选的窗口扣留是正确的拒绝，不是正确值已经交付。没有任何真实确认被登记，也没有发出任何模型请求。

## 用例与故障注入

`tests/vnext/test_historical_ma_confirmation.py`（16 条，合成候选）：请求逐条绑定文字哈希、文字变了就是另一个请求、文字与哈希不符按名拒绝、无候选不成请求；回答的形式（引文不在该条目里、引文来自另一个条目、长度越界、未知决定、漏答/重答/答了没问的条目、多余键与非严格 JSON）；计数（只数被确认的；有无法判定的条目整个窗口扣留）；登记在当前代码下重新推导，改数重封的登记按名拒绝。

`tests/vnext/test_historical_event_items.py` 新增的 `ARegisteredConfirmationIsCountedAndCheckedAgain`（真实申报、合成回答，所以证明的是"检查过的回答 → 计数"这条路径，从不证明某份申报说了什么）：计数就是被确认的条目；全部被否定的窗口是 0；有无法判定的条目整个窗口按名扣留；批次默认 LIVE、从不消费记录模式的回答；回答另一个问题的登记不是这个窗口的；只有表格标题的 1.01 带着它共享的正文。两个窗口都要求组件带着登记记录，供数据根重建同一个答案。

`fault_injections.py` 逐条破坏规则、要求对照先干净跑完两个套件，结果在 `fault-injections.json`。
