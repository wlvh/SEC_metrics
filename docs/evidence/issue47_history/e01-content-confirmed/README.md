# E01 按"经内容确认的并购公告"口径：候选读取、按名扣留与调用需求

## 口径

2026-09-27 所有者决定（`../owner-decisions-2026-09-27/decisions.json`）：E01 采用"经内容确认的并购公告"；已有数值和接受记录不自动继承；新增真实模型调用仍需单独许可。

## 路线怎么答

后继路线 `catalog/r6/E01_content_confirmed_ma_v1.json` 用哈希点名它替换的已批路线（`catalog/event_routes.json` 的 E01，`ce19effe…`），保留已批定义的候选条目 1.01 / 2.01 / 8.01，去掉关键词规则，写明计数口径（本注册人或子公司参与的合并、收购、处置或业务合并，宣布、达成或完成）与不计口径（借款/票据/信贷等融资协议、对本公司证券的要约收购与回购、薪酬雇佣、募集资金用途、与股东的合作或和解协议、本公司不是当事方的交易）。冻结目录不改，普通路线与已冻结的 Run 仍用已批路线。

`scripts/vnext/historical_event_items.py`（规则文件）把窗口里每一个候选条目从主文件自己的文字里读出来——从该条目标题到下一个条目标题或签名，绑定字节区间与 SHA-256——但**不确认任何一条**：

- 窗口里没有候选条目 → 由路线自己的匹配器答 0；
- 窗口里有候选条目 → 按名扣留 `HISTORICAL_E01_CONTENT_CONFIRMATION_NOT_REGISTERED`（类别 `CONTENT_CONFIRMATION_NOT_EXECUTED`），扣留结果逐条列出等待确认的条目区间；
- 条目文字定位失败 → 按名扣留 `HISTORICAL_EVENT_ITEM_TEXT_NOT_LOCATED`，从不静默少计。

后继路线有自己的哈希，所以 Spec 与 spec 闭包都是新的；绑在 Spec 上的旧接受记录不会落到新结果上——不是删掉旧记录，而是它们说的是另一个定义的值。

## 为什么不能用规则确认

同一批已保存申报上量过：40 份 8.01 里关键词规则对 2、错 5、漏 3（`../e01-item-text/census.json`）；七个窗口 13 个 1.01 里 11 个是借款协议（`../e01-keyword-branch/decision.json`）。按条目代码或关键词计数都代替不了读内容。

## 用例与故障注入

`tests/vnext/test_historical_event_items.py`：条目文字定位（沿用）、有候选即按名扣留、每个候选都从自己的文字读出、旧定义的值不被带过来（候选窗口不发布，唯一的零窗口换了 Spec）、Spec 来自后继路线、改写 brief 不改变任何候选、零候选窗口由匹配器答 0 并绑定读取记录、针对另一条已批路线写的后继被拒、无候选的事件指标不受影响。`fault_injections.py` 逐条破坏这些规则并要求对照先干净跑完整个套件，结果在 `fault-injections.json`。
