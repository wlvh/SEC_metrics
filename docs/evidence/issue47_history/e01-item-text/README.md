# E01 的 8.01：从项目自身的正文确认，而不是从程序写的说明句

## 实现错误（已修，只在历史路线）

冻结的匹配器把 E01 的关键词拿去和每条 claim 的 `brief` 比。凡是 hdr.sgml 带条目代码的申报——本仓库保存的每一份 8-K 都带——`brief` 就是程序自己写的句子 `8-K item 8.01 parsed from hdr.sgml`，任何关键词都不可能出现在里面。所以 8.01 分支一份都没读过、一份都没放行过。这是明确的实现错误，不是口径问题。路由器被 `issue_28` 各世代按字节冻结、普通路线原样在用，所以修复只在历史路线的后继规则文件里：`scripts/vnext/historical_event_items.py`（第 34 个规则文件），由 `historical_zero_ai_results.py` 在 E01 分支调用。**普通路线（#28）的 E01 仍带这个缺陷**，不从本任务改上游。

## 读的是什么（来源范围）

8.01 的正文 = 主文件里从该条目标题到**下一个条目标题或签名**为止的文字，在冻结的 `_visible_text` 视图里定位，所以任何人从同样字节能重建同一个区间。标题的判定：`Item x.yy` 后跟大写词、且前面不是指向条目的功能词（"into this Item 2.03"、"under Item 1.01"）或开引号——Macy's 的封面把空复选框渲染成字母 "o"，所以"前面任何小写词都算引用"会丢掉 Macy's 的全部条目，列表必须封闭。同一条目的连续标题（"Item 5.02" 后接 "Item 5.02(b)"）算一个条目；被别的条目隔开的两次标题、以及 "Items 7.01 and 8.01" 这种合并标题，**按名拒绝**而不是猜：读不到的条目既不计入、也不悄悄不计入。

**不读的**：条目按引用并入的附件（EX-99 新闻稿等）。它们是单独文档、本仓库一份没存，而且它们算不算"8.01 正文"本身是待决范围问题的一部分；每个条目记录自己的正文是否提到并入附件。

独立核对：`tools/read_e01_eight_o_ones.py` 不导入路线任何模块、按自己的方式找条目。本仓库保存的 **40 份**带 8.01 的 8-K，路线的读法全部唯一定位；其中阅读工具能找到的 36 份，两边的正文（规范化后）**逐份相同**；另外 4 份是 Paramount 前身把标题写成 "Item 8.01 Other Information"，阅读工具的标题模式不认识。

## 读者看不见的文字不进条目正文（2026-09-29，真实调用之前）

合并 base `8fc4f5d4` 时读到 #28 在自己的 8.01 来源组件上查出、并经独立审阅两轮才修住的一类问题：`display:none`、`<style>`、`ix:hidden` 里的文字，以及用 `opacity:0.0`、`color:transparent` 之类样式弄成不可见的文字，会被当作“可见正文”；一处加粗的“Item 9.01”交叉引用会把条目提前截断，截掉的段落不留痕迹。#47 的历史路线用的冻结 `_visible_text` 更宽——它**不排除任何隐藏内容**，每个文本节点都收——而 E01 内容确认会把条目正文原样交给模型。所以这不是“#28 的问题”，是 #47 在第一次真实 E01 调用之前必须关上的口子。

**先量**（`hidden_text_census.py`，改代码之前跑，结果 `hidden-text-census.json`）：按冻结视图同样的切分逐节点重建文本，每个节点记下哪个外层元素把它藏起来；51 份已保存 8-K 的重建与冻结视图**逐字相同**（重建不等就不信它给的位置）。56 个候选条目（1.01/2.01/8.01）：

| 问题 | 结果 |
|---|---|
| 隐藏文字落进条目区间 | 0（51 份文档每份都有隐藏文字——内联 XBRL 表头——都在第一个条目之前） |
| 明确不可见的样式落进区间 | 0（初判的 6 个全是 `text-indent:-72pt`、`-18pt` 悬挂缩进，是排版不是隐藏） |
| 结束用的条目标题在条目之后出现不止一次 | 0（49 个以下一个标题结束） |
| 以签名结束且签名字样不止一处 | 0（7 个以签名结束） |
| 若照搬 #28 的宽判据（任何内联 `color`/`position`/`background` 都算不确定） | **56 个里拒 36 个**，几乎全是 `color:#000000` |

**所以改成三道窄检查**（`historical_event_items.item_text`，规则文件）：(1) 条目区间里任何一个节点被隐藏元素（`<head>`/`<title>`/`<script>`/`<style>`/`<template>`/`<noscript>`/`<svg>`/`ix:hidden`、`hidden` 或 `aria-hidden` 属性、`display:none`/`visibility:hidden`）包着，或被按取值就不可见的样式（透明度低于 0.1 或读不出、字号 0、透明色、偏移或缩进 999 以上）包着，按名拒绝 `EVENT_ITEM_TEXT_A_READER_CANNOT_SEE`；(2) 结束条目的那个编号在条目之后只能出现一次，否则 `EVENT_ITEM_END_HEADING_NOT_UNIQUE`——按“出现次数”而不是按“连续同号并成一组”数，后者会把交叉引用和真标题并成一组而漏掉；(3) 以签名结束时签名字样只能有一处，否则 `EVENT_ITEM_END_SIGNATURES_NOT_UNIQUE`。重建与冻结视图不等则 `EVENT_ITEM_TEXT_VIEW_NOT_REBUILT`。四种拒绝都记为开发缺口（程序没法确定读者看到的正文或条目在哪里结束），不是披露结论。**冻结视图不改**：选择“拒绝”而不是“剔除隐藏文字后照读”，因为剔除会换掉任何人都能从同样字节重建的那个视图。

**没有移动任何东西**：56 个候选条目的正文哈希与结束方式与改前的普查逐个相同（用例 `test_every_saved_candidate_reads_the_text_it_read_before` 直接对照普查文件），E01 的 7 个请求重算后 `request-measurement.json` 逐字节不变。9 个注错全部由点名的用例抓到（`visibility_injections.py` → `visibility-injections.json`）；其中“任何内联颜色、定位都算不确定”同时被整份语料的对照用例抓到。**不保证的**：白色文字（有背景色时可见，本语料的条目区间里没有）、外部样式表（本语料 0 份）、浏览器渲染的其余情形——都不认为“看得见”，但也没有检测；遇到时的正确处理是扩展检查，不是放行。

## 含义未定时路线答什么（过渡规则）

关键词出现在 8.01 正文里是否就算"确认"，是待决的含义问题：已批的子串规则说算，指标名字（并购公告）说融资语境里的不算。已批条款要求**关键词确认**，所以正文里没有任何关键词的 8.01，在该条款的任何读法下都不算确认。过渡规则只回答不依赖这个决定的部分：

- 窗口内每个 8.01 的正文都没有关键词 → 答案 = 直接计入的 1.01/2.01 条数；观察记录绑定每个被读的 8.01（区间、正文哈希、读到的结果）。
- 有任何一个 8.01 的正文带关键词 → **按名扣留** `HISTORICAL_EVENT_KEYWORD_CONFIRMATION_MEANING_PENDING`，每处命中连同所在句子记录下来；两种读法都不默认采用。"必须出现具名对手方"不作为含义采用。

它答的是**现行已批定义**下的值。把 E01 改成"经内容确认的并购公告"会同时去掉关键词要求、并对 1.01 也要求内容确认——那是新定义，有自己的结果，见下文与 `../e01-keyword-branch/`。

## #28 读取器的两类反例，在本方读取器上核对与修复（2026-10-02）

#28 对它自己的 8.01 读取组件（`e01_item_source.py`，提交 `bc37a277`）做的限定独审给出两类反例（`7fc74694`，离线合成 HTML）。两套实现不同：本方从冻结的可见文本视图读条目，不看 HTML 结构。所以没有照搬结论，逐条拿反例试本方 `historical_event_items.item_text`：

1. **移到视窗外的文字。** `_hidden_by_style` 只拒绝 `text-indent/left/top/margin-left/margin-top` 不超过 −999 的偏移；`position:absolute;right:-1200px`、`position:fixed;bottom:-1200px` 和正的大偏移都被当成可见。本方同样成立。现在这七个属性的偏移绝对值达到 999 即拒（`EVENT_ITEM_TEXT_A_READER_CANNOT_SEE`）。没有文字的定位元素（已存申报里的 `position:absolute;bottom:0`）和几个点的缩进不受影响。
2. **只在链接里的条目标题。** 冻结视图不知道链接；一份 8-K 若只有目录里那个带链接的"Item 8.01"，本方会把目录当成条目起点、把目录文字当正文。本方同样成立（#28 的另一半——跳过带链接的 9.01 结束标题——本方不成立：任何下一个条目标题都结束本条目）。现在重建视图时同时记下每个文字节点是否在 `<a href>` 里，条目自己的标题在链接里就按名拒绝（`EVENT_ITEM_HEADING_IS_A_LINK`）；`<a name>` 锚点不算链接。目录与正文标题都在时，本方原本就以"标题出现两次"拒绝，不变。

两条都是拒绝，不是猜测：读不出的条目按实现缺口扣留，不是披露结论。

**量测**：`all_saved_items.py` 走遍恢复根请求账本里的每个 8-K 头文件（检出与获取导出），读每个候选条目（1.01、2.01、8.01）。修改前后各跑一次：306 个条目，305 个能读、1 个原本就因结束标题不唯一被拒，**修改前后逐个相同，没有条目移动**。E01 确认请求计量（`../e01-content-confirmed/request-measurement.json`）重算后逐字节不变。所以这次修复今天不移动任何结果或请求；它挡的是将来遇到这两种写法的申报。
