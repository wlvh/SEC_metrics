# 申报行在历史块里的钉定期间：来源集发现

## 问题（量出来的）

SEC 把一家注册人的申报列表分成主文档的 `recent` 块和若干历史块，并会重新分块。钉定路线在读申报里的任何数之前，先用冻结的 `_exact_filing_source_set` 在一份目录里找到目标申报的行，再以这份目录建来源集。此前四条路线交给它的**都是主文档**。本仓库已存目录实测：50 个目标期间里 6 个（JPMorgan FY2021–FY2024、Salesforce FY2022–FY2023）的 10-K 行只在历史块里（`../financial-route/target-row-blocks.json`）。这些期间的原件与目录全部取得之后，这些路线仍会在这一步停下——**是实现缺口，不是披露缺失，也不是获取能解决的**。

## 没有真实正例，所以用真实材料构造一个

那 6 个期间都没有已存原件，所以无法在真实期间上看路线怎么处理这种行。`tests/vnext/historical_block_fixture.py` 用 Marriott 的已存材料造了一个：主文档里 2024-06-30 及之前申报的行整体移进一个新的历史块（`CIK0001048286-submissions-003.json`，声明区间就是它自己正文的首末申报日，与 SEC 的写法相同），经录制会话记录下来——与任何捕获相同的申领、落盘、收据、终态与冻结检查点重放。**每一份申报的字节都是本仓库已存的字节，变的只有"这一行列在哪份目录里"。**唯一的接缝是规划器对"主文档要不要取"的回答：已存主文档一致，规划器正确地说不需要；这里对这一个网址答"需要"，因为要构造的场景就是 SEC 重新分了块。新块不需要接缝：派生主文档落盘后，规划器自己声明它、它未保存，于是按普通方式被准入。`RECORDED_TEST_ONLY`，零调用。

一个根同时给出三种情形，全在真实申报上：

| 期间 | 情形 | 期间选择 |
|---|---|---|
| FY2025 | 本期与上一期的行都还在 `recent` | 只读主文档，与正常根相同 |
| FY2024 | 上一期（FY2023）10-K 的行移进了块 | 读主文档＋新块 |
| FY2023 | 本期 10-K 自己的行移进了块 | 读主文档＋新块 |

三期在两个根上选中的本期与上一期申报完全相同。

## 修前（`measured-before.json`）

与修后用同一个脚本、同一种比较产出：在临时把四处调用点改回主文档的代码上跑，跑完原样还原。

FY2023：**16 个指标**与正常根不同，全部是同一个错误 `Filing accession is absent from submissions: 0001628280-24-004372`——accession 三个（A01/A02/B12）、公司事实十一个、零 AI 报表两个（B01/B03）。连对 Marriott 本应是"结构性不适用"的 A01/A02 也丢了，因为 accession 路线先建来源集、后问适用性。其余 23 个在两个根上逐字段相同：文本（C02/D01/D02）已经经 `historical_metadata_context` 读块，事件与 C04 的冻结路线按窗口读所有重叠的块，B06、住宿、B13 不经这一步。

FY2024：**零差异**。冻结的上一期遍历（`normal_companyfacts_results._prior_filing`）本来就跨块找上一期、并返回列出它的那份目录。

## 修法

`scripts/vnext/historical_filing_inventory.py`（第 33 个规则文件）对**本期**申报回答冻结代码已经为上一期回答的同一个问题：主文档的 `recent` 块列出它，就返回主文档——**就是路线读进来的那个对象**，所以行在 `recent` 的期间一个字节都不变；否则在钉定选择加载过的块里找，恰好一个块列出它才返回。每个块经路线自己的读取器读，所以和主文档一样是 Run 的请求证明来源；并按上一期遍历的同样三条检查：索引声明了它、同一注册人、正文在声明区间内。

接在四处：公司事实的本期来源集（上一期遍历保持读主文档，因为它要从主文档里的历史索引出发）、accession 实例、零 AI 报表（事件分支保持主文档，理由相同）、金融路线（它不经读取器而按网址读证明，所以同一查找对它自己的证明提问；没有期间选择时——回归用例交进来的普通准备——只问主文档，与普通路线相同）。

## 修后（`measured-after.json`）

三期、39 个指标在两个根上**答案逐字段相同**：结果比适用性、质量、发布状态、原因码、值、期间与单位；文本类比候选状态与按序的每条摘录。FY2023 那 16 个恢复成与正常根一样的答案——6 个带值（B01 23,713,000,000、B04 3,083,000,000、B05 2,718,000,000、B07、B08、B09），10 个是与正常根相同的结构性不适用或无值。两个根上仍一致拒绝的是 C02 的 FY2023/FY2024（那两年的代理未保存）、D03（未接线）与 D04（无登记评估），这些拒绝本来就与目录无关。

**唯一的身份差异是 FY2023 的 D02**：它的候选记录了找到这份申报的那一行（`metadata_origin`：哪份目录、第几行），行移进新块后记为 `CIK0001048286-submissions-003.json` 第 62 行，而不是主文档第 329 行；其余字段与八条摘录逐条相同。变的是溯源，不是答案，而且应该变——一个把申报绑定在它实际被找到的地方的候选，行换了地方就该换身份。**它修前就在**（用同一把尺子重产的 `measured-before.json` 里 FY2023 同样只有 D02 身份不同）：出处来自文本路线自己的元数据视图，那一层本来就读块，与本次修改无关。结果类指标同理：修后来源集指向新块，所以结果编号会不同，比较的是答案而不是身份。

**测量本身先错了一次**：第一版把文本 Run 输入的 `primary_result` 拿来比，而文本类的这个字段按设计是空的（结果在建 Run 时才从候选导出），于是 D01/D02 在两个根上"相同"——是两个相同的 `AttributeError`。两个相同的失败也算相等，这正是比较要防的东西；改为比较 Run 工厂先导出的候选之后，才看到上面那个身份差异。

## 注错（`fault_injections.py` → `fault-injections.json`）

八个全部被抓：四条路线各自改回用主文档（各由对应的路线用例抓到）；查找改为搜索所有声明的块而非选择加载的块、跳过区间检查、接受两个块都列出同一行、对 `recent` 里的行返回相等的副本而非同一对象——后者由两条 `assertIs` 用例抓到，它守的是"行在 `recent` 的期间连对象身份都不变"。

## 用例（`tests/vnext/test_historical_filing_inventory.py`，15 例）

- 构造根的前提本身：行确实不在派生主文档的 `recent` 里、确实在块里，零调用。
- 行在 `recent`：返回的**就是**主文档对象（`assertIs`）；正常根上同一份 FY2023 申报同样返回主文档。
- 行在已加载的块：返回那个块，角色是历史块。
- 选择没加载的块不被搜索：`HISTORICAL_FILING_ROW_IN_NO_LOADED_BLOCK`。
- 拒绝分支（内存文档）：块正文超出声明区间（已存 JPMorgan 块就是这样）、索引没声明的块、另一注册人的块、两个块都列出同一行、选择不以主文档开头。
- 路线层：FY2023 在两个根上公司事实十一个、accession 三个、B01 逐字段相同，且修后的来源集点名的是新块；公司事实里 B04 要求是 EXACT，免得两个相同的拒绝也算相等。
- 金融路线：借银行特征让 Marriott FY2023 走开门的一侧（构造输入，只断言用哪份目录证明申报）——钉定期间读块；不带期间选择时只问主文档，在构造根上按名拒绝，说明放行它的是选择加载的块。

## 不主张

任何 JPMorgan 或 Salesforce 往年的值——那 6 个期间仍缺原件（获取计划 A 类）。这里证明的是：原件到位之后，"行列在哪份目录里"不再挡住这四条路线；以及行在 `recent` 的期间不受影响。
