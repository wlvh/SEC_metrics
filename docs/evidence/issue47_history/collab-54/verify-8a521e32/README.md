## 怎么核的

- **程序树**：本方 `51250475`，加 `8a521e32` 的 21 个公司文件（逐个与其 blob 相同；覆盖提交只在核对目录里，不进分支），打注册补丁、重新铸造（closure `fa9b580a`）。
- **准备端来源**：在这棵树里用本方 `tools/vnext_historical_sec.py restore` 恢复整份取数会话（1,547 行，导入编号 `8dd14ffb…`）。
- **#54 的命令**：`export --history-years 5` → `install-runtime --kind historical`（`issue_54_v3`，closure `723f08af…`）→ `install` → `compute --report-end`。
- **对照**：同一棵程序树、同一个来源根上，本方入口（`../../period-batch/period_runs.py`）建的 Run。
- **读回**：`../verify-2a642e56/compare.py`，在另一进程里分两种方式读回：
  - 收据哈希检查：`read_run_receipt`，只核清单里三个文件的哈希；
  - 原生冷重放：`load_frozen_run` 加 `render_historical_run`，从 Run 自己的数据根重推，再把行与证据的字节和计算写出的比对。

## 接缝怎么接的（读 `8a521e32` 的代码）

`install-runtime` 在安装出的运行树里改了冻结事件遍历的一行（`normal_zero_ai_results.py` 的运行树副本）：原来拿数据根列出的 8-K 与“程序根里的旧式原件目录”比对；现在比对的另一侧换成 `company_event_census.installed_event_filings`。它先认证已安装的公司来源：外部信任记录核对每个文件的哈希，头文件集合必须正好等于准入时登记的闭包，多一个、少一个、来自别的注册人都拒绝。认证通过后，原样调用冻结的 `_acquired_event_filings`。窗口和补充规则仍是原来的零 AI 路线。数据根不能给自己作证，因为信任记录在信任根里，不在包里。本方历史事件遍历（`historical_event_walk.py`）在运行树里执行的就是这份代码。

## 其他检查

- C02、D02 是 `CONFIRMED_INVALID`，但原因不同：
  - C02 `aaaf8e0f…` 是选择器修复之后的新选择，本方没有对它的判读，坐标级缺陷 `C02_PARAMOUNT_2024_SELECTOR_ADMITS_TEXT_OUTSIDE_BOARD_COMPOSITION` 的释放点名的是更早的两个结果编号。所以在任何闭包下它都被撤回，这个答案对。
  - D02 `5aa340a1…` 正是本方阅读接受过的结果：缺陷 `D02_PARAMOUNT_2024_KEYWORD_PROXY_ADMITS_TRANSACTION_COST_NOTE` 对它释放过，点名的是闭包 `ed360ebc`、`500ddf5f`。#54 运行树的闭包是 `723f08af`，释放没有点名它，所以读取器把同一个结果判为撤回。规则本身就是这样定的（释放同时点名结果与闭包），但在 #54 的视图里，一个已修复、已接受的结果被显示成无效。见下面“接口观察”。

## 接口观察（给 #54，不是缺陷）

1. **版本释放与闭包。** 本方缺陷登记的释放同时点名结果编号和闭包。#54 运行树有自己的闭包（`723f08af`），所以本方已修复、已接受的结果在 #54 路径上被重算出来时（例如上面的 D02 `5aa340a1…`），#54 的读取器仍显示撤回。两种处理都可以：#54 的读取器把“同一结果编号在别的闭包下被释放”单列成一种状态，不判为无效也不判为通过；或者本方在核对过 #54 某次运行之后，为它的闭包补点名释放（本方给自己的批次就是这样做的）。前者不需要本方跟着 #54 的每个闭包更新登记，本方倾向前者；由 #54 决定。
2. **结果视图里的期间是 Run 坐标。** `results` 的 `period` 是 Run 的财年坐标（FY2025 显示 2025-01-01 至 2025-12-31），而事件指标实际计数的窗口在行里（2024-01-01 至 2025-12-31）。对连续注册人两者相同；对接续注册人不同。只看视图的人可能以为计数只覆盖 2025 年。建议视图要么把字段名写明是坐标，要么同时带出行里的测量窗口。
