# SEC 批准的延伸：第二次、也是唯一一次追加

所有者 2026-09-30 在会话里选择"一次批约 420"（执行者转录在 `../owner-decisions-2026-09-30/decisions.json`，不是所有者本人在 GitHub 上的评论）：一条评论覆盖（1）三家公司历史分片与索引的刷新，（2）Southwest 在第一份批准上限处没取完的请求，（3）刷新之后规划器才能声明的 JPMorgan、Pfizer、Salesforce 往年需求。数字是停止上限，实际只取规划器声明要取的。

**批准本身仍是所有者亲手发布的那条评论**：正文就是本目录的 `approval-comment-body.json`，逐字节发到 Issue #47；执行者随后用 `python3 tools/vnext_historical_sec.py register-extension --approval-url <评论链接>` 从 GitHub 读回并登记。执行者发的任何评论都不算批准。

## 为什么不是第二本账

冻结的检查点重放覆盖基线之后的每一行。第二本账在同一个数据根上登记它取回的东西，就要把第一本账的槽位再数一遍。所以延伸让同一本账继续：同一个根、绑定、槽位、认领日志、开跑标记与导出，上限加上批准的增量，授予换成为这次批准的那一组。第一份批准的正文、记录与策略都不变。

所有者的评论写明它延续的账本状态——已提交导出里认领日志的摘要、大小与行数（1130 行），累计 `[0,0,1354]`（1130 次真实请求加恢复时按上限记的 224）。`pin_extension` 要求本账的认领日志以恰好这些字节开头才加上限：别的账本、被重置或回退的这本账，都不会被加上限。

## 已请求过的 URL 再请求一次的规则

零自动重试的意思是认领过的 URL 永不再认领。延伸只开两个口子，都由规划器点名、不由调用方点名：

- `SNAPSHOT_REFRESH`：已存副本与其索引不一致（类别限 `SUBMISSIONS_INDEX`、`SUBMISSIONS_HISTORY`）；
- `REPLACEMENT_ACQUISITION`：最近一次请求失败（类别限 `FISCAL_EVENT_FILING`，即 Southwest 那一次 HTTP 503）。

每个延伸一次：先前认领它的槽位都必须在延伸所述状态之内，所以延伸之内认领过的 URL 不会第三次请求。再请求的请求体里带延伸序号，所以摘要与第一次不同，账本"同一请求不许抽两次"的规则照旧成立。

## 上限怎么算出来的

`tools/propose_historical_extension.py` 在导出恢复出的根上跑规划器与声明，逐项算（零调用），结果在 `proposed-extension.json`：

- **今天就能声明的**：到期行按拟议授予逐行问门禁、被接受的那些。
- **刷新索引就要重取全部分片**：这是量出来的，不是假设。已提交的 JPMorgan 索引（2026-08-17）列 69 个分片、`001` 是 2025-07-15..2025-08-13；取数时（2026-09-29）的索引列 70 个、`002` 是 2025-07-22..2025-08-23——分片边界整体移动了。所以新索引意味着新分片：每家按"索引＋它列出的全部分片＋1"算，减去已声明的刷新行。**这正是我在问所有者时说错的地方**：问题里写"刷新 6 次"，JPMorgan 实际是索引加约 70 个分片。
- **目录漏掉的目标**：JPMorgan 的五个目标是 2025、2023、2022、2021、2020——FY2024 的年报行在真 007 里，已存的 007 来自另一次分区。按"最近五个财年"它漏掉 FY2024：年报链 2、代理 1、事件按其财年窗口在可信分片里的 8-K 数 ×2。
- **陈旧分片藏起来的 8-K**：分片声明数多于已存份数的（Pfizer 4 份、Salesforce 6 份）按差额×2；已存副本是另一次分区的（JPMorgan 007）按前四年同一日期段 8-K 数的最大值×2。
- **还没有治理计划的目标**：每个一份代理。
- **今天只因为同时服务一个框外目标而被拒的行**（JPMorgan FY2020 年报链作为 FY2021 的上一期）。

8-K 估计器先校准：凡是声明已点名、而且一份都没存的窗口，估计值必须等于规划器报的到期行数，否则不写出。JPMorgan FY2021/FY2022/FY2023 三个窗口 70/54/52 行，估计值逐一相等。

## 独立审阅（全新上下文的同族子代理，不是人）

结论 PASS_WITH_FINDINGS：没有找到从公开实时入口为别的账本加上限、加得比批准多、或在所有者规则之外再请求的路径。两处中等、五处低风险，逐条先复现再修，每条一个用例、一个注错：

- **M1 恢复与延伸没有绑在一起**：在容器里登记了延伸却没推送就花了额度，容器丢了，按分支恢复时读不到延伸，丢失段的保留量会漏掉只有延伸允许的行。修法：实时路径要求检出里的延伸文件与分支尖端的逐字节相同才发请求（`require_extension_on_branch`，CLI 的 `_branch_tip` 读出尖端的这两个文件）；恢复时导出若是在某个延伸下花的，许可必须带同一个延伸；恢复记录写明它是在哪个延伸下记的保留量，之后只在同一个延伸下成立。
- **M2 提案里加过一项"2022 年代理的 SEC 头文件"**（为 #77 预留），审阅指出：声明里根本没有这些行，而按类别写的授予会放行这些公司那个窗口里的任何治理文件，说的比做的多，也超出了所有者 (1)(2)(3) 的范围。已删去；#77 另行处理。
- **L1 上限只加在内存里**：`pin_extension` 收任何字典。现在实时账本只接受从 GitHub 读回过的延伸；第一次钉住时在根旁写下它（`.<根名>.extension-1.json`），之后任何进程钉住的必须是同一个；会话持有的授予与账本钉住的延伸不一致即拒绝（审阅者做过一个没被抓到的注错：会话换回第一份批准的授予，原有用例全绿——现在由专门的用例抓住）。
- **L2 替换的范围比"最近一次请求失败"宽**：规划器把任何读不出的已存副本都标成替换（包括选择冲突、哈希不符）。现在替换还要求规划器的理由以 `LATEST_SOURCE_REQUEST_FAILED` 开头。
- **L3 `_capture_one` 信任传进来的标记**：现在持锁时按账本槽位重算，对不上即拒。
- **L4 所述累计数只和评论比过**：现在钉住时按认领日志前缀逐通道计数，加上当时已记的恢复保留量，必须等于所述累计。
- **L5 提案工具的自检只记录不停止**：实时账本不在、前缀或行数或累计对不上、估计器没有校准窗口，现在都按名停下、不写出。

**复审**（同一审阅者，针对上面七条）：七条都不能从公开入口绕过；新发现一处中等——L4 的修法按"还原的认领日志长度"数恢复保留量，延伸取数途中丢失、在第一次导出前恢复时，这次恢复还原的正是所述导出、长度相等，会被算成所述状态时已花的，之后每次钉住都被拒。改为把状态绑到**恢复链的前缀**：所述状态多带一项 `resumes`（导出里 `ledger/resumes.jsonl` 的摘要与大小），钉住时本地恢复链（按导出的方式取公开视图）必须以这些字节开头，只数前缀里的保留量；前缀之后的恢复必须还原不短于所述长度的日志（否则就是所述状态漏掉了一笔更早的收费）。锚点改为先写临时文件再链接就位。残留的一条（部分检查只约束走代码路径的调用方）与第一份批准的限度相同，写明不修。这一改动让正文多了 `resumes` 一项，摘要随之改变并重新钉住。
