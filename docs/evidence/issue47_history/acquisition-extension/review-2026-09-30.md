# 独立审阅报告：SEC 批准的延伸（2026-09-30）

审阅者：全新上下文的同族子代理，不是人。只读审阅；审阅者在自己的稀疏克隆里跑用例与注错（跑完已删），零 SEC、零模型调用，没有改动检出。下面是报告原文的要点，逐条的修法与对应用例、注错见同目录 `README.md`「独立审阅」与 `extension_injections.py`。

**结论：PASS_WITH_FINDINGS**。没有找到从公开实时入口为别的账本加上限、加得比批准多、或在所有者规则之外再请求 URL 的路径。

审阅者在克隆里的运行：六个新类（20 例）全过；整个 `test_historical_sec_session` 203 例里只有 7 例与未重建的接线收据有关的失败（预期）；15 个注错全部抓到；字面量扫描器在新文件里零命中。

## 发现

- **M1（中）恢复的保留量没有绑到在用的延伸，实时路径也不要求延伸已在分支上。** 复现：同样的认领与帧，第一份批准下保留量 0，延伸后的许可下 6。情形：登记延伸、没推送就取了只有延伸授予的行、容器丢失、在分支尖端恢复时读不到延伸、保留量漏算，再登记延伸后上限变成 1354+N 而丢失段少算。建议：实时路径要求延伸文件与上游一致才钉住；恢复要求导出里的延伸与许可的一致；恢复记录写入延伸摘要。
- **M2（中，提案工具）`X_PRE_TAGGING_PROXY_HEADERS` 说的比做的多，上限计入了门禁会拒绝的请求。** 声明里没有头文件行；授予按类别，会放行这些公司窗口内任何治理文件（复现：一个代理主文件被该授予放行）。也超出了所有者转录的 (1)(2)(3)。建议删去或明确重问所有者。
- **L1（低）上限的抬高没有落盘、应用处也不核验。** 复现：一个未经核验的字典让 LIVE 账本的上限变成 `[0,0,1000001]`，根旁不留任何记录。未被抓到的注错：会话换回第一份批准的许可，账本仍钉着延伸，六个类照样全绿。建议：只接受读回过 GitHub 的延伸、根旁写锚点、会话与账本一致性检查。
- **L2（低）REPLACEMENT 比"最近一次请求失败"宽。** 规划器对任何读取错误都标替换；复现：理由为 `SOURCE_ATTEMPT_SELECTION_CONFLICT` 的行拿到序号 1。建议只认 `LATEST_SOURCE_REQUEST_FAILED`。
- **L3（低）`_capture_one` 信任传进来的标记。** 复现（真实录制链）：延伸下已请求过的 URL 以 `reclaim=1` 再请求成功，计数 `[0,0,3]`。只有私有调用方能这样做。建议持锁重算并比对。
- **L4（低）`ledger_state.cumulative` 只和评论比过、没和账本比过。** 脚本复现：所述 `[0,0,3]`、实际 `[0,0,1]`，按所述算允许多取。今天无影响（实时账本 1130 认领、保留 224，合 1354）。建议钉住时重算前缀计数加保留量。
- **L5（低，提案工具）自检不停止。** 实时账本前缀不符只记 `false` 照样写出；没检查行数；实时账本不在就跳过；某家公司没有校准窗口时估计器未经校准。建议一律停下。
- **过程提示**：审阅时正在跑的提案进程启动于工具被修改之前，其输出来自旧源码；钉住摘要之前要重跑。

## 审阅者核对过、认为成立的

钉住要求认领日志前缀与行数完全一致；上限不落盘所以跨进程再钉不叠加，同一进程第二次钉住被拒。评论的每个授权字段都与读回的正文比对；严格 JSON；已存记录与读回评论两边都查出处（编号、链接、议题、作者编号与类型、OWNER、未编辑、无应用标记），正文必须一致；第一份批准的评论与类型、别的批准、别的根、新增用途都被拒；正文摘要未钉住时拒绝登记。再请求按种类与类别、只对状态之内的序号，延伸下认领过的 URL（包括失败的替换）不会再请求；标记改变摘要所以账本的重复规则也挡住第二次。没有延伸时：上限、拒绝文本、请求摘要、导出索引字节与 `lost_segment_reserve` 的集合参数都不变。实时路径顺序：第一份批准→接线→尖端→经 GitHub 核验延伸→保留量钉住→延伸钉住。

## 复审（同一审阅者，针对上面七条修复）

**结论：PASS_WITH_FINDINGS**。七条修复都不能从公开入口绕过；审阅者在克隆里跑整个模块 209 例（只有 7 例收据相关的预期失败）、25 个注错全部抓到，上一轮那个没被抓到的注错现在在运行时被 `_check` 以 `LEDGER_AND_SESSION_DISAGREE_ON_THE_EXTENSION` 拒绝。新发现：

- **N1（中）L4 的修法会永久拒绝一个正当流程**：延伸取数途中容器丢失、在第一次导出之前恢复，这次恢复还原的正是所述的那个导出，它还原的认领日志长度等于所述长度，于是按"还原长度不超过所述长度"算，它的保留量被算进"所述状态时已花的"，之后每次钉住都被拒。复现：花满上限 2、取状态、追加一条还原长度等于状态长度、保留 4、带延伸的恢复记录——钉住被拒 `[0,0,2] stated, [0,0,6]`；长度加 1 或没有这条记录时都能钉住。建议把状态绑到恢复链的前缀（导出本来就带 `ledger/resumes.jsonl`），只数前缀里的记录。
- **N2（低）第一次钉住中断会挡住以后的每次钉住**：先 `open("xb")` 再写，崩在中间会留下空锚点。建议先写临时文件、fsync，再 `os.link` 就位，冲突时与已有的比较。
- **N3（低，残留）有些检查只约束走代码路径的调用方**：`_capture_one` 的重算信任调用方给的 `dependency`（把一条已存来源的行改标成刷新并传标记，能成功）；删掉锚点后别的延伸字典也能钉住；`provenance_verified_against_github` 可以在字典里伪造。这些都经不过 `capture`、`capture_pending` 或 CLI——它们在锁下从帧建行、只从核验过的策略建延伸——所以约束的是代码路径，不是调用方（与第一份批准相同的限度）。
- **备注（非安全）**：`_capture_one` 每次都读全部槽位的 `sec-plan.json`，约 400 次获取 × 约 1500 个槽位就是约 60 万次小文件读取；可以在一次持锁内缓存。

审阅者核对过：分支检查对两端都没有或都相同的文件放行、`git show` 读 blob 没有换行或过滤属性问题；恢复拒绝导出里有而许可里没有的延伸、恢复记录写入延伸；第一轮的恢复记录没有 `extension` 字段仍能通过；延伸之后的导出（长度更长）恢复后能钉住；替换只认 `LATEST_SOURCE_REQUEST_FAILED`（规划器与事件、治理声明的读取都带这个前缀）；真实状态算出来是 1130＋224＝1354；没有延伸时行为实质不变，唯一的接口变化是 `branch_tip` 必须返回 `extension_files`，缺了按名拒绝（CLI 会提供）。
