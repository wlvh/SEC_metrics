# 取数驱动的运行摘要（虚拟机里保存的副本）

每次 `tools/vnext_historical_sec.py acquire` 运行结束时，会在账本根的 `runs/` 目录写一份摘要：逐家公司记录跑了几轮、取了哪些文件、哪些失败、哪些不在任何授予里、哪些已被认领，以及停下的原因和累计计数。导出（`evidence/issue47_acquired/`）不带这个目录，而账本根只在执行者的云容器里，容器一回收这些摘要就没了。所以在 2026-10-03 把账本根里全部 32 份摘要原样打包提交：

- `runs.tar.gz`：32 份 JSON 原样打包（文件名即 UTC 时间，2026-09-29 18:50 至 2026-09-30 23:31）。打包是确定的：按文件名排序，时间、属主一律置零。
- `index.json`：每份摘要的 SHA-256、大小、停止原因、累计计数，以及逐家公司的轮数、取数数、失败、授予外与已认领数。

**这不是权威记录。**权威记录是导出里的账本：槽位、认领日志、检查点，用 `tools/vnext_historical_sec.py restore` 恢复，冻结检查点重放会逐行核对。摘要只是驱动自己对每次运行的叙述，而且不完整：

- 第 1–288 号槽位是 2026-09-29 容器丢失之前取的，那些运行的摘要随容器丢了（恢复经过见 `../ledger-lost-2026-09-29/`）。
- 恢复之后的 1,259 个槽位里，有 1,234 个能在摘要里找到对应记录。缺的 25 个所在的运行没有写出摘要：第 1164 号（Salesforce 的 submissions 索引，那次运行被后台任务的 2 小时上限停掉）和第 1524–1547 号（JPMorgan）。这些槽位在账本里都有完整的终态与收据。
- 有 15 个 URL 各对应两个槽位：14 个是 JPMorgan 的 submissions 索引与分片，先在第 19–32 号槽位取过，之后在扩展批准下按刷新规则于第 1284–1298 号重取；另一个是 Southwest 的一份 8-K 头文件，第 1130 号返回 HTTP 503（按设计计数、不重试），之后在扩展批准下按“最近一次请求失败”的替换规则于第 1171 号取回。

最后一份摘要（`20260930T233112Z.json`，只跑了 JPMorgan，没有再取任何文件）：停止原因为空，累计 `[0, 0, 1771]`，上限 `[0, 0, 1867]`。每家公司最后出现的那份摘要里，授予外的依赖都是 0。

同一个账本根里另有几样东西没有提交，原因如下：

- 每个槽位的 `sec-wire/` 副本：共 2,518 个文件。逐个核对过，都与导出行归档里的原件逐字节相同。
- 38 份较早的 `acquisition-attribution/`：每份对应一次较早导出时的账本状态。导出只需要最新的那份，它已经在导出里。
- 根旁边的开跑记录 `.initialized.json`：里面有一个只能留在本机的随机数。公开的标记评论只带它的公开视图和摘要，不能把它带出这台机器。容器回收之后，若要在新容器里继续花剩下的 96 次额度，需要按 `scripts/vnext/historical_sec_resume.py` 走恢复流程（所有者决定），不能复制开跑记录。
