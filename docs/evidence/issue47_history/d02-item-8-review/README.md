# D02 Item 8 审阅：两个方向都覆盖的请求合同（待调用许可）

## 为什么要有它

D02 的已批来源是 Item 3、legal proceedings 与 contingencies notes。路线把 Item 3 和 Item 3 点名并入的附注整段取入；**财务报表其余部分（Item 8）只靠一个关键词进入**。关键词分不清"披露了一件法律事项"和"顺路提到诉讼"：在 11 份有 D02 集合的申报上，它准入 24 个 Item 8 块，其中 5 个错（Lumen 1670 法律费用政策、Pfizer 2175 估计的不确定性、Pfizer 2240 应收账款催收、Paramount 2108 交易成本、Paramount 2257 债务契约），三条确定性替代规则各在一份真实申报上失败（`../d02-content-read/keyword-proxy-decision.json`）。对应的四个位置按既有要求撤回，修复责任在执行者。

外部审阅对这件事的要求是：若走模型审阅，**必须同时覆盖漏选方向**——只审关键词放进来的 24 块，证明不了没有漏掉关键词从未放进来的披露。

## 请求是什么（`scripts/vnext/historical_legal_review.py`）

- **一份申报一个请求**，由路线自己的读法构造（`historical_text_results.item_8_review_pool`）：Item 8 里 D02 可能取入的每一个块——排除已被并入附注占有的块、页面装饰与运行页眉、审计报告，只保留路线本来就会考虑的两类（实质块、超链接句）。和关键词代理的差别**只在关键词本身**：池是关键词作用之前的全集。`legal_review_request` 要求池里关键词会准入的部分逐块等于当前提案里的 Item 8 摘录，所以两种读法不会各自漂移。
- **必须明确回答的块**：关键词的全部准入，加上所有带法律程序词汇（litigation、lawsuit、claim、proceeding、court、settle、investigation、penalty、contingen…）的块。每块恰好一个决定（IN_SCOPE / OUT_OF_SCOPE / CANNOT_TELL_FROM_THE_TEXT）；IN 与 CANNOT_TELL 必须带该块原文的精确子串作引文，OUT 不带。
- **词汇只决定哪些块必须被明确回答，不限定能被计入什么**：请求里的任何其他块都可以经 `also_in_scope` 计入（同样要引文），所以一段一个法律词都没有的披露仍然到得了。这就是漏选方向的通道，它是按构造存在的，不靠词表。
- **定义随请求走**（`DEFINITION`）：计入的是注册人或其合并子公司的法律程序、诉讼、仲裁、政府调查或执法行动、索赔（原告被告均算；进行中、威胁、和解或了结均算），以及由此产生的或有损失、计提或准备金（含确认与披露政策），及其标题与续接句；不计入的是顺路提到诉讼的块（估计的不确定性、法律费用政策、应收催收、交易或融资成本、债务契约）、不涉及索赔的担保/采购承诺/租赁、别家公司的事项（除非注册人或子公司承担风险）、审计报告。这些例子都来自已读出的误取，定义本身来自已批来源。

## 登记之后改变什么

- **只改 Item 8**：Item 3 与并入附注照原样；Item 8 的关键词准入被审阅计入的块替换，按文档顺序放在原来的位置（`apply_legal_review`）。覆盖记录写明方法、登记编号、被去掉的关键词准入与关键词够不到而被计入的块；候选与 Evidence 都随之改变，旧集合不能冒充审阅后的集合。
- **没有登记的位置不变**：`prepare_business_text_sources` 在没有审阅时逐字节返回原来的准备结果，输入绑定也不多一个字段。所以今天已接受的 D02 值不会因为这段代码而移动；审阅登记之后产生的是新结果、新结果编号，要重新阅读才能接受——已有接受不自动继承。
- **过期的审阅按名拒绝**：请求编号是内容哈希，池、某块文本或提示词变了就是另一个请求；某位置有审阅但没有一条回答今天的请求时，报 `D02_REVIEW_REGISTERED_FOR_ANOTHER_REQUEST`，而不是悄悄退回关键词。
- **有块没判定就按名扣留**：任何 CANNOT_TELL 使整份申报以 `HISTORICAL_D02_ITEM_8_REVIEW_DOES_NOT_SETTLE_IT` 扣留，不发布"已判定的部分"。
- **登记与消费**与 E01、D04 同一套：创建者日志在检出的 `.git` 里、按位置键（公司、钉定期间、申报字节）存放；数据根里读安装副本；RECORDED_TEST_ONLY 只在点名时才被消费，批次默认 LIVE，所以测试登记进不了批次。

## 调用路径

- 仓库里：`historical_model_calls` 把 D02 加入可授予指标与请求类型，D02 与 E01 共用"一个位置一个请求"的来源形状（`_single_request_source`），账本摘要是请求编号与模型的内容哈希。
- 出口补丁里（只在 #47 运行树应用）：D02 自己的答案检查与 WB-3 接受记录、自己的登记分支、执行器的 `--metric D02`，以及一个在同一条调用路径上的用例类（福特：Item 8 只有一个交叉引用块，是真实申报里最小的请求）。

## 计量（`request-measurement.json`，`measure_d02_requests.py`，参考分词器，零调用）

12 个已存 D02 位置各一个请求：共 9,753 个块，其中 318 个必答；参考输入 417,576 token（单个 963–56,802，最大的是 Pfizer）。福特的 Item 8 只有一个交叉引用块、没有必答块，请求 963 token——它仍是一个请求，因为漏选方向要求连这一个块也被看过。

输出也量了，因为输出有硬上限（max_tokens 4,096），而 D02 的回答是唯一随申报变长的：每个必答块一条。用同一分词器数合成回答：全部排除时 13–1,574 token；每把一个必答块改成计入并带最长引文（300 字符或整块），另加 2–80 token。所以在上限内 Pfizer 最多能有 45 个必答块被计入，其余 11 份即使全部必答块都计入也放得下；已读出的 Item 8 计入块最多的是 Southwest 的 5 个。

## 验证（零调用）

- **用例**：`tests/vnext/test_historical_legal_review.py`，27 例（合成文档上的合同 17 例在 fast 层；Lumen FY2025 真实申报上的 10 例在 saved-source 层）。
- **注错**：`fault_injections.py`，18 个注错全部由具名用例抓到。第一次运行是 17 个："池吃进附注占有的块"在类夹具处就被池与提案的一致性检查拒绝——它同时改变池与关键词两份列表，守卫先于任何用例触发，这是守卫该做的事，但记下来是夹具处的捕获；于是把请求改成第一次用到时才构造、另加一条不经请求直接读池的用例（`test_the_pool_is_item_8_s_own_blocks`），重跑后 18 个全部由具名用例抓到（`fault-injections.json`）。
- **运行树端到端**：`recorded_d02_run.py`，Lumen FY2025，合成回答把 3382、3383 判为计入、其余必答块判为排除（`recorded-d02-run-lumen-2025.json`）。同一位置按批次默认（LIVE，没有可消费的登记）建出的 Run，Item 8 摘录是关键词给的 1670、3382、3383；按记录模式装入审阅后 Item 8 只剩 3382、3383，Run 冻结、PUBLISHED/EXACT，公共行 41 条证据并写明"记录测试回答、无真实调用信用"，删掉创建者日志里的登记后另一进程冷读得到同一 run_id 与结果编号，两种 Run 的结果编号不同。运行树是 `ba54996a` 加未提交改动与两份补丁（闭包 `3d1c84cc…`）。
- **出口路径**：补丁内的 `AD02ReviewIsOneCountedCallOnTheSamePath`（福特）——一次计数的调用、答案检查、从本账本自己的槽位登记、批次默认读不到测试登记、形式失败是计数的失败而不是登记、D02 的请求不能被当成别的指标的请求。

## 不主张什么

- 这里没有任何真实调用，登记全部是合成的测试回答；用例证明的是"一个回答怎样变成被计入的块"，从不证明回答是对的。
- 审阅本身的正确性要靠内容验收：审阅登记之后，按已批定义两个方向读原文，才可能计入第三层。
- 定义里"顺路提到诉讼"的边界是判断题；模型会在边界上出错，形式检查挡得住答非所问与编造引文，挡不住读错意思。
