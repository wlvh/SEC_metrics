# 全帧批次的建 Run 成本：一个期间一个数据根，同一状态只推导一次

**为什么**：取数之后要把全帧（约 47 个期间 × 39 个指标）逐位置跑原生 Run。旧做法（`../targeted-round-30a7934b/targeted_runs.py`）每个位置新装一个数据根，并在同一进程里对同一份字节反复推导同样的东西，在获取来的根上跑不完：

- 每个数据根都拷一份全部已获取的原件（`checkpoint_installation`），328 次获取时约 295 MB/个；
- 每个已存来源的核验都经冻结验证器重放整个获取检查点（一次重放随获取数平方增长，288 次获取时 26 秒）；
- 建一个 Run，`historical_run.replay_case` 在建立、每次校验开放 Run、冻结、每次读取冻结 Run 时都要跑，每次都重新加载整个 Requirement 快照（`load_requirement_snapshot`，逐代重验转移与决定链，约 13.5 秒）并重新准备钉期输入（`prepare_historical_run_input`，年报输入要解析申报并检查财年标签，15–20 秒）。一次 B03 建 Run 在剖析下 405 秒里有 330 秒花在 14 次快照加载与 10 次准备上；
- D01 的后继链（`historical_risk_results`）每推导一次候选就重新解析一次年报：一次建 Run 解析同一份字节 27 次，剖析下 240 秒里占 180 秒。

这些重复在同一进程里不可能给出不同答案——除非它们读的文件在两次之间变了。另一个进程从原件冷读每个 Run；**但那个进程也开着同样两个块**，所以它查得出"建好之后有东西变了"，却不能独立检验推导缓存自己的假设（这一点原先写成"独立检查不动"，不准确，是复审指出的）。为此每个期间按标签哈希抽一个位置，关掉推导缓存再冷读一次（`--memo-off-read-back 1`）；重放块在这次冷读里仍开着——在取数后的根上一次冻结重放要几分钟，全关的冷读做不了全帧。

## 三件事

| 做法 | 在哪里 | 等价的证据 |
|---|---|---|
| 一个期间一个数据根（该期间所有指标装进同一个根，装完再建 Run） | `period_runs.py --layout shared` | 4 个指标上与逐位置数据根比对（见"实测"）：Run 逐字节相同，文本 Run 只差审阅决定时间 |
| 检查点重放按账本状态只做一次；重放里的三个日志纯函数按参数值只算一次，缓存有界 | `scripts/vnext/historical_run_replay.py` 的 `run_checks_replay_once` | 键就是规划器的 `_replay_state`（同一套定义、同一组用例）；注错见 `injections.json`（18 个，全部由为它写的用例抓到；第一次运行漏了一个，见下） |
| 快照加载与四个准备按"参数 + 所读目录树的状态 + 环境"只推导一次 | `scripts/vnext/historical_derivation_memo.py` 的 `derived_once_per_state` | 快速用例加 3 个在本仓库已存原件上调用五个真实函数的用例；注错见 `memo-injections.json` |

两个缓存块都不是规则文件，不改 Requirement closure；它们只在批次驱动与冷读进程里打开，任何规则模块都不打开。

### 推导缓存的键为什么够，以及它自己怎样核对

键是：调用点名的目录树（快照所在的仓库根，或 `repo_root`；D01 的准备不点名目录，拿到的是原件字节，按 SHA-256 入键）、运行树（代码与已装政策；`.git/objects` 除外，其内容只经 refs 与 index 起作用，而这两者在键里）、进程环境。每棵树按每个条目的路径、类型、大小、修改与变更时间、inode、设备、链接数取指纹——改写文件而不移动变更时间是做不到的。

"键外不读任何东西"这句话不是假定，而是**每个被记住的答案都核对一次**：冻结函数运行期间，审计钩子记下它打开的每个文件、列出的每个目录、启动的每个进程；读了键外的东西（解释器自己的安装目录除外）或启动了进程的答案照样返回，但不记住。树里有符号链接就不取指纹（键看不见链接目标），参数不是纯数据、调用抛错、同一函数在自己的计算里被再次调用（快照加载的父代）都直接走冻结函数。

**钩子看不见的**：`stat`/存在性检查不产生审计事件；依赖时钟的答案会被第一次调用的答案代替。所以五个函数都在已存原件上各调两次冻结版本，要求两次答案相同，再要求缓存给出的就是冻结答案（`TheRealFunctionsAnswerTheirOwnAnswer`）。

## 实测（Macy's FY2022，328 次获取恢复出的根，12 个指标，同一棵运行树、同一 closure）

| | 安装 | 建 Run + 公共行 | 另一进程冷读 |
|---|---|---|---|
| 只开重放块 | 约 5 分钟 | 约 31 分钟（每个 2–4 分钟） | 未跑完（容器重启） |
| 两个块都开 | 172 秒（3 次重放） | 262 秒（结构化 5–17 秒/个，文本约 75 秒/个） | 125 秒 |

- **等价**：12 个 Run 里 10 个逐文件逐字节相同；两个文本 Run（D01、D02）只差审阅决定的时间以及由它导出的决定编号、校验收据编号与清单哈希；12 行公共行与证据全部相同（`compare_runs.py` → `compare-memo-off-on.json`）。
- 共享数据根与逐位置数据根（B01、B03、D01、E02）：同样只差文本 Run 的审阅时间。
- D01 单独建 Run（新数据根、缓存从空开始）：剖析下 240.8 秒 → 75.4 秒。这是**在其余缓存已开着的情况下再加上 D01 文本准备的缓存**（基线的剖析里已有 32 次命中），不是冻结路径对缓存路径的比较——原先的写法会让人读成后者，是复审指出的。

**这组数字的两个限定**：两个块都开的那次运行，建 Run 的进程用的是缓存的较早版本（只有快照与两个钉期准备，还没有文本准备），而且运行期间我改动过运行树（缓存模块本身与注错脚本）——后者只会多出几次未命中、不会改变答案，但计时不是干净的。等价结论不受影响：Run 是逐文件比的。最终版本在取数后的真实根上的计时，随全帧批次一并记录。

## 注错漏掉的那一个

重放块第一次注错时 `PARSED_ROWS_ARE_SHARED`（命中时把记住的行列表本身交出去）没被任何用例抓到。为它写的用例只改了第一次调用的结果——那是冻结解析自己返回的对象，从来不是记住的那份——所以把记住的对象交出去这件事它看不见。用例改为也改第二次（命中）拿到的结果、再要求第三次与冻结答案相同之后，重跑 15 个全部由为它写的用例抓到（`injections-first-run.json` 是第一次的结果，`injections-before-review.json` 是这次重跑，都原样保留）。复审后为三个辅助缓存的上界各加一个注错（`THE_PREFIX_MEMO_IS_UNBOUNDED` 等），在克隆里重跑共 18 个，全部由为它写的用例抓到（`injections.json`；对照 0 失败）。推导缓存的"答案是副本"用例一开始就是这么写的；同一种错误在两个块里写法不同，是注错才看出来的。

## 独立复审（2026-09-30，全新上下文的同族子代理，不是人）

结论 PASS_WITH_FINDINGS：在批次实际走的路径上，没有找到让冻结路径会拒绝的东西被接受的途径；复现出来的每一处分歧要么失败闭合（调用抛错），要么需要一个任何已追踪路线都到不了的条件。它自己做的等价测量：Marriott FY2025 的 37 个已接线指标（38 个 Run）在两个块都开的情况下建成，全部冻结出公共行；另一进程分别在两个块都开、都关的情况下冷读，38 个 Run 的 run_id、result_id、记录哈希与值逐个相同，且与建立时相同（30 个 Run：开 129 秒、关 666 秒）。

逐条处理：

1. **（中，已复现）缓存自己的目录遍历在别的进程写键控目录时会抛错。** 批次里这是真实的：每个 worker 都往运行树的信任日志（`.git` 下，在键里）登记自己数据根的检查点，写入方的临时文件可能在遍历读到它时被删掉。后果是位置失败，不会误接受。改为遍历失败（`OSError`）即按"不能键控"交给冻结函数；命名目录不存在时同样如此，于是冻结函数给出它自己的具名拒绝。批次驱动原先只在安装失败时保留数据根，建 Run 失败也删掉——现在只有全部冷读一致、每个未出公共行的位置都是具名拒绝（带类别或理由码，不是 Python 故障）时才删；D04 每期都按名失败，若"任何失败都保留"，每个约 0.8 GB 的根会把磁盘撑满。
2. **（低，已在复审期间解决）** 重放块"行列表是新拷贝"的用例原先只改冻结解析自己返回的对象；已改，注错重跑 15/15（见"注错漏掉的那一个"）。
3. **（低中）没有用例覆盖的机制**，每个都补了用例和注错：运行树的键跳过整个 `.git` 而不只是 `.git/objects`（信任日志与评估登记都在 `.git` 下）；`True` 与 `1` 的类型标签；字典键必须是文本；路径参数的真实路径部分；按文件描述符打开的豁免。另外只在真实已存原件上以仓库根调用过五个函数、没有以数据根调用过——复审的追踪只补了 Marriott FY2025，这一条仍然只有那一个例子。
4. **（低）键外的输入**：`stat` 与存在性检查审计钩子看不见（已写明）；工作目录不在键里——改为任何相对路径的打开都算键外，答案不记；解释器目录原先包括整个安装前缀（系统解释器上就是 `/usr`），键控目录或输入落在它下面就既不检查也不入键——改为只认标准库、site-packages 与字节码目录；内层调用不能键控时原先不给外层记"外来目录"，于是只做了 `stat` 的外来依赖会被记住——改为只要内层点名的目录不在外层键里，或点不出名字，外层答案就不记。"不移动变更时间就改不了文件"依赖文件系统细粒度记录变更时间，复审在本机实测 2000 次同尺寸改写无一例外。
5. **（低，合成复现）** 答案拷贝不了（如含模块对象）时原先会把冻结的成功变成 `TypeError`——改为返回答案、不记。
6. **（低）重放块的三个辅助缓存没有上界**：328 次获取时仅前缀就约 208 MB/进程，按上限外推约 1.24 GB/进程。改为每个辅助缓存有界、最旧的先丢（前缀与解析各 4 个，attempt id 65536 个）：一次重放在每个获取前后各切一次前缀，下一次的"前"就是上一次的"后"，最近几个就是它还会再要的。
7. **（低）README 措辞**：独立冷读与 D01 基线两处已改（见上）；等价证据两边都开着重放块，这一点照实写。
8. **（低，运行上）重放块的注错脚本原地改运行树**：00:49 时运行树里的 `historical_run_replay.py` 正是一个注错版本，那段时间从运行树启动的批次或冷读会加载注错代码；它的用例还往运行树的 `.git` 日志里写录制检查点。核对过：本文引用数字的实验在 00:28 以前就已结束，注错从约 00:48 开始，没有重叠。脚本改为接收一个克隆目录（`injections.py <tree> <out>`），不再改它自己所在的树。

复审的探针与输出在会话临时目录里，没有提交；这里记的是它报告的结论与本仓库据此做的改动。

## 冻结路径（两个块都关）

没有在这组实验里单独跑：它在 328 次获取的根上每个位置要几十分钟。两个块各自与冻结路径的等价由它们的用例担保（重放块的答案就是冻结重放本身的答案；推导缓存的五个真实函数两次冻结调用相同、缓存给的就是冻结答案），复审在 Marriott FY2025 的 38 个 Run 上做了两个块全关的冷读对照（见上）；批次里每个期间再抽一个位置关掉推导缓存冷读一次。

## 用法

```
# 从运行树（HEAD 加注册补丁）执行，SOURCE_ROOT 是该运行树信任日志登记过的来源根
python3 batch_plan.py > plan.tsv
SOURCE_ROOT=<root> python3 docs/evidence/issue47_history/period-batch/frame_batch.py plan.tsv <out> --workers 3
```

`frame_batch.py` 每个期间一个进程（各自的字节码目录，不往运行树写），期间结束且每个 Run 都被另一进程冷读得到同一个运行与结果才删它的数据根；已有 `period-<label>.json` 的期间跳过，所以重启后接着跑。
