# 历史分片的一致性：SEC 的区间约定与缺行的旧快照

**问题**：SEC 把一个注册人较早的申报拆进若干"历史分片"，并在主 submissions 文档里为每个分片声明日期区间 `[filingFrom, filingTo]` 和申报数 `filingCount`。目录（`normal_history_catalog`）只有在分片是"它的索引所声明的那个分片"时才信任它。冻结的检查（`normal_governance_input.history_body_alignment`，#28 的文件）只做一件事：目录保留的那几类表单，其申报日期必须落在声明区间里。实测它在两个方向上都答错：

1. **把新鲜的分片判成不一致**。JPMorgan 的索引与 69 个分片是 09-29 在两分钟内一起取回的，重取之后仍被判"不一致"，所以获取的刷新机制对它永远不会结束。原因是 SEC 的区间约定：相邻两个分片的声明区间之间空着一天，那一天的申报放在较旧的分片里。
2. **把缺行的旧分片判成一致**。只看保留表单的日期，就看不出分片少了申报。JPMorgan 的 007 号分片是 07-06 存的、来自另一次分区的正文，里面一份保留表单都没有（所以冻结检查什么也查不到），而真正的 007 号分片正好覆盖 JPMorgan FY2024 年报的申报期；Pfizer 与 Salesforce 的最新分片是在索引之前存的，此后从 recent 列表挪进分片的申报两边都没有。事件计数会因此悄悄少算。

- **空档日**：JPMorgan 51 个分片里所有晚于声明终点的申报（2372 份，各种表单）都恰好落在"声明终点 + 1 天"，也就是下一个分片声明起点的前一天；没有一份早于声明起点。其余九个索引里八个也留这一天空档，Ford 不留。
- **缺行的旧分片**：JPMorgan 007（声明 2025-01-28..03-01、2023 份；存的是 2024-10-29..11-27 的 2084 份）、Pfizer 001（存的正文到 2020-12-30、2001 份；索引声明到 2021-01-31、2005 份，recent 从 2021-02-02 起——2020-12-31..2021-02-01 的申报两边都没有）、Salesforce 001（存到 2023-07-25、2010 份；声明到 2023-07-29、2016 份，recent 从 2023-07-31 起——07-26..29 的 6 份缺）。其余不一致的分片都在早于五年窗口的区间里。
- **空档日与财年首日**：所有索引里，有申报的空档日没有一个是某个财年的第一天（某份 10-K 报告日的次日）。这一点决定了下面"没有改"那一条今天不丢任何申报。

## 改了什么（规则文件，#47 自己的）

- `normal_history_catalog.block_last_days`：每个分片的最后一天是下一个较新分片声明起点的前一天（最新分片的下一个是 recent 列表，从它最早的申报日起），且不早于声明终点。
- `normal_history_catalog.history_block_coherence`：分片里的**全部**申报（不只是保留的表单）数目等于声明数，且都落在[声明起点, 最后一天]。缺声明数也不信任。目录的两个加载函数、`historical_filing_inventory`、`historical_governance_results` 的 C04 历史遍历都改用它；Company Facts 路线的上一年遍历改用 `historical_filing_inventory.prior_filing`（冻结 `_prior_filing` 的后继，只换这一项检查）。
- `normal_history_catalog._candidate`：不一致的分片只阻断它可能装着相关申报的期间——申报日期晚于上一期报告日的一切（本期年报、它的修订、财年窗口的事件），即分片最后一天晚于上一期报告日；没有上一期的最旧期间照旧被任何不一致阻断。原来是整家公司一律阻断，那会让一个早于五年窗口的旧分片把最新一年也挡住。
- 冻结的 `history_body_alignment` 与 `_prior_filing` 不动：它们被 `issue_28` 各世代按字节绑定，普通路线还在用。
- 规划器读这个目录来决定哪些分片要重新取（`SNAPSHOT_REFRESH`），所以目录进了 SEC 接线收据的证据集，与规划器同理。

## 没有改的

- 事件窗口（#28 冻结的事件路线）和 C04 窗口按**声明**区间挑分片：一个财年若恰好从有申报的空档日开始，那天的申报会被跳过。实测没有这样的日子，所以今天不丢任何东西；它没有被防住。
- 行数相同、内容不同的分片（同样多的申报、换了几份）会通过：索引给出的唯一独立摘要就是数目。

## 验证

- `tests/vnext/test_history_block_coherence.py`：构造分片逐条说明区间约定、数目与日期按全部申报算、按期间阻断；另外三个读分片的地方（申报清单查找、Company Facts 上一年遍历、C04 历史遍历）各有一对构造分片——新鲜但有空档日申报、缺一份申报——冻结检查在这两个上都答错，所以哪处留在冻结检查上都有用例失败；最后一个类读全部真实分片（含导出里的）。
- 注错 `injections.py`（原地改规则文件，所以在隔离副本里跑）：16 个，在隔离克隆里跑；结果随后补上。
- 原先拿这些旧分片当"分片驻留"正例的用例改到按已存分片重导出索引的录制根上（`tests/vnext/derived_history.py`），真实已存字节上改为断言按名拒绝。

## 效果

在最终恢复根（1130 次获取）上用规划器实测改动前后，见 `effect.py`；尚未跑，结果随下一次提交补上。按规则推算（未实测）的方向：这次改动在两个方向上移动帧——JPMorgan 的新鲜分片不再被误判；Pfizer 与 Salesforce 最新分片的最后一天晚于某些目标期间的上一期报告日（Pfizer 2021-02-01 晚于 FY2021 的 2020-12-31；Salesforce 2023-07-30 晚于 FY2024、FY2023、FY2022 的上一期），这些期间会被新判定阻断——它们原来被静默放行、事件会少算——要重取那两个分片与其索引才能解除，而这不在已批授予里。

零 SEC 或模型调用。
