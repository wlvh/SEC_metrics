# 普通更新的来源发现

`tools/vnext_normal_update.py --discover-sources` 根据保存的 SEC 清单自动列出当前及上一期年报、相关修订、最新代理材料和财年 8-K 的来源依赖。输入是公司清单和原始请求记录，不需要用户指定 accession、文件或答案。默认仍是原有的年度输入检查；旧调用方式不变。

```bash
python3 tools/vnext_normal_update.py --discover-sources \
  --output /absolute/new-external-directory/source-requirements.json
python3 tools/vnext_normal_update.py --discover-sources --company jpmorgan_chase
PYTHONPATH=scripts python3 -m unittest -v tests.vnext.test_normal_source_requirements
```

输出文件必须新建于源码及正式发布工作区之外。指定公司时只允许公司清单内的唯一集合。CLI 对缺口返回 2，同时保留其余公司输出；来源都可用返回 0。两个退出码均不授予获取、运行或发布权限。

## 如何决定下一步来源

1. 验证本地清单、原始正文和独立请求头均来自安装代码所绑定的既有来源基线。
2. 从清单得出新年报主文件地址，然后才读取主文件和公司事实数据。主文件尚未保存时仍输出其地址；申报声明的身份与经过原件核对的身份分别保存。
3. 以原件的实际期间读取相关历史清单。当前清单和历史正文冲突时列出需刷新的数据集，不能宣布文件集合完整。
4. 对已选年报及修订读取 accession 目录，发现原生 instance XML；对财年 8-K 同时列出主文件和头文件。缺少目录时保留“子文件名称尚未发现”，不能把已知 URL 列表说成完整来源集合。
5. 按 URL 去重，保留每种用途。最后一次 GET 失败时保留该失败，不能退回较早成功来满足依赖。

`new_discovery_dataset_urls` 是要重新检查最新状态时需要刷新的清单和 companyfacts。`missing_or_failed_source_urls` 是当前保存材料中的缺口。两者是发现输入，不是已获授权的调用计划；完整刷新后可能发现新地址。原件之间存在可替代关系时，各指标仍由自己的来源验证器裁决，不能由此清单直接决定是否有完整财务结果。

## 真实材料验证和边界

2026-09-12 的十公司只读检查得到 305 个已知 GET 地址、27 个待刷新数据集地址、8 个缺失或失败文档。Marriott 和 Paramount 的已知依赖可用；JPM 当前清单与历史分片冲突，文件集合未证实；其余七家保留文档缺口。其中 Salesforce 有真实失败的财年 8-K 头文件，其他缺口主要是先前年报 HTML；已保存的原生 XML 仍可支持部分指标。

来源测试使用三家公司实际原件，并删除主文件、删除目录、篡改目录正文、改变目录主体和文件名、输入后续年报元数据。实际首次 8 项通过，缺文件与篡改测试在新外部目录执行，不修改原件、不读取旧结果、不连接网络。

这是普通更新的来源发现接线。它不发起请求，不绕过既有基线导入限制，不形成新获取信用，不执行指标，也不证明 39 指标全部来源或生产更新成立。下一步仍是新预算下的受信获取及新来源进入正常计算的接线；关闭的旧获取阶段继续关闭。
