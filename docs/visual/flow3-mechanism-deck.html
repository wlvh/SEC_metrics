流程三 · 一批结果如何成为当前正式版本

正式性不来自「刚刚写过这个文件」，
来自一次合法的指针切换

这条流程接收的不是一堆待写入的 CSV，而是一批已经算对、可以重放的结果。 它先证明这批结果完整而无重复，再把整版内容封成一个内容寻址的不可变目录， 最后只用一次原子替换宣告「当前正式版本是谁」。 把「更新十几个文件」转化成「切换一个指针」，崩溃窗口就从十几个收敛成一个，而且这一个是可判定的。

01 问题 为什么不能直接覆盖

十几个文件的更新，有十几个可以崩在中间的时刻

要替换的误解：「把新文件写到 outputs/ 下面，覆盖旧的」看起来只是一次批量写入。 它不是——它是十四次独立写入，每两次之间都存在一个下游可以读到的中间态。

问题不在于某个文件写坏了。每个文件都是合法的，格式校验全过。 问题在于下游读到的组合从未存在过：一半来自新版本，一半来自旧版本。 这种损坏没有任何单文件校验能发现。

而且退不回去。旧字节已经被覆盖，除非事先手工备份—— 可手工备份本身又是一个会写到一半崩的操作，于是你需要一套机制保证备份的正确性， 然后又需要一套机制保证那套机制。

最根本的缺失是：这个目录里只有文件，没有版本。 你说不出「现在生效的是哪一版」，也说不出「上一版是什么」。

02 核心设计 一个提交点

把更新十几个文件，转化成替换一个指针

一版 = 一个不可变目录，目录名就是它全部内容的指纹。 目录里有一份 manifest，列出每个文件的路径、SHA-256、字节数。 根目录只留一个很小的 active_publication.json，说明当前正式版本是哪一个包。

发布 = 先把新目录整个写好并验证，然后原子地重写这一个指针文件。

指针替换是唯一的提交点。这句话的实际含义是两条： 它之前的所有失败都不改变正式版本；它之后的所有失败都可以从指针恢复。 没有第三种结局，也不需要猜。

代价是要多维护一批对象——发布包、切换意图、切换收据、历史链—— 并且旧包永远留着，没有任何 GC。这是这套设计明确接受的成本。

03 主角 三个对象

模块只是工位，对象才是主角

判断一个对象是不是主角，用一句话检验：删掉它，我还能不能准确说清这一层建立了什么新事实？

删掉批次权威，说不清「这一批到底完不完整」——单个结果只能证明自己。
删掉不可变发布包，说不清「这一版包含什么」。
删掉 pointer 加切换历史，说不清「哪一版是正式的、它是怎么来的」。

第三个必须是两件东西合在一起。pointer 只是一个四字段 JSON； 如果它能脱离收据链单独被改，那么改一个文件就能把任意包——包括一个从未通过验证的包——变成「正式版本」。 收据链把这件事变成：你还得伪造一整条自洽的历史，而且新 tip 的 hash 必须和指针对上。

04 第一站 批次权威

十个结果各自正确，不等于这一批完整

07 第三站 candidate_status

空值不等于失败

要替换的误解：「矩阵里有空值就是失败，没有空值就能发。」

批次级判定只读两个字段，而且只有一种组合会阻断发布。 N_A_STRUCTURAL 表示这个指标按公司 traits 本来就不适用—— 它是完整结果的一部分，不阻断。 APPLICABLE + WITHHELD 表示本应有结果但证据或计算不足，这才阻断。

两者在 CSV 里可能都显示为空，语义完全相反。

判定是算出来的，函数体里没有任何调用者传入的布尔值； 未知的字段值也不会被当作「不阻断」，而是直接抛 StateError——fail closed，不是 fail open。

被判 BLOCKED 时的对象结局是完整的：不产生 projection_manifest_id、 不写发布包、指针逐字节不变、结果与 Trace 全部保留供审计。 失败的尝试不会用空值覆盖成功的旧版本。

08 第四站 写包

目录名就是内容指纹，写包本身是个小事务

publication_id 不是随机的，是从 identity 内容派生的： candidate_status、requirement_hashes、batch / projection / validation 三个 ID、 全部文件的 {path, sha256, size}、ledger_binding，以及 previous_publication_id。

因为前驱也在 identity 里面，整条发布链是一条 hash 链： 改动任何一个历史版本的任何一个字节，都会让它自己的 ID 变，进而让所有后继版本的 ID 失效。

写入过程本身是个小事务：先写进隐藏临时目录，逐文件原子写，写完 manifest， 在临时目录上先跑一次完整验证，通过了才 os.replace 目录级改名并 fsync 父目录， 最后对最终目录再验一次。

而且它是幂等的：最终目录已存在时，验证已有内容与本次 manifest 逐字段相等， 相等直接返回，不等报错。同一个 ID 永远不可能指向两组不同的字节。

09 第四站 准备 ≠ 发布

磁盘上 9 个包，只有 3 个进过切换历史

准备阶段完全不碰指针。这个性质有一个很直观的证据： 仓库里现在有 9 个内容完整、manifest 自洽、验证通过的发布包， 而切换收据里只出现 3 个 publication ID。

另外 6 个是两次完整的彩排——准备好了、验证过了、从未提交。 这正是这个设计想要的：彩排的代价只有磁盘。

反过来说，按目录 mtime 挑「最新的那个」会绕过前驱校验、CAS 和整条切换历史。 正确的入口是 PublicationView.open(publication_root=repo_root)， 不是 glob(outputs/publications/*)[-1]。

这条区分要一直记到最后一页：目录存在、曾经提交、当前 active、通过验收，是四种不同的事实。

11 第六站 唯一提交点

镜像先写、指针后写，官方状态由指针决定

事务在排他锁内按固定顺序进行。前四步都还没有改变官方状态： CAS 与前驱双检失败时，连 intent 都还没写。

两个前置条件都要。「当前指针 == 我准备时的前驱」防的是并发； 「包自己声明的前驱 == 当前指针」防的是错配。单独任何一个都不够。

然后写 switch intent——这是 write-ahead 记录， 它保存 previous / proposed 两个指针、切换模式、上一条收据 ID， 以及 14 个旧镜像当时的 {sha256, size}。它记 hash，不记字节。

12 韧性 崩溃恢复

「出错就回滚」是错的：方向由指针决定

进程死亡不会执行任何清理代码——故障演练用的是一个继承自 BaseException 的异常，故意不继承 Exception，这样它能穿透生产代码里所有的 except (OSError, ValueError, PublicationError)。

磁盘上只留下 intent 和一个停在某处的状态。下一个 writer 取得排他锁后， 读 intent、读当前指针，然后只做一次比较。

第三条出边是这个设计最重要的部分：它不猜。 如果状态既不是事务前也不是事务后，说明发生了这套机制没有建模的事情， 此时任何自动动作都可能让情况更糟。

还原镜像时不用备份，用不可变包重建：从 R1 包读出字节， 要求 hash 与 size 与 intent 记录完全一致才写回。 好处是系统里从来只有一份权威字节——备份本身会写一半、会损坏、会和权威源不一致。

13 韧性 并发

锁负责串行，CAS 负责决胜

两个发布者可以同时准备，因为准备不碰指针。提交时排他锁把他们排成一列。

但排队之后，第二个人的前提可能已经过期。 锁只保证「不会同时写」，它不保证「我拿到锁时，我准备阶段看到的那个前驱还是当前值」。 CAS 检查的正是这一句。

只有锁没有 CAS，第二个 writer 会基于一个已经过期的前提，把 winner 覆盖掉。

loser 的结局是干净的：抛 Publication CAS predecessor changed， 不留任何痕迹——收据数量不变，镜像未被触碰。 它准备好的包仍在磁盘上、完全有效，只是从未提交。

回滚受同类约束：只能回到当前指针证明的直接前驱， prepared-only 的兄弟版本即使内容完全有效也不能被回滚过去。

  • 代码故障矩阵的两个并发场景真开两个线程，要求恰好一个成功一个失败。fault_matrix.py:64-70 · EXACTLY_ONE_WINNER / CAS_LOST_ACTIVE_PRESERVED
  • 代码回滚目标必须是当前指针的直接前驱。publication.py:5580-5586 · "Rollback target is not the committed predecessor"
14 历史 切换收据

所有收据必须构成恰好一条链

指针写完之后，writer 生成一条 PUBLICATION_SWITCH 收据， 绑定新指针、切换模式和上一条收据的 ID。

每次读取时这条链都要重新验证：收据 ID 等于其余字段的 content hash 且文件名就是这个 hash； 没有悬空引用；恰好一个 tip；tip 的 pointer 与指针文件逐字段相等； 从 tip 往回走无环。

最硬的是最后一条：走完之后访问过的收据集合必须等于全部收据集合。 你不能往这个目录里塞一条无关的收据，哪怕它自身格式完全合法。

15 下游 PublicationView

读者钉住一个版本，之后再也不看指针

PublicationView.open() 只接受一个 root，做八步校验， 然后把 publication ID 和 bundle 目录钉在内存里。 之后每次 read_bytes() 只允许读 manifest 列出的路径， 并且重新校验那个文件的长度与 sha256。

即使外部指针随后切到别的版本，已打开的 View 仍读旧包；新 View 才看新版本。 这是多文件一致读的真正下游保证——不是「切换很快」， 而是「你手里的这一次读取，从头到尾属于同一个版本」。

读者也参与锁协议：writer 从镜像准备一直持排他锁到收据落盘， 所以持共享锁的读者永远看不到「指针已切、收据未写」那个故意留出的中间态。

一个会绊住新人的真实坑：open() 要求 outputs/active_publication.json.lock 存在且是普通文件， 而这个文件在 .gitignore 里。 全新 clone 里它不存在，任何要打开发布视图的代码都会直接失败。 这不是 bug——锁文件本来就不该进版本库—— 但它意味着「clone 下来就能离线验证」这个性质需要多一条说明。

16 边界 包证明到哪为止

包证明完整性，不证明时效与验收

一个自然的理解是：既然包是不可变的、自包含的、每次读都验 hash， 那么打开它就等于拿到了完整可信的证据。这个理解有四处需要限定。

一、Requirement 声明会漂移。包里记的 requirement_closure_hash 与当前仓库重新推导的值已经不同， 而 open() 照常成功——它把这个字段列为必须存在，但不从仓库重新推导。 这是正确的设计：不可变包应该记录发布当时的事实。但它意味着那是一个历史声明，不是当前断言。

二、验证范围包自己写着：LIGHT_REVIEW_MODE / PASSED_WITH_CAVEATS， 并显式列出 issue_15_full_acceptance.not_run。

17 收束 因果心智地图

十道门，每一个 ≠ 都需要一组具体的证据

可以换的实现细节：JSON 指针、本地目录、fcntl 文件锁、 rename、14 个镜像的具体清单、存储后端。这些都是当前实现，不是产品承诺。

不能丢的因果：完整批次决定内容资格 · 独立投影加事后比较 · 精确的门禁绑定 · 不可变版本 · 唯一提交点 · 前驱与 CAS · write-ahead 恢复 · 一条连通历史 · 钉住式读取 · 篡改时 fail closed。

如果未来迁到对象存储或多机数据库，这十条必须逐条找到对应物—— 而不是「把文件复制到云上」。多机方案还要额外定义网络分区、ack 丢失、 租约与 ETag 语义，那是新问题，不是同一个问题换个地方。
