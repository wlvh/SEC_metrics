如何变成可信事实

02问题

模型能给你一个数字，但这个数字不带出处

有些指标 SEC 的结构化数据（XBRL）里根本没有——酒店的入住率和 RevPAR 只出现在年报正文的 MD&A 表格里，是一张普通 HTML 表，没有任何标签。于是只剩一条路：让模型去读那张表。

这一页要替换的误解 「模型准确率够高就行」。准确率是一个统计量，它无法告诉你这一次属于哪一条来路。财务指标要的是逐条可追溯，不是平均正确。

也不是这个 「用第二个模型检查第一个模型」。第二个模型同样不带出处，只是把不可验证性又叠了一层，还多了一层幻觉。

这一页建立的事实 问题不是「抽取」，而是让一个模型给出的数字带上可机械验证的出处。
03问题

同一个标签，两个数字

这不是构造的例子。下面是 Marriott FY2024 年报里 table_000011 的真实内容 实测。第 18 行和第 28 行的行标签，raw_text 逐字节相同——都是 "\nWorldwide (2)"。挂在它们下面的入住率是 69.7 和 69.8。

为什么这一页重要 模型说「Worldwide 入住率 69.8」，这句话什么都没证明。表里有两个 Worldwide，行标签的原始字节完全一样。

要把它们分开，必须同时给出两个坐标：段落头 (19,0) 证明这是 Systemwide 口径，行标签 (28,0) 证明这是 Worldwide 地域。少任何一个都不够。

这就是后面所有机制存在的理由。

这一页建立的事实 一个数字加一个行标签不足以定位一个事实。坐标是必需的，而且不止一个。
04核心设计

模型只负责指认，不负责证明

解法不是把模型换得更强，而是改掉它被要求交付的东西：不要答案，要坐标加声明。这一步把一个不可判定的命题换成了一个可机械判定的命题。

这一页建立的事实 举证责任被搬到了模型自己身上：它必须说出一个可以被原文验证的东西。所有推导留给确定性代码。

一个数字要从 HTML 字节走到「可以进计算」，中间只有一次外部模型调用；它两侧的十二个工位全部是本地确定性计算。下面这张图是后面十四页的地图：三个主角对象、四道机械闸门、以及每一站的失败出口。

06第一站 · DerivedAsset

不筛表，全部展开成一个坐标空间

一份 SEC HTML 里没有坐标，只有嵌套的 <table> 和大量合并单元格。「第 28 行第 15 列」这句话在合并格的世界里是有歧义的。这一站把 2 047 740 字节变成一个无歧义的地址空间。

这一站最关键的约束 build_table_grid() 的签名里没有任何过滤参数。docstring 写死："No metric terms or filter parameters are accepted by this API." 代码

为什么这条约束重要：如果允许按关键词筛表，那么「模型选中了正确的表」这个结论就被污染了——是模型选对了，还是筛选器已经把答案递到它面前？不筛，模型面对的就是完整的 67 张表。

  • 2 047 740 字节 → 67 张表 / 19 329 展开格 / 8 654 原点格（44.77%）实测
  • 构建耗时 1.15 s，derived_asset_id = sha256:6b9fabbd… 与冻结 Run 落盘值逐字符相同
  • 资源上限在分配前检查。max_total_cells = 100000 是硬编码常量
这一站建立的事实 任意 (table_id, row, column) 要么唯一解析到一个格子，要么越界报错——而且这个解析过程只依赖原始字节。
07第一站 · 关键字段

每个格子同时拥有两个文本字段

这一对字段的差异，是后面全部戏剧性的来源。raw_text 是解析器保留的原样文本，HTML 实体未解码、空白未折叠；text 是实体已解码、连续空白折叠成单个空格、首尾去空白之后的结果。

先记住这件事 Evidence 检查数值时用 text，检查口径标签时用 raw_text。这个不对称是刻意的，第 12 页会讲清楚为什么，第 13 页会展示它的代价。

其余字段 row_index / column_index（展开后的坐标）、origin_row_index / origin_column_index（合并格的左上角）、rowspan / colspan、header（是否 <th>）、is_origin。

谁有修改权 没有人。创建后只读，而且每次 Run 冻结验证时都会从原始字节重建一遍并要求逐字段相等。

这一站建立的事实 同一个格子的「原样」与「归一」两种读法同时被保留，谁在什么场合用哪一个，是后面契约的一部分。
08第二站 · 传输

压缩省 token，但压缩引入了一个新风险

展开后的网格有 3 554 243 字节，其中 55.23% 是合并格的副本，直接塞给模型是纯浪费。但压缩引入了一个全新的风险：模型看到的表和 Evidence 重读的表可能不是同一套。如果这个风险不消掉，「系统回去重读」这句话就没有意义——它读的可能是另一个世界。

这一站建立的事实 新增四个绑定字段：expanded_derived_asset_id、expanded_grid_sha256、compact_payload_sha256、round_trip_receipt_id。往返验证通过之后，「同一套表」成为下游可以依赖的前提。
09第三站 · 出网

先落 marker，再开 socket

这是整条链路唯一有外部副作用的地方，所以七个步骤的顺序是被刻意设计过的。付费模型调用最危险的情况不是报错，而是请求可能已经发出、本地却不知道远端执行没有。

重试策略 循环是 for attempt_ordinal in (1, 2)——1 次初始 + 最多 1 次重试。而且 qualification 这条路的授权里写着 automatic_retry_count: 0，一次都不重试 落盘。

HTTP 429 / 5xx / TIMEOUT 是 RETRYABLE；HTTP 400 / 401 / 402 / 422、SCHEMA_VIOLATION、EVIDENCE_FAILURE 全是 TERMINAL。_classify 的默认分支也是 TERMINAL——不认识的情况按保守处理。

背后的原则 重试用来对抗网络抖动，不用来对抗模型质量。允许对 schema/evidence 失败重试，等于把「多试几次」变成一种事实上的质量策略，那会污染 qualification 的统计意义——「通过了」就变成了「试了几次终于通过了」。

副作用的边界 全部外部副作用被限制在文件系统的 10 个命名空间里。流程一的 structured_only_result() 反过来扫这 10 个目录，只要有任何一个文件就报错——这是「这批发布确实没调过模型」的机械证据。

10第四站 · ObservationCandidate

模型返回的是坐标，不是答案

这是第一个承载模型输出的对象。它代表的事实是：模型声称这些坐标上有这些内容。它不代表这些内容是真的。下面是 Run 4863af40 的真实返回 落盘。

Reader 做了什么 validate_reader_output() 做极严的结构校验：重复 key 直接拒；根字段必须恰好 4 个；每个 candidate 字段必须恰好 8 个；角色顺序必须与 Spec 完全一致（缺、重、乱序都拒）；所有 locator（选中的、竞争的、口径证据的）必须落在同一张目标表内。

Reader 没做什么 它一次都没有去看那张表。模块 docstring 就是它的设计声明："Validate strict Reader output without solving or correcting its claims." 代码

新增的三个字段 candidate_hash（只覆盖实质主张，不含模型名、时间戳、日志）、assistant_output_sha256、status。

status 由代码算，不由模型声明：有未决竞争主张、或有任何口径值查不到精确别名 → REVIEW_REQUIRED；否则 CANDIDATE。

这一站建立的事实（以及没建立的） 结构合法、角色齐全、坐标不越表。仅此而已——内容是否为真，此刻一个字都没验。
11第五站 · EvidenceCheck

四道闸门，各自排除一类事故

这是整条链路里唯一一个「凭什么信」的对象。前面的 Candidate 只是模型的说法，后面的 Review 只处理语义，中间这一层是唯一的机械真值判定——全部是确定性代码，没有模型参与。

这一站建立的事实 Evidence PASS 不代表这个数字是业务要的数字，只代表「模型指的位置上确实写着它说的东西，而且口径标签能追到表里」。Evidence REJECTED 确实代表这个主张站不住。
12核心机制

值比归一化文本，标签比原样文本

这是流程二最核心、也最有争议的一条契约。_verify_claim_cell 用 cell["text"]，_verify_local_labels 用 cell["raw_text"]。同一个格子的两个字段，被用在两个不同的检查里。

13失败路径

一个换行符的完整去向

这不是教学假设。2026-08-26，Run cf8dbd0c：远端调用完全成功（HTTP 200，零重试），模型输出结构完全合法，选的表对、指的格对、数也读对了 落盘。唯一的问题是 scope_evidence_2.raw_text 少了一个前导换行。

本次实测 把 cf8dbd0c 真实返回的那份 candidate 喂给两个内部函数，结果是 value check : PASS → 0.698，label check : FAIL → SCOPE_LABEL_TEXT_MISMATCH 实测。值检查是通过的——模型的答案完全正确，只差一个换行符。

但它没有精确的落盘原因 第 ③ 步那条 REJECTED 记录从未落盘。grep -ro SCOPE_LABEL_TEXT_MISMATCH artifacts/ 在整个仓库里命中 0 次 实测。落盘的只有 attempt 上那个笼统的 error_class: "EVIDENCE_FAILURE"——具体哪个字段、哪个坐标、差在哪一个字符，全都要靠重跑才能知道。
14核心机制

归一化只有一条路：Spec 声明的精确别名表

口径标签重读通过之后，还要回答一个问题："Comparable Systemwide Properties" 这串字对应哪个规范口径？这一步没有正则、没有模糊匹配、没有数值容差、也不用第二个模型。

B10 的完整别名表 三个维度，每个维度一个候选值，每个候选值一个别名字符串 落盘：

property_population: {comparable: ["Comparable Systemwide Properties"]} operating_scope: {systemwide: ["Comparable Systemwide Properties"]} geography: {worldwide: ["Worldwide"]}

这就是泛化边界 Hilton 的表里写的是 System-wide（带连字符），Hyatt 写的是 System-wide hotels (a)——两个都不在这张表里。别名表的覆盖面，就是这条链路的泛化边界。

模块 docstring 写死了这个立场 "It deliberately contains no numeric, percentage, date, or free-text normalizers." 代码

15第六站 · Review

能不能不要人，由三个机械条件决定

Evidence PASS 不等于批准。Evidence 能证明「第 19 行第 0 列确实写着 Comparable Systemwide Properties」，但「可比全系统口径是不是业务要的口径」是一个语义判断，由人或被明确授权的 SYSTEM 承担。

SYSTEM 记录从不假装有人批准过 reviewer_type = "SYSTEM"、reviewer_id = system:optional-review-v1、reason = EVIDENCE_BOUND_AUTO_APPROVE，全是固定常量。代码注释直说："It never claims a person approved the result." 代码

批准的对象是一整包，不是一个数字 review_unit_hash 罩住 12 项内容，其中包括 rendered_review_hash——实际渲染给复核者看的字节的 hash。任何一项变了，旧的批准自动失效。

16第七站 · VerifiedObservation

模型说的 69.8 从来没有进入过下游

这一页解决一个很常见的误解：「模型说的数字进了系统」。没有。进入下游的是 Evidence 自己算出的 0.698；模型的原话只留在 attempt 的原始响应字节里，不参与任何后续计算。

这一站建立的事实 这个对象和流程一产出的 VerifiedObservation 是同一个类型、同一个 schema，交给同一个 Calculator。下游看不出这个 Result 是哪条路来的——除非它去看 approval_effect_hash 空不空。
17第八站 · 冻结

冻结 = 从原始字节重算一遍，不是打标记

落盘的 PASS 不能自证。Run 冻结时，系统会把整条链从 RawBlob 的字节重新算一遍，并要求每一步的结果与落盘记录逐字段相等。

但「冻结」不等于「永远可重放」 仓库里 6 个 FROZEN Run，只有 4 个能重放；另外 2 个属于一个已被取代的 qualification cycle，它们冻结时的 Requirement 快照与当前仓库不一致，重放时被拒 实测。

这个状态本身是可辩护的：当前 freeze receipt 指向的 cycle 里的 4 个 Run 全部可重放，失效的是被取代的历史证据。但可重放性是相对于当前 Requirement 快照而言的——把「冻结」画成一个永久保险箱，就传达错了。

最后一步不是「进入正式发布」 这条链在 Run 冻结处结束。到当前快照为止，进入 active publication 的 AI 结果数量是 0，三个 provider 计数器全为 0 落盘。

18通过的范围

live_ready = true 到底说了什么

当前 freeze receipt 写着 live_ready_family_ids = ["lodging_kpi_table"] 落盘。一个不了解背景的人会自然地把它读成「模型读酒店 KPI 表这件事已经验证过了」。这是全篇最容易被误读的一句。

  • 7 次通过，全部是 Marriott。跨发行人 7 次尝试，0 次成功。
  • 公平地补一句：跨发行人的 7 次里，只有 1 次用的是当前 prompt。当前 prompt 上是 7/8，唯一那次失败正好就是唯一那次跨发行人尝试。

样本被换过两次 qualification 最初要求不同发行人。Hilton 试了 7 个 fixture 版本、6 次真实调用，全部失败；Hyatt 试了 3 个版本、1 次调用，失败。之后样本被换成同一家公司的不同财年，判据也相应从 different_issuer_cik 改成 same_issuer_distinct_fiscal_year_and_accession，然后就全过了 落盘。

context 门的 PASSED 是一次豁免 估算 395 337 tokens 对预算 200 000——接近两倍，门却是 PASSED。依据是 EXACT_REVIEWED_QUALIFICATION_REQUEST_WITH_TERMINAL_USAGE：估算器是故意保守的上界，一次经人工逐 SHA 复核过的真实请求可以覆盖它。

financial family 至今卡着 JPM 那份 12.9 MB 的 10-K 有 679 张表、60 348 个原点格，展开后 124 761 格，上限 100 000。普查收据显式记录了没有做过的事——六个 forbidden_actions 全 false。宁可卡着，也不为了跑通而悄悄丢表。

准确的读法 live_ready = true 说的是「在 Marriott 这一家公司的三个财年上，用当前 prompt，两个 task 的机械证据链完整」。它不支持「模型能读任意酒店集团的 KPI 表」。

这不是隐瞒——fixture id、判据、每一次失败的 Run 全部完整落盘且内容寻址。但只画「通过」不画「在谁身上通过」，就是在误导。
