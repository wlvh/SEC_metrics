流程一 · 结构化 SEC 数据如何成为正式指标

一个数字要通过十一道关，
才配叫「当前正式指标」

这条流程接收的不是一个已经可信的数字，而是一组可以按字节复核的 SEC 原始材料。 它把材料逐级升级成有来源、有资格、有结论、有版本的事实。 每一关只回答一个「事后无法回答的问题」，代价是每一关都要生成一个不可变、内容寻址的对象来承载答案。

01 RawBlob raw_asset_id

第一关只证明一件事：我说的是这一组字节

要替换的误解：「文件在 evidence/ 目录里」不是身份。路径可以改名， 中间任何一级目录都可以被 symlink 指向别处，同名文件可以被整份替换。

这一关刻意降级了下游能说的话：从「有个文件」降到「这是这一组确切的字节」。 降级换来的是可核对性——raw_asset_id 就是字节自身的 SHA-256，改一个 bit 就不是它了。

路径解析逐段检查每一级是否 symlink，并要求 resolve() 之后仍在仓库根下； 每次重新读取字节时还会再核一次 hash 与长度。

仍然没有证明的：这组字节属于哪家公司、哪一次申报、有没有资格代表某个会计概念。 那是下一关的事。

02 SourceReference source_reference_id

同一组字节，两个申报身份

要替换的误解：内容 hash 只证明「同一组字节」，它不证明这组字节属于哪家公司的哪一次申报。

这是整条链上最反直觉的一处：一份 Company Facts JSON 会生成两个 SourceReference。 同一份字节、同一个 request_attempt_id，但 accession 不同，所以 ID 不同。

为什么要这样：Company Facts 是「一家公司所有历史事实的合集」，一份文件里同时含 FY2025 和 FY2024 的数字。 只建一个引用，就说不清「这个 2024 年的 Assets 是通过哪份年报申报的」。 分成两个观察之后，适配器用 fact["accn"] 把事实按申报切开，每条事实归属到一次具体申报。

构造函数的 docstring 把意图写得很直白：Two observations of the same bytes remain distinct when their filing identity differs.

03 SourceSetManifest source_set_manifest_id

唯一一个证明否定命题的对象

要替换的误解：前两关证明的都是「我手上这个东西是真的」。 没有任何一步证明「我该拿的都拿到了」。

对正数来说，漏一份文件只是算小了；对 0 来说，漏一份会让「没发生」和「没看见」变成同一件事—— 而且没有任何异常、没有任何日志，只有一个错误的数字。这是整层里唯一一类 hash 发现不了的错误， 所以它需要一个专门的对象来防。

关键机制是构造时的自我否证：调用方声明「我要用这 N 个 filing」， 构造函数自己从 submissions 字节里独立算出「按发现规则应该是哪 N 个」，两边必须完全相等。 调用方无法通过多传或少传引用蒙混过关。

8-K 集合还要另外调 verify_source_set_completeness()， 把整个清单从字节重建一遍并要求逐字段相等。

05 DeterministicVerifiedClaim verified_claim_id

选中必须是筛选条件的唯一解，不是排序后的第一名

要替换的误解：「找到了 Assets」远远不够。 JPMorgan 那份 Company Facts 里，us-gaap:Assets / USD 有 206 条事实，横跨 73 个 accession。

每一级筛选都是 catalog 声明的维度——accession 角色、期间角色、单位、form、fiscal_period—— 不是代码里的 if。calculator.py 的模块 docstring 写得很明确： 它不含任何指标、公司、行业或 scope 分支，全部业务顺序、概念、guard 和容差都以数据的形式到达。

关键的确定性保证：允许筛出多个候选，但它们的 (value, unit) 必须完全一样。 一旦同一条件下出现两个不同的值，整批发布中止，不做任何猜测。相同值的多个候选按 claim ID 排序取第一个—— 这是纯粹的去歧义 tie-break，不影响结果。

因此选中的 claim 集合是输入字节的函数，不含任何随机性或时间依赖。

06 VerifiedObservation observation_id

被拒绝的路径被写进对象，而不是写进日志

claim 是「来源格式层」的事实。要参与公式，还必须说清楚：它在哪个指标里扮演什么角色、 在什么口径（scope）下成立、系统试过哪些分支、为什么退到了这一条。

catalog 的 branches 是一个有序数组。依次尝试，第一个所有 component 都能找到 claim 的分支胜出。 找不到概念时抛内部私有异常 _BranchUnavailable，被捕获后记进 rejected 列表，继续试下一条。

这叫契约 fallback：它不是网络失败后的重试，而是指标定义提前声明的会计口径优先级。 Pfizer 没有申报 OperatingIncomeLoss，所以 B07 退到第二条分支—— 用「税前利润 − 非营业损益」重构营业利润，并把 quality 标为 APPROX。

最值得看的字段：rejected_branches 从 [] 变成 [{branch_id, reason}]。这不是日志，是一个被 hash 覆盖的字段，随 bundle 永久保存。 三个月后你仍能读出「那次发布，Pfizer 的 B07 为什么走了近似路径」。

approval_effect_hash 恒为空字符串——空字符串在这里是正式语义：未经任何人工或系统审批。 AI 路径走 reviewed_observation()，那里这个字段是真的审批 hash。所以「这个数是不是模型给的」在对象层面一眼可辨。

12 发布事务 active pointer

这一关建立的是：「当前正式版本是谁」由一个受审计的指针决定， 而不是由哪个 CSV 最后被写入决定。

十四个根目录兼容镜像先写、指针后写，是刻意的顺序。 历史边（switch receipt）必须写在指针之后——代码注释写得很直白： 提前持久化它，会让「指针前崩溃」留下一个孤儿，日后指针被篡改时可能被误读成已提交。

崩溃恢复只认两种状态：当前指针等于 previous 就向后回滚， 等于 proposed 就向前补齐；两者都不是就 raise，拒绝猜第三种。

读者也参与这个锁协议：PublicationView.open() 拿共享锁， 并拒绝在有未完成 intent 时读取。所以读者要么看到完整的旧事务，要么看到完整的新事务， 绝不会看到「指针已切但历史边还没写」这个刻意留出的中间态。

13 切换历史 5 份 switch receipt

这不是设计文档，是真发生过的五次切换

中间那次 ROLLBACK 是有意义的：它证明回滚不是文档里的一句承诺， 而是一条走通过的路径，并且回滚目标必须是当前指针已证明的直接前驱—— 不能回到任意历史版本。
