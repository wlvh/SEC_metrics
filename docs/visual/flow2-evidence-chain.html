第 0 幕 · 建立问题

同一个标签，两个数字

读这份文档的人几乎都会先把问题想成：模型给了一个数字，我们去检查这个数字对不对。这个想法在这里行不通，而且不是因为模型不够强。

下面是 Marriott FY2024 年报里 table_000011 的真实内容 实测。请先看第 18 行和第 28 行的行标签：它们的 raw_text 是逐字节相同的 "\nWorldwide (2)"。挂在这两个标签下的入住率分别是 69.7 和 69.8。

table_000011（29 行 × 39 列，节选第 8–28 行）

Marriott FY2024 的「全球入住率」，B10 这个指标要的是哪一个？
先猜，再往下看。这一步不影响任何机制状态。
这一幕建立的事实

一个数字加一个行标签，不足以定位一个事实。要把 69.8 和 69.7 区分开，必须同时给出段落头的坐标（第 19 行）和行标签的坐标（第 28 行）。这就是后面所有机制存在的理由：把「这个数字对不对」换成「你指的那几个位置上是不是真的写着这些字」。

第 1 幕 · 对象出生

DerivedAsset：把 2 MB HTML 变成一个坐标空间

上一幕说「必须给坐标」。但一份 SEC HTML 里没有坐标——只有嵌套的 <table> 和大量 rowspan/colspan。第 28 行第 15 列这个说法在合并单元格的世界里是有歧义的。

这一幕要替换的误解是：「先把相关的表挑出来再给模型看」。build_table_grid() 的签名里没有任何过滤参数，docstring 写死了 "No metric terms or filter parameters are accepted by this API." 代码——因为一旦允许按关键词筛表，「模型从完整文档里选对了表」就不再是一个能成立的结论。

每个格子同时拥有两个文本字段

这一对差异是后面全部戏剧性的来源
这一幕建立的事实

任意 (table_id, row_index, column_index) 要么唯一解析到一个格子，要么越界报错——而且这个解析过程只依赖原始字节。同一份 HTML 重建一万次，derived_asset_id 完全相同。

第 2 幕 · 消除一个新风险

往返验证：模型看到的表 = Evidence 重读的表

展开后的网格有 3 554 243 字节 实测，其中 55.23% 是合并格的副本。直接塞给模型是纯浪费，所以要压缩。

但压缩引入了一个全新的风险：模型看到的表和 Evidence 重读的表可能不是同一套。如果这个风险不消掉，后面「系统回去重读」这句话就没有意义——它读的可能是另一个世界。

编码 → 解码 → 逐字段相等

table_payload.py:265 / 308-310
expanded canonical JSON3 554 243 B→331 877 B（9.34%）实测

只编码原点格，每个压成一个位置数组 [row, col, rowspan, colspan, header, raw_text, text]，加上表的形状。解码器靠 span 把副本重新展开。

decoded = decode_compact_table_payload(transport=transport)
if decoded != tables:
    raise TablePayloadError("Compact table round trip differs")

注意这是 !=，不是比 hash。同一个不变量在三个不同的信任边界上各验一次：编码函数自己验（实现正确）、build_reader_payload 再验（载荷没被中途替换）、check_evidence 第三次验（复核用的和发出去的是同一套）。

这一幕建立的事实

「模型看到的内容和 Evidence 重读的内容一致」不是「差不多一致」，是解码回来后 Python == 逐字段相等。新增的绑定字段：expanded_derived_asset_id、expanded_grid_sha256、compact_payload_sha256、round_trip_receipt_id。

第 3 幕 · 唯一有外部副作用的地方

先落 marker，再开 socket

这一幕揭示一个从对象上看不见的状态：「远端到底执行了没有」。付费模型调用最危险的情况不是报错，而是请求可能已经发出、本地却不知道结果。

第 4 幕 · 模型的主张进场

ObservationCandidate：结构合法，内容一个字都没验

这是第一个承载模型输出的对象。它代表的事实是：模型声称这些坐标上有这些内容。它不代表这些内容是真的。

要替换的误解是：「JSON 校验通过了，说明模型答对了」。validate_reader_output() 做的是极严的结构校验——根字段必须恰好四个、candidate 字段必须恰好八个、角色顺序必须与 Spec 完全一致、所有 locator 必须落在同一张目标表内。但它一次都没有去看那张表。

第 5 幕 · 全场中心 · 可扰动

EvidenceCheck：系统自己回去读一遍

这是整条链路里唯一一个「凭什么信」的对象。前面的 Candidate 只是模型的说法，后面的 Review 只处理语义，中间这一层是唯一的机械真值判定。

第 7 幕 · 语义授权

Review 与 VerifiedObservation：谁为口径负责

要替换的误解是：「Evidence PASS 就等于这个数字对了」。不等于。Evidence 只能证明「你指的位置上确实写着这些字」；「可比全系统口径是不是业务要的那个口径」它不判断，也不假装能判断。

check_evidence 的 docstring 用的词是 "the asymmetric mechanical Evidence Checker" 代码——它能证伪，不能证实。证伪可以机械化，证实不能。

第 8 幕 · 通过的范围

live_ready = true 到底说了什么

当前 freeze receipt 写着 live_ready_family_ids = ["lodging_kpi_table"] 落盘。一个不了解背景的人会自然地把它读成「模型读酒店 KPI 表这件事已经验证过了」。

这是全篇最重要、也最容易被误读的一句。下面是仓库里全部 15 次真实调用的逐条结果——不是抽样，是全部。

4 个 prompt 版本 × 3 家发行人 × 15 次真实调用

qualification 样本被换过两次

落盘 git 历史（本地 clone 为 shallow，只覆盖这 3 个提交）

context 门的 PASSED 是一次豁免

这一幕建立的事实

live_ready = true 的准确含义是：在 Marriott 这一家公司的三个财年上，用当前 prompt，两个 task 的机械证据链完整。它不支持「模型能读任意酒店集团的 KPI 表」——跨发行人 7 次尝试 0 次成功。

公平地说：这不是隐瞒。fixture id、判据、每一次失败的 Run 全部完整落盘且内容寻址，任何人都能查出来。但只画「通过」不画「在谁身上通过」，就是在误导。
