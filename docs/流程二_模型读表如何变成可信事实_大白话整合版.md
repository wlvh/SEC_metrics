# 流程二：模型读表如何变成可信事实

## 大白话整合版

> **核对基线**：`wlvh/SEC_metrics` 分支 `agent/issue-15-final-delivery`，当前 HEAD `5d2a9ff7e52e70571164444adf293111e715ed9e`。
>
> **本文目的**：不按文件和函数讲代码，而是说明一条模型读出来的数字，为什么不能直接相信，以及系统怎样一步步把它变成可以计算、可以追责、可以重放的事实。
>
> **当前状态先说明**：系统已经实现并实际跑通过这条机制，也保存过真实成功和失败样本；但最新分支已经切换到一个新的干净资格周期。这个新周期目前只是准备条件通过，尚未产生新的模型调用和 Run。正式对外版本仍然是 zero-AI R2，AI 表格结果还没有进入 active publication。

## 一、先说结论

这套系统最核心的原则只有一句：

> **模型只负责指出“答案可能在哪一格”，系统自己回到原始 SEC 表格里检查；检查通过、审核批准、整条链可以重放以后，这个数字才有资格成为事实。**

所以系统走的不是：

```text
模型说 69.8% → 数据库保存 69.8%
```

而是：

```text
原始 SEC 文件
→ 完整表格坐标
→ 模型提交“哪张表、哪一格、什么口径”的候选
→ 程序按坐标重新读表
→ 审核完整证据包
→ 生成 VerifiedObservation
→ 生成指标结果和计算轨迹
→ 从原始文件重放整条链
→ 通过资格认证后，才可能进入正式发布
```

模型不是事实生产者，更像一个**指路的人**。它可以说“我认为答案在这里”，但不能自己给自己盖章。

## 二、为什么不能直接相信模型读出来的数字

酒店年报里可能同时出现很多看起来很像的数字：

- 2024 年和 2023 年；
- Worldwide 和不同地区；
- Systemwide 和 Company-operated；
- Comparable properties 和全部物业；
- 绝对入住率和同比变化；
- 标题相似但口径不同的多张表。

模型回答“69.8%”时，至少有以下几种可能：

1. 真正读到了正确格；
2. 读对了表，但抄错数字；
3. 读成上一年度；
4. 读成另一种经营口径；
5. 数字本身存在，但来自另一张表；
6. 根本没有从本次文件里读，而是凭训练数据或上下文猜出来。

这些情况在最终回答里都可能长得一样。

要求模型“解释理由”也不能解决问题，因为答案和理由仍然都由同一个模型生成。真正可验证的办法，是让模型给出**坐标**，然后由程序自己去核对坐标里的内容。

---

## 三、系统里的角色怎么分工

为了避免“提答案的人同时负责证明答案”，系统把权力拆开了。

| 角色 | 大白话解释 | 有什么权力 | 没有什么权力 |
|---|---|---|---|
| 模型 | 找答案的人 | 提交候选表、候选格、原文、口径标签 | 不能直接写正式指标 |
| Reader | 收申请单的人 | 检查模型输出是不是严格、完整、可定位 | 不查表、不纠错 |
| Evidence Checker | 查原件的人 | 按坐标重读原始表格，给出 PASS 或 REJECTED | 不替模型寻找另一个答案 |
| Review | 批准证据包的人或受控 SYSTEM | 批准或拒绝完整语义包 | 不能覆盖 Evidence 失败，也不能顺手改值 |
| Calculator | 算结果的人 | 只消费已经批准的标准化事实 | 不理解模型自然语言 |
| Run replay | 复盘审计的人 | 从原始字节重新建表、重跑核对和计算 | 不相信已经落盘的 PASS |
| Qualification / Publication | 决定能否正式使用的人 | 检查跨样本稳定性并控制正式切换 | 不会因为一次成功就自动上线 |

这里最重要的是：

> **模型负责选择，程序负责验证，Review 负责授权。三种权力不能合并。**

## 四、一条数字是怎样一步步变成事实的

### 第 1 步：先锁定到底在读哪份 SEC 文件

系统接收的不是一段随便传进来的 HTML，而是一份已经绑定好的材料：

- 哪家公司；
- 哪个 fiscal year；
- 哪个 accession；
- 哪个 document；
- 原始文件的 SHA-256；
- 文件大小；
- 对应哪次不可变请求记录；
- 本次要执行哪个表格任务和指标口径。

这一步解决的是：

> **我们读的到底是不是那份被批准的年报，而不是另一个同名文件、临时文件或被修改过的文件。**

只要 source、hash、accession、document 或请求记录对不上，流程会在调用模型之前停止。

---

### 第 2 步：把整份 HTML 变成稳定的表格坐标系

HTML 表格不是天然的 Excel。它有 `rowspan`、`colspan`、空白、脚注、隐藏的换行和不规则结构。

系统会把文件里的**所有表格**按原始顺序解析成矩形网格，并给每一个逻辑单元格固定地址：

```text
table_id + row + column + origin + rowspan + colspan
```

例如：

```text
table_000011，第 28 行，第 15 列
```

不只是“第几行第几列”，还要说明这个格子的原点和合并范围。这样模型不能随便编一个看起来合理的坐标。

系统在这里有一个很强的选择：

> **不按关键词筛表，不只发送“最相关的几张表”，而是保留完整表集合。**

好处是不会因为前置筛选器漏掉正确表，也能证明模型和验证器看到的是同一份材料。代价是 token 和内存都很贵，这也是 financial family 当前被资源上限挡住的主要原因。

---

### 第 3 步：压缩表示，但不能删掉业务内容

完整展开后的表格有很多合并格副本，直接发送很浪费。系统会把它压成更紧凑的格式。

但这里的“压缩”只能去掉重复表示，不能：

- 删除某张表；
- 改变表格顺序；
- 删除某个单元格；
- 按指标词做筛选；
- 先替模型选中目标表。

压缩后必须当场解码，并逐字段还原成原来的完整网格。还原不一致，就在出网前失败。

因此下游可以相信：

> **模型看到的紧凑表格，和 Evidence 后来重新读取的完整表格，是同一个事实世界。**

---

### 第 4 步：先登记“可能要出网”，再真正调用模型

模型调用会付费，而且可能发生一种麻烦情况：请求已经发出，但本地进程在收到响应前崩溃。

系统因此采用以下顺序：

```text
固定请求身份
→ 抢占唯一 reservation
→ 写入 egress marker
→ 才允许打开 socket
```

这样做是为了区分：

- **确定还没出网**：可以安全恢复；
- **可能已经出网**：不能假装没发生，也不能盲目再发一次。

同一个精确请求同时只能有一个执行者。第二个执行者要么复用已经被验证过的成功响应，要么看到 `SINGLE_FLIGHT_HELD`，不能重复调用。

如果 egress marker 已经存在，但远端最终结果无法确认，系统记录：

```text
UNKNOWN_REMOTE_OUTCOME
```

并停止，而不是自动重试。因为重试可能造成两次扣费和两个无法唯一归属的答案。

---

### 第 5 步：模型提交的不是答案，而是一张“候选事实申请单”

模型必须返回严格 JSON，内容至少包括：

- 选中了哪张表；
- 指标角色是什么，例如 `occupancy`；
- 报告期间；
- 原始数字文字；
- 报告单位；
- 精确单元格坐标；
- 支持 scope 的同表标签坐标；
- 其他竞争候选；
- 尚未解决的冲突。

Reader 会检查：

- JSON 是否严格；
- 是否有多余或缺失字段；
- role 是否正好等于任务要求，且顺序一致；
- 所有 locator 是否都留在模型选中的同一张表；
- 是否引用了本次没有提供的资产；
- competing 和 unresolved 是否被完整保留。

通过以后才创建：

```text
ObservationCandidate
```

它的普通含义是：

> **模型确实以规定格式声称“答案在这里”。**

它仍然不是事实。此时系统甚至还没有确认那个坐标里真的写着模型声称的数字。

---

### 第 6 步：Evidence 按模型给的坐标重新读表

这是整条链最关键的一步。

Evidence Checker 会重新检查：

1. Candidate 是否绑定本次正确 source；
2. 模型看到的表格集合是否完整、顺序是否一致；
3. 指定 locator 是否真实存在；
4. locator 的 origin、rowspan、colspan 是否一致；
5. 该格的文本是否等于模型声称的值；
6. competing candidate 的坐标是否也能重读；
7. scope 标签是否来自同一张目标表；
8. scope 原文是否真实存在；
9. scope 是否只能通过 MetricSpec 声明的精确别名变成标准口径；
10. Spec 声明的恒等关系是否成立。

Evidence 的原则是：

> **只检查模型指定的格，不搜索替代答案。**

假如模型指错了格，即使文件其他地方真的有同一个数字，也会失败。否则系统就无法分清：到底是模型选对了，还是验证器替模型把答案修好了。

Evidence 的结果只有两类核心含义：

```text
PASS      = 本地材料机械支持这个主张
REJECTED  = 这个主张无法由指定材料证明
```

还可能出现一种“机械证据没有被否定，但语义仍需人决定”的情况。此时 Evidence 整体可以是 PASS，不过 Candidate / scope 检查会标成：

```text
REVIEW_REQUIRED
```

例如原始标签真实存在，但不在 Spec 的精确口径别名表里。系统不会猜，也不会允许 SYSTEM 自动批准，而是把剩余判断交还给人。

---

### 第 7 步：Review 批准的是完整证据包，不是一个孤立数字

即使 Evidence PASS，也只说明“表格里确实这样写”。它还没有回答：

> **这组口径是否被允许成为业务计算输入？**

所以系统会建立一个完整的 ReviewUnit，把以下内容一起锁定：

- 模型选中的主张；
- 竞争候选；
- 未决问题；
- source；
- MetricSpec；
- Evidence 结果；
- 完整目标表；
- 实际渲染给 reviewer 看的字节。

Review 有两条合法路径：

- 具名 `HUMAN` 批准或拒绝；
- 在 D-06 明确授权、Evidence 已经完整闭合时，由固定身份的 `SYSTEM` 批准。

这里的 SYSTEM 不是第二个模型，也不会冒充人。它只是根据固定规则，把“没有剩余语义争议的证据包”做成一条可审计批准记录。

Review 不能：

- 修改模型原值；
- 把错误 locator 换成正确 locator；
- 覆盖 Evidence REJECTED；
- 只批准主答案却忽略竞争项；
- 在上下文变化后继续复用旧决定。

---

### 第 8 步：批准以后，才创建 VerifiedObservation

这是整条链第一次产生可以叫“可信事实”的对象。

`VerifiedObservation` 不是把模型 JSON 原样复制下来。它重新组合了不同权威来源：

| 字段 | 真正来源 |
|---|---|
| 公司和期间 | Run authority |
| metric 和 role | MetricSpec / task contract |
| 数值 | Evidence 重新读取并标准化后的值 |
| 规范单位 | MetricSpec |
| scope | 有效 ReviewDecision 批准的标准口径 |
| source 和 locator | 原始 SourceReference + Candidate 精确坐标 |
| approval effect | 当前有效 ReviewDecision |

因此，模型说的原始字符串不会直接进入指标结果。

例如：

```text
模型声称：69.8 percent
Evidence 重读并标准化：0.698 ratio
Review 批准：worldwide / systemwide / comparable
最终 Observation：B10 = 0.698 ratio
```

---

### 第 9 步：Calculator 只消费已经批准的事实

Calculator 不再理解模型的自然语言，也不再查表。它只拿 `VerifiedObservation` 做确定性投影或计算，产生：

```text
MetricResult + ExecutionTrace
```

- `MetricResult` 是最终指标值；
- `ExecutionTrace` 说明这个结果消费了哪条 Observation、走了什么公式或投影。

如果 Review REJECT，系统不会假装“没有结果”，而会形成明确的 `WITHHELD` 终态，说明结果为什么被扣留。

---

### 第 10 步：Run freeze 不是验 hash，而是从头重演

只看 hash 不够安全。因为有人可以同时修改 Candidate、Evidence、Observation、Result，再把所有 hash 一起重算，做出一套内部自洽的假链。

因此 Run freeze 会重新：

1. 读取原始 SEC 字节；
2. 重建完整表格网格；
3. 重建发送给模型的请求；
4. 从保存的 assistant 原始响应重新创建 Candidate；
5. 重新运行 Evidence；
6. 重新验证 Review 绑定；
7. 重新创建 Observation；
8. 重新计算 Result 和 Trace；
9. 检查整套对象有没有多、少、悬空或被替换。

在正常成功路径中，全部一致、正式结果集合也完整以后，Run 才通过 validation 并从 `OPEN` 变成 `FROZEN`。

所以：

> **FROZEN 的核心含义不是“文件没变”，而是“这组落盘对象已经成为不可变终态，并且能按其适用规则机械重验”。**

还要注意一个容易忽略的细节：代码也允许把某些完整的失败或 `NOT_RUN` 状态冻结下来，目的是保留不可变审计记录。这种 audit-only FROZEN 不等于业务成功，也拿不到 qualification 或 publication credit。

因此，判断一个 Run 是否可用于资格认证，不能只看 `FROZEN`，还要同时看 validation、Review、Result 状态和 qualification terminal。

## 五、用 Marriott FY2024 入住率走一遍正常路径

历史真实成功样本可以简化为：

```text
Marriott FY2024 10-K
→ 解析出完整表格集合
→ 模型选择 table_000011
→ 指向 row 28 / column 15
→ 声称原文是 69.8，单位 percent
→ 同表标签支持 Comparable + Systemwide + Worldwide
→ Evidence 重新读到同一格和同一标签
→ 69.8 percent 标准化为 0.698 ratio
→ SYSTEM 在 D-06 授权下批准完整证据包
→ 生成 B10 VerifiedObservation
→ Calculator 生成 B10 = 0.698 ratio
→ Run 重放通过并 FROZEN
```

这里真正有价值的不是“模型读出了 69.8”，而是：

> **系统能够证明，69.8 来自被批准的 SEC 文件、被指定的表和格、被指定的期间与口径，并且事后可以完整重放。**

## 六、最重要的历史失败：只差一个换行符，也不能放过

历史上有一次真实调用：

- HTTP 200；
- JSON 结构合法；
- 表选对了；
- 格选对了；
- 数字 69.8 也读对了；
- 唯一差异是 scope 标签的前导换行。

模型返回：

```text
Worldwide (2)
```

原始表格保存的是：

```text
\nWorldwide (2)
```

当时的契约要求 scope 标签 `raw_text` 逐字相等，因此 Evidence 返回：

```text
SCOPE_LABEL_TEXT_MISMATCH
→ EVIDENCE_FAILURE
```

后面的 Review、Observation、Result、freeze 全部没有发生，active publication 也没有受影响。

这件事说明系统做对了两件事：

1. 没把 HTTP 200 当成业务成功；
2. 没让验证器偷偷 `trim()`，制造一个没有版本记录的例外。

它也暴露了一个真实问题：

> **让模型复述不可见的原始空白很脆弱，一次业务上完全正确的调用可能因为 HTML 排版字符失败。**

项目后来的处理不是放宽 Evidence，而是修改并冻结 prompt，明确要求模型保留首尾空白并用 JSON escape 表示。后续样本已经证明该修订可以成功。

长期更稳的方向，是把“允许怎样处理空白”设计成一个明确、有版本、可测试的 normalization contract，而不是依赖临时 `strip()`，也不是永远把所有负担推给模型。

## 七、下面这些“成功”绝对不能混在一起

| 状态 | 它只证明什么 | 它还没有证明什么 |
|---|---|---|
| HTTP 200 | provider 返回了响应 | 内容正确 |
| Schema valid | JSON 结构符合要求 | 坐标和值真实 |
| Evidence PASS | 指定本地材料支持 Candidate | 业务语义已获准 |
| Review APPROVE | 完整证据包得到有效授权 | Run 可重放 |
| Run FROZEN | Run 已成为不可变、可重验终态；可能是成功，也可能只是失败审计 | 获得 qualification credit，更不等于模型跨样本稳定 |
| Family QUALIFIED | 规定的布局、holdout、fresh 序列完成 | 已切换正式版本 |
| Active PUBLISHED | 发布事务完成，active pointer 已切换 | 未来永不漂移 |

最容易犯的错误，是把前面某一层的成功，越级解释成后面一层的成功。

## 八、为什么系统故意这么严格

### 1. 为什么不先筛几张最相关的表

因为筛选器一旦漏表，模型根本没有机会找到正确答案。更麻烦的是，系统事后无法证明“没被筛掉的表里已经包含全部相关证据”。

当前方案优先保证完整性，代价是更高的 token 和内存成本。

### 2. 为什么 Evidence 不替模型修错格

因为同一个数字可能出现在不同年度、不同地区、不同经营范围或另一张表里。验证器搜索到“另一个能对上的格”以后，表面结果可能正确，但模型实际选错这件事就被隐藏了。

错误应该产生新的模型响应和新的 Candidate，而不是修改旧 Candidate。

### 3. 为什么不用第二个模型审核第一个模型

第二个模型仍然是概率系统，只是把信任问题往后推了一层。当前 Evidence 是确定性程序，同样输入得到同样结果，可以离线测试和重放。

模型可以辅助人理解证据，但不能代替原始 source proof。

### 4. 为什么远端结果不确定时不自动重试

因为“请求失败”和“远端可能已经执行、只是本地没收到结果”不是同一回事。后一种情况自动重试可能产生重复收费和两个答案。

### 5. 为什么 freeze 要重做一遍，而不是只验 hash

因为 hash 只能证明内容身份，不能证明对象之间的关系是真的。重放才能证明 Result 确实来自 Observation，Observation 确实来自 Evidence，Evidence 确实来自原始 SEC 字节。

## 九、当前分支现在到底走到哪一步

截至当前 HEAD `5d2a9ff`，必须把“历史证据”和“当前周期进度”分开看。

### 1. 历史上已经证明过什么

以前的 qualification cycles 中已经存在：

- 真实 provider 调用；
- Schema 和 Evidence 失败样本；
- Marriott Occupancy / RevPAR 成功样本；

所以这条链不是纸面设计，也不是只有 mock 的 demo。

```text

```

这个周期当前目录中只有一个 0 字节的：

```text
provider_ledger.jsonl
```

没有新的 Run，也没有新的 provider 调用。这表示项目把当前 authority、freeze 和 Stage-A 重新绑定后，从一个干净周期重新开始记录，而不是把旧周期的 Run 数量直接继承为新周期进度。

### 3. `lodging live_ready = true` 到底是什么意思

当前 freeze receipt 显示 lodging family 的：

- context gate：PASS；
- resource gate：PASS；
- protected closure gate：PASS；
- 两个 task request 都 ready；
- `live_ready = true`。

它的准确含义是：

> **现在具备按当前冻结契约开始受控 live qualification 的前置条件。**

它不等于：

- 当前新周期已经执行过模型；
- qualification 已经完成；
- AI 结果已经发布。

### 4. 当前 lodging 资格范围也不能被夸大

当前 matrix 测的是 Marriott 同一发行人的多个财年和不同布局：

- development：FY2025；
- second layout：FY2024；
- holdout：FY2023；
- Occupancy 和 RevPAR 两个任务；
- 还要求 3 轮 fresh samples。

因此即使这一序列最终完成，它首先证明的是：

> **当前冻结方案在 Marriott 多年度、不同布局上的稳定性。**

它不能自动外推成“能稳定读取任意酒店集团”。历史上 Hilton、Hyatt 的跨发行人尝试没有形成成功证据，这个泛化问题仍然存在。

### 5. financial family 仍然卡在哪里

financial family 当前不是模型质量不行，而是在模型调用之前就被阻断：

```text
EXPANDED_GRID_RESOURCE_LIMIT
```

原因是大型金融年报展开所有 rowspan / colspan 后，完整矩形网格超过当前资源上限。

正确的长期方向不是偷偷删表或提高上限，而是设计惰性、无损的逻辑网格：只保存原点格和 span map，查询坐标时再解析，同时保持所有 locator 与旧语义一致。

### 6. 正式对外版本是什么

当前 active pointer 仍指向：

```text
publication_fe01e227...
```

它是 2026 年 8 月 20 日提交的 zero-AI R2。当前 AI 表格 qualification 证据尚未进入 active publication。

## 十、当前系统最值得肯定的地方

### 1. 它没有要求“模型永远正确”

系统接受模型会出错，但把错误限制在 Candidate 层，不能直接污染业务结果。

### 2. 每一种失败都有不同含义

`SCHEMA_VIOLATION`、`EVIDENCE_FAILURE`、`REVIEW_REQUIRED`、`UNKNOWN_REMOTE_OUTCOME`、`WITHHELD`、qualification incomplete，不会被一个模糊的 `success=false` 混在一起。

### 3. 失败不会覆盖旧的正式版本

最新 AI attempt 失败，active zero-AI R2 继续服务。失败证据被保留，但不会自动污染正式矩阵。

### 4. 它同时约束模型、人工和系统自动化

模型不能自签；Evidence 不能修答案；reviewer 不能改值；SYSTEM 不能冒充人；落盘对象不能靠重算 hash 自证。

---

## 十一、下一步最值得做什么

### P0：把“当前进度”做成不会误导人的状态页

至少分开显示：

```text
EGRESS_READY
SAMPLE_FROZEN
FAMILY_QUALIFIED
PUBLISHED
```

现在的 `live_ready` 太容易被读成“已经通过”。

### P0：完成当前 clean cycle，而不是继续引用旧周期的成功数量

按当前冻结的 prompt、schema、serializer、Evidence、Spec 和 source authority，依次完成：

```text
SECOND_LAYOUT
→ PRODUCTION SEMANTIC FREEZE
→ HOLDOUT
→ FRESH 1 / 2 / 3
```

Occupancy 和 RevPAR 两个 task 都必须完成。序列中间不能悄悄修改语义契约；一旦改动，应启动新的 freeze / cycle。

### P1：让失败原因直接可见

现在 invocation 顶层经常只看到 `SCHEMA_VIOLATION` 或 `EVIDENCE_FAILURE`。应增加只读、不可晋升的详细失败收据，直接保存：

- 哪个字段不合法；
- 哪个 locator 失败；
- 是值不等、scope 文本不等，还是别名缺失；
- 使用了哪个 Evidence 版本。

失败收据只能用于诊断，不能提供 qualification credit。

### P1：把空白处理变成版本化合同

保留 exact raw source，同时明确规定 model-facing 文本允许哪些有限变换。任何变换都要：

- 穷举；
- 有版本号；
- 可测试；
- 可重放；
- 变更后重新 qualification。

不能把一个随手的 `.strip()` 当修复。

### P1：为 financial family 做惰性、无损网格

目标是减少合并格副本的内存物化，而不是删除表。新旧实现必须在每个逻辑坐标上返回完全相同的 cell、origin 和 span。

### P1：显式记录资格证明的适用范围

资格收据不只应写 `PASS`，还应说明：

- 覆盖了几个发行人；
- 覆盖了哪些财年和布局；
- 是 same-issuer 还是 cross-issuer；
- 哪些泛化边界还没有被证明。

## 十二、最容易记住的版本

### 30 秒版

SEC 年报里的酒店指标没有 XBRL 标签，只能让模型读普通 HTML 表。系统不相信模型直接给出的数字，而是要求它返回表格和单元格坐标。程序再回到同一份 SEC 文件，按坐标重读数字和口径标签；对不上就拒绝，绝不替模型找另一个格。证据通过后，完整证据包还要由人或被明确授权的 SYSTEM 批准，才会生成 `VerifiedObservation`。最后 Run 从原始字节把整条链重演一遍。单个 FROZEN Run、家族资格完成和正式发布，仍然是三个不同状态。

### 一句话版

> **模型只指路，程序自己走过去看；看见的内容、口径、批准和重放全部闭合后，才把候选升级成事实。**

## 事实核对说明

可以拆成两个维度理解：

| 维度           | 当前做法                                                     |
| ------------ | -------------------------------------------------------- |
| 模型调用粒度       | 一个公司、一个期间、一个指标任务，单独调用一次                                  |
| 每次调用读取的材料    | 该公司对应 SEC filing 的完整表格集合，原顺序、无关键词预筛                      |
| 模型输出         | 通常只返回一个指标角色的候选值与精确坐标                                     |
| 最终事实         | 每个指标分别形成自己的 Candidate、Evidence、Review、Observation、Result |
| 是否一次提取公司全部指标 | **不是**                                                   |

## 以 Marriott 为例

目前 lodging family 有两个独立任务：

```text
lodging_occupancy_table_v2 → B10 Occupancy
lodging_revpar_table_v2    → B11 RevPAR
```

所以系统的实际执行方式是：

```text
Marriott FY2025 SEC HTML
    ├─ Occupancy 任务
    │    └─ 单独调用模型
    │         └─ 输出 occupancy 的表、行、列、值、scope
    │
    └─ RevPAR 任务
         └─ 另一次模型调用
              └─ 输出 revpar 的表、行、列、值、scope
```

当前 task catalog 已经把 Occupancy 和 RevPAR 拆成单角色任务；不是一次让模型同时返回 Occupancy、RevPAR、ADR。

financial family 也是类似的。目前配置里是八个独立任务，例如：

```text
assets under management
capacity utilization
debt to equity
geographic exposure
liquidity coverage ratio
net interest margin
nonperforming loan ratio
value at risk
```

也就是理论执行粒度为：

```text
JPMorgan × AUM       → 一次任务
JPMorgan × NIM       → 一次任务
JPMorgan × NPL ratio → 一次任务
JPMorgan × VaR       → 一次任务
……
```

当前 catalog 总计是 **8 个 financial 单指标任务 + 2 个 lodging 单指标任务**；Occupancy 任务的 `required_roles` 只有 `["occupancy"]`。

---

## 但“单指标抽取”不等于“只把指标附近的内容发给模型”

以 Marriott Occupancy 为例，系统不会先搜索“occupancy”关键词，再截出一张相关表。

它会：

```text
整份 Marriott SEC HTML
→ 解析其中全部表格
→ 保留全部表、原始顺序
→ 无损压缩
→ 全部交给 Occupancy Reader
→ 让模型自己选择目标表和目标格
```

然后 RevPAR 任务又会拿同一份完整表格集合，执行另一次独立调用。

这是当前架构里一个很明显的成本：

> **每个单指标任务都会重复携带完整文档 payload。**

文档也明确总结了这个取舍：单角色任务获得了独立 qualification、更小的输出 Schema 和更窄的失败范围，但代价是每个 task 重复传输完整文档，而且失去了同一次响应里的跨指标一致性检查。

---

## 为什么不一次把一个公司的所有指标全部抽出来

当前设计主要是在换取四个东西。

### 1. 一个指标失败，不拖死其他指标

假设让模型一次返回：

```text
Occupancy + RevPAR + ADR
```

只要 ADR 的字段格式错了、坐标错了，整个响应可能都无法通过严格 Schema 或 Evidence。

拆开后：

```text
Occupancy 成功 → Occupancy 可以形成独立 Run 证据
RevPAR 失败    → 只影响 RevPAR
```

失败域明显更小。

### 2. 每个指标可以独立做资格认证

系统的 qualification 是按 task 记录的。

例如在每个阶段，都要求分别存在：

```text
SECOND_LAYOUT:
    Occupancy
    RevPAR

POST_FREEZE_HOLDOUT:
    Occupancy
    RevPAR

FRESH_STABILITY 1:
    Occupancy
    RevPAR
```

也就是说，不能因为 Occupancy 稳定，就顺便宣称 RevPAR 也稳定。当前资格序列明确把两个 task 分开要求。

### 3. Prompt、Schema、scope contract 更简单

Occupancy 只需要回答：

```text
role = occupancy
value
unit
period
locator
scope evidence
```

而不用同时处理多个角色之间的字段、竞争候选和单位差异。

这会减少一个响应内部互相污染的可能性。

### 4. 每个指标的审计链更清楚

每个指标单独拥有：

```text
TaskContract
→ Provider Request
→ Assistant Response
→ ObservationCandidate
→ EvidenceCheck
→ ReviewDecision
→ VerifiedObservation
→ MetricResult
```

出现问题时，可以准确说：

```text
Marriott FY2025 Occupancy 成功
Marriott FY2025 RevPAR Schema 失败
```

而不是只能说“Marriott 这次批量抽取部分失败”。

---

## 它的代价也很明显

假设一家公司有 8 个 AI 表格指标，而整份 filing 的模型输入约 160,000 tokens。

当前单任务模式理论上可能变成：

```text
8 个指标 × 160,000 tokens
≈ 1,280,000 input tokens
```

即使 8 个指标都来自同一份 SEC 文件，也会重复发送大体相同的完整表格材料。

而且存在另一个问题：**各指标分别抽取成功，不自动证明它们彼此一致。**

例如：

```text
Occupancy 从表 A 抽出
RevPAR 从表 B 抽出
```

两者可能：

* scope 不同；
* 一个是 comparable，一个是 all properties；
* 一个是 systemwide，一个是 company-operated；
* 一个使用全球口径，另一个使用区域口径；
* 甚至来自不同目标表。

历史上的多角色 Reader 可以在一次响应里检查：

```text
ADR × Occupancy ≈ RevPAR
```

现在拆成独立任务后，这种跨指标一致性不再天然存在，需要后续单独增加 deterministic reconciliation。文档也把这一点列为后续改进方向。

---

## 更准确的一句话

当前系统不是：

```text
一家公司 → 一次模型调用 → 抽出全部指标
```

也不是：

```text
一个指标 → 只截取一小段相关 raw data → 调模型
```

而是：

```text
一家公司的一份 SEC filing
→ 建立完整表格坐标系
→ 针对每个指标分别建立独立 task
→ 每个 task 都读取完整表格集合
→ 每个指标分别完成 Candidate / Evidence / Review / Result
```

因此，**调用和验证是按指标拆分的，原始材料视图却是按整份公司 filing 提供的。**

从架构取舍上看，它目前明显偏向：

```text
审计隔离、失败隔离、资格隔离
>
token 成本、调用次数和跨指标联合抽取效率
```
