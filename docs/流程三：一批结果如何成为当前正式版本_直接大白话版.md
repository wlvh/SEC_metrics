# 流程三：一批结果如何成为当前正式版本

> **直接 / 简单 / 大白话版**
>
> 核对基线：`wlvh/SEC_metrics` 分支 `agent/issue-15-final-delivery`，当前 HEAD `5d2a9ff7e52e70571164444adf293111e715ed9e`。
>
> 本文整合三份既有模块文档，并重新核对当前 `publication.py`、active pointer、active bundle、validation manifest、zero-AI receipt 和 switch history。
> 它解释的是“结果怎样正式生效”，不是“指标怎样算出来”。

---

## 一句话先讲明白

这个模块不把十几个新文件直接覆盖到正式目录。

它先把整批结果装进一个**完整、封口、以后不能改的版本包**，然后只做一件真正改变正式状态的事：

> **把“当前版本指针”从旧包切到新包。**

所以：

- 新包已经做好，**不等于**已经发布；
- 指针没有切，新失败再多，正式世界仍是旧版；
- 指针切换时有并发或崩溃，系统能明确判断应恢复旧版还是完成新版；
- 下游不是到处找“最新文件”，而是先锁定一个正式版本，再只读这一版。

可以把整个设计理解成四样东西：

```text
点名册：这批结果是不是一个不少、一个不重
封口箱：这一版到底包含哪些固定字节
路标和账本：此刻哪一版正式，以及它怎样成为正式
快照票：下游一次任务只读同一个版本
```

---

## 一、为什么“所有文件都算好了”仍然不等于正式版本

假设十家公司的指标都已经算出，矩阵、证据表、覆盖率、报告和校验文件也都生成了。看起来只要复制到 `outputs/` 就结束了。

问题是，下游消费的不是十几个彼此独立的文件，而是**同一个版本的一整套事实**。

直接覆盖会产生几类很危险、但单看文件格式又发现不了的问题。

### 1. 半新半旧

程序先写了新的 `metrics_matrix.csv`，还没写新的 `coverage_matrix.csv` 就崩了。两个文件分别都合法，但它们来自不同版本。下游读到的是一套历史上从未真正存在过的组合。

### 2. 局部完成冒充整批完成

十家公司只完成九家，或者二十二个指标少了一个。若只判断“目录里有结果”，缺失就可能被误当成业务空值。

### 3. 两个人互相覆盖

A、B 都基于旧版准备新结果，同时开始发布。没有锁和前驱检查时，最终可能是 A 的矩阵、B 的证据、A 的报告。

### 4. 新版本有问题却退不回去

旧文件已经被覆盖，所谓回滚只能靠手工备份或重跑旧代码。重跑后的结果未必还和当年一样。

### 5. 文件存在，却不知道是不是正式的

`outputs/publications/` 里可以同时有多个完整候选包。目录更新时间最新、名字最新、文件最齐，都不代表它被正式采用。

### 6. 读到一半发生切换

下游先读矩阵，版本随后切换，再读证据表。若没有“固定版本”的读取方式，一次分析会混入两个世界。

因此，这一层真正解决的不是“怎么写文件”，而是：

> **如何把一批已经成立的结果，升级为一个完整版本；再用一个唯一、可恢复、可审计的动作，宣布它从此是当前正式版本。**

## 二、先分清六种状态

这是理解整个模块最重要的一步。

```text
局部结果已经算出
≠ 整批结果完整

整批结果完整
≠ 候选允许发布

候选允许发布（PUBLISHABLE）
≠ 不可变版本包已经做好（PREPARED）

版本包已经做好
≠ 当前正式版本（ACTIVE）

当前正式版本
≠ Issue #15 全量验收已经完成
```

六种状态分别回答不同问题：

| 状态 | 它只证明什么 |
|---|---|
| 局部结果完成 | 某次 Run 或某个坐标自己的证据链成立 |
| 批次完整 | 本次要求的公司 × 指标一个不少、一个不重 |
| `PUBLISHABLE` | 当前规则允许把候选装成正式版本包 |
| `PREPARED` | 一个完整、不可变、可验证的新包已经存在 |
| `ACTIVE` | 指针已经通过合法事务切到这个包 |
| full acceptance | 更高层完整 Cutover、终态循环和正式验收全部通过 |

系统故意不把这些状态合并，因为很多事故正是从“差不多算完成了”开始的。

## 三、四个关键角色

### 角色一：批次权威——先点名，证明一个不少、一个不重

普通路径使用 `BatchManifest`；当前 R2 使用专用的 `ZERO_AI_COORDINATE_INDEX`。两者格式不同，但责任相同：

> **从仓库声明的公司、指标、适用性和期间反推“本来应该有哪些结果”，再确认实际结果与之精确相等。**

它不是看行数大致对不对，而是检查每一个 `(company_id, metric_id)` 坐标：

- 缺一个，不行；
- 多一个，不行；
- 同一个坐标出现两次，不行；
- 不同财年混在一批，不行；
- 本来不适用的指标也必须明确留下 `N_A_STRUCTURAL`，不能靠缺行表达；
- 本来适用却证据不足的 `WITHHELD`，不能伪装成正常空值。

当前 R2 的真实批次是：

```text
22 个累计指标 × 10 家公司 = 220 个 Result 坐标
```

这一步完成后，只能说“整批结果闭合了”，还不能说公共 CSV 已经正确，更不能说已经发布。

---

### 角色二：不可变版本包——把这一版装箱、封口、编号

完整批次通过投影、兼容性和验证后，系统把所有对外文件和内部证据一起装进：

```text
outputs/publications/publication_<内容指纹>/
```

这里的 `publication_id` 不是随便生成的版本号，而是由以下内容共同算出的指纹：

- Requirement 哈希；
- 批次 ID；
- 投影 ID；
- validation receipt ID；
- 每个文件的路径、SHA-256 和字节数；
- request ledger 绑定；
- 前一个 publication ID。

因此，只要任何文件、证据或前驱关系变了，`publication_id` 就应该变。旧包不能原地修补；要修正，只能产生一个新包。

写包时也不是直接写最终目录，而是：

```text
隐藏临时目录
→ 逐文件写入
→ 写 manifest
→ 在临时目录完整验证
→ 原子改名为最终 publication 目录
→ 再验证一次
```

当前 active R2 的 manifest 绑定 25 个 payload 文件：14 个对外文件、11 个内部文件；再加上 manifest 自己，目录一共 26 个文件。

最关键的边界是：

> **包做好，只代表“有一个完整候选版本存在”；active pointer 此时仍然可以继续指向旧版。**

仓库当前有 9 个 publication 目录，但正式 switch history 只承认 3 个 publication ID。其余包即使完整，也只是准备过、彩排过或未提交过的候选。

### 角色三：active pointer、switch intent 和 switch receipt——决定谁正式，并留下可恢复历史

#### active pointer：唯一正式路标

`outputs/active_publication.json` 只有四个字段：

```json
{
  "publication_id": "当前版本",
  "bundle_manifest_sha256": "当前版本清单的哈希",
  "previous_publication_id": "切换前的正式版本",
  "committed_at_utc": "切换时间"
}
```

系统把**原子替换这个小 JSON**定义为唯一正式提交点。

不是 CSV 写完时，不是 bundle 创建时，也不是 receipt 写完时。只有 pointer 切换，才意味着“当前正式世界”发生变化。

#### switch intent：切换前先留下“黑匣子”

在改动任何兼容镜像前，系统先写一份 intent，记录：

- 原 pointer；
- 目标 pointer；
- 是 `COMMIT` 还是 `ROLLBACK`；
- 原 switch receipt tip；
- 14 个兼容镜像切换前的 hash 和 size，或者原本不存在。

它不保存第二份备份字节。恢复时，系统从不可变 bundle 重新构造旧或新镜像，再用 intent 中的 hash 证明构造结果正确。

#### switch receipt：指针切完后再记历史账

receipt 记录这次切换是：

```text
从哪个 active
以 COMMIT 还是 ROLLBACK
切到哪个 active
接在上一条 receipt 的哪一端
```

所有 receipt 必须组成一条完整链：一个根、一个 tip、没有断链、分叉、孤儿或环。pointer 必须与唯一 tip 完全一致。

这能防止有人只把 pointer 手工改回一个历史值，就假装完成了合法回滚。

#### 为什么 receipt 必须在 pointer 后写

若先写 receipt、再切 pointer，进程可能在中间崩溃，留下一个“看起来已经提交”的孤儿历史边。

当前顺序是：

```text
intent
→ 兼容镜像
→ pointer（唯一提交点）
→ switch receipt
→ 读回验证
→ 删除 intent
```

---

### 角色四：`PublicationView`——下游拿到一张固定版本的快照票

安全下游不应直接轮流读取根目录的多个 CSV，而应先：

```text
PublicationView.open(publication_root)
```

打开时它会：

1. 取得共享锁，避开 writer 正在切换的窗口；
2. 确认没有未完成的 switch intent；
3. 读取 active pointer；
4. 验证 pointer 对应 switch history 的唯一 tip；
5. 完整验证 bundle 的文件集合、hash、size 和 publication ID；
6. 验证 pointer 记录的 manifest hash；
7. 把这个 publication ID 固定下来。

此后，即使别人把 active 切到下一版，这个 View 仍然只读自己打开时的那一版。每次 `read_bytes()` 还会再次核对该文件的 hash 和 size。

所以根目录的 `metrics_matrix.csv` 等 14 个文件只是**兼容镜像**：

- 方便旧程序继续按固定路径读取；
- 可以从 active bundle 重建；
- 不是权威源；
- 绕过锁和 View 的多文件读取，不享有完整快照保证。

## 四、一次正常发布到底怎样发生

把细节压缩成十步，就是：

### 第 1 步：固定旧世界

先用 `PublicationView` 打开当前 active，明确新候选是基于哪个正式前驱建造的。

### 第 2 步：证明整批完整

从 registry、release plan、MetricSpec 和真实结果重新推导 expected exact set，拒绝缺失、重复、额外坐标和期间冲突。

### 第 3 步：独立生成公共结果

新 producer 从 Result、Trace、Observation 和 source facts 生成公共行。旧 CSV 只能在生成之后充当兼容性对照，不能成为新值的语义输入。

### 第 4 步：得到 `PUBLISHABLE` 或 `BLOCKED`

若出现适用指标 `WITHHELD`、兼容性失败、gate 失败或 exact set 不闭合，候选是 `BLOCKED`，旧 active 继续服务。

### 第 5 步：ValidationReceipt 绑定这一次的精确字节

PASS 不是调用者填写的布尔值。receipt 必须绑定这批 Batch、Projection、前驱、检查项及实际文件的 path/hash/size。

### 第 6 步：建造 immutable bundle

临时写入、两次验证、原子改名。新包出现，但 pointer 不动，因此仍只是 `PREPARED`。

### 第 7 步：收窄提交权限

公共 `commit_publication()` 和首次链提交 API 故意永远报：

```text
FORMAL_CUTOVER_AUTHORITY_REQUIRED
```

真正的私有提交 primitive 只能由受治理的 Cutover 或专用 zero-AI release 编排器调用。一个普通脚本不能拿自制 bundle 直接变成 active。

### 第 8 步：加独占锁，先恢复旧事务，再做 CAS

writer 进入临界区后先处理任何遗留 intent，然后比较三件事：

```text
调用方认为的前驱
= 当前真实 active
= 新 bundle 自己声明的前驱
```

任何一个不一致，提交立即失败，而且发生在写 intent 和镜像之前。

### 第 9 步：intent → mirrors → pointer → receipt

先记录恢复信息，再更新 14 个兼容镜像，随后原子替换 pointer，最后写 receipt。

### 第 10 步：从正式读取入口重新读回

系统重新打开 `PublicationView`，确认 pointer、history、bundle 和文件共同成立；zero-AI R2 还逐个比较 14 个对外文件与根目录镜像。成功后删除 intent，事务封口。

## 五、为什么 pointer 是整个系统的分水岭

最容易记住的规则是：

```text
pointer 之前：新版本还没正式发生
pointer 之后：新版本已经成为正式事实
```

但还要加一个重要限定：**硬崩溃恢复**和**同一进程内可捕获异常补偿**不是一回事。

### 情况一：进程在 pointer 之前直接死亡

磁盘上仍是旧 pointer，可能已经有部分新镜像和一个 intent。

下一位 writer 看见：

```text
current pointer == intent.previous_pointer
```

于是它删除可能的孤儿边，从旧不可变 bundle 恢复旧镜像，删掉 intent。最终继续承认旧版。

### 情况二：进程在 pointer 之后直接死亡

磁盘上的 pointer 已经是新值，但 receipt 或镜像收尾可能未完成。

下一位 writer 看见：

```text
current pointer == intent.proposed_pointer
```

于是它验证新 bundle，补写 receipt，从新包重建镜像，删掉 intent。最终完成新版，而不是猜测性回滚。

### 情况三：pointer 写完后，原进程仍活着并捕获了后续普通异常

事务代码还有能力同步补偿：恢复旧镜像、恢复旧 pointer、删除本次 receipt 和 intent，然后向调用方返回失败。

所以更准确的说法是：

> **pointer 是持久化正式状态的唯一判断点；进程丢失后，恢复方向只看 pointer。若原进程仍持锁且能可靠补偿，它可以在返回失败前把整个事务撤销回旧状态。**

### 情况四：pointer 既不是 previous，也不是 proposed

系统不猜，直接报错：

```text
Pending switch pointer is neither previous nor proposed
```

这通常意味着发生了机制之外的人工篡改或未建模状态。自动“修复”反而可能扩大损失。

## 六、几个最重要的失败和回退场景

| 场景 | 系统怎么处理 | active 最终怎样 |
|---|---|---|
| 少结果、重坐标、混财年 | 批次构建失败 | 旧版不变 |
| applicable 结果 `WITHHELD` | 候选 `BLOCKED` | 旧版不变 |
| bundle 已准备但未提交 | 保留候选供审计 | 旧版不变 |
| 两个 publisher 并发 | lock 串行，第二个因 CAS 过期失败 | 只有一个赢家 |
| mirror 写到一半普通异常 | 原进程恢复所有旧字节 | 旧版不变 |
| pointer 前 hard crash | 下一 writer 按旧 pointer 恢复 | 旧版不变 |
| pointer 后 hard crash | 下一 writer 补齐 receipt 和镜像 | 新版完成 |
| 根目录镜像被改坏 | 从 active bundle 重建 | active 不变 |
| active bundle 被改一字节 | `PublicationView` fail closed | 不返回正式数据 |
| 显式 rollback | 复用同一事务切回已提交直接前驱 | 前驱重新 active |
| 最新一次更新失败 | latest 可记录失败 | 上一 active 继续服务 |

### rollback 不是“复制备份”

合法 rollback 只能回到当前 pointer 证明的**已提交直接前驱**，不能随便挑一个 stored bundle。

它不会：

- 重跑旧 parser；
- 重算旧指标；
- 修改旧 bundle；
- 删除新 bundle；
- 手工覆盖 CSV。

它只是把已验证的旧包重新设为 active，并生成一条新的 `ROLLBACK` 历史边。

## 七、用当前真实 R2 把整件事串起来

截至当前分支，active pointer 仍然是：

```text
active      = publication_fe01e227848d6a42…   （R2）
predecessor = publication_81eb84764bb3b3f…   （R1）
committed   = 2026-08-20T11:38:54Z
```

R2 的真实内容关系是：

```text
22 个累计指标
× 10 家公司
= 220 个 vNext Result 坐标

其中：
141 个已有 legacy key 被新实现重新生成并逐字段比较
79 个是新增 public key
再保留 89 个本轮尚未迁移的 legacy 行
最终 metrics_matrix.csv = 309 行
```

它还证明：

- 141 个迁移 key 的 20 个公共字段比较没有 unexpected delta；
- 模型、mock transport 和付费 provider 计数都是 0；
- active bundle 有 25 个 manifest-bound payload，加 manifest 共 26 个文件；
- 14 个对外文件有对应根目录兼容镜像；
- switch history 有 5 条边，真实经历过：

```text
建立 legacy A
→ 提交 R1 B
→ ROLLBACK 回 A
→ 再 COMMIT 恢复 B
→ 从 R1 前向 COMMIT 到 R2
```

因此，rollback 在这里不是一段“理论上应该能用”的代码；R1 的 A→B→A→B 已经以正式 receipt 留下历史。

另一个很有价值的事实是：当前分支后来已经加入新的 R3 lodging / qualification 证据，但 active pointer 仍指向 8 月 20 日的 R2。这正好说明：

> **新证据出现、新 Run 完成、甚至新候选准备好，都不会自动改变正式版本。只有 publication transaction 越过 pointer commit，active 才会变化。**

## 八、当前 R2 到底证明了什么，又没有证明什么

### 它证明了

1. 当前 active 确实是 `publication_fe01e227…`，并有合法 predecessor 和 switch-history tip；
2. R2 的 22 个 zero-AI 指标、220 个坐标和 309 行公共矩阵按专用 R2 契约闭合；
3. bundle 的文件集合、hash、size 和 publication identity 自洽；
4. 指针、manifest、bundle 和兼容镜像在 R2 读回时一致；
5. 下游通过 `PublicationView` 可以固定读取同一版；
6. 历史旧包不需要重算即可 rollback。

### 它没有证明

1. Issue #15 的 full acceptance 已经完成；
2. AI table 指标已经进入 active；
3. 所有 39 个指标已经完成最终 Cutover；
4. 当前正在推进的 qualification 已自动发布；
5. `validation_run_manifest.json` 是 `FULL_VALIDATION / PASSED`。

当前 active R2 的真实标记是：

```text
mode   = LIGHT_REVIEW_MODE
result = PASSED_WITH_CAVEATS
not_refreshed_artifacts = issue_15_full_acceptance.not_run
```

R2 仍能正式 active，是因为它走的是专用 zero-AI formal release authority。这里的 `FORMAL` 应理解为：

> **这个包有权走正式前向提交。**

而不是：

> **整个 Issue #15 已完成所有 full validation 和最终验收。**

还有一个更普遍的边界：

> **hash 能证明字节没有变化、内部声明彼此自洽；它不能单独证明这些业务判断今天仍然成立，也不是外部数字签名。**

发布层负责“这批已验证字节怎样安全成为当前版本”，不重新替上游判断某个指标值本身是否正确。

## 九、阅读和操作时只要守住七条纪律

1. **不要扫描 publication 目录找“最新”。** 只认经过验证的 active pointer。
2. **不要把 bundle 存在当成已经发布。** `PREPARED ≠ ACTIVE`。
3. **不要把 `PUBLISHABLE` 当成 active。** 它只说明候选有资格继续。
4. **需要跨多个文件的一致结果时，先开 `PublicationView`。** 不要无锁轮流读根目录镜像。
5. **不要把 latest attempt 当 active。** 最新尝试可以失败，上一正式版仍然健康。
6. **不要手工改 pointer 或删 intent。** recovery 必须由同一套锁和状态机处理。
7. **不要把专用 zero-AI R2 active 扩大解释成 full Cutover。** 范围标签必须保留。

---

## 十、这个设计为什么合理，又在哪里会失效

### 当前前提下合理

当前系统是单仓库、单机、本地文件系统、低频发布、强调离线审计。在这个前提下：

- immutable bundle 容易复制和复验；
- 一个小 pointer 就能提供原子提交点；
- `flock + CAS` 足以处理合作进程的并发；
- 旧版本完整保留，rollback 不依赖重算；
- 全套证据都是普通文件，clone 后可检查。

### 它付出的代价

- bundle、receipt 和候选目录会持续增长；
- 为兼容旧路径维护 14 个镜像，增加了事务复杂度；
- `PublicationView.open()` 要重验整包，成本随包大小增长；
- pending intent 未恢复时，reader 会 fail closed；
- 公共提交 API 故意不可用，第一次读代码的人可发现性较差。

### 什么时候需要换控制面

若未来变成多主机 writer、高频发布、网络文件系统、对象存储或严格高可用，不能继续把本地 `fcntl` 和 rename 的语义直接外推。

可以把 pointer、CAS、intent 和事务状态迁到强一致数据库或有条件写的对象存储，但以下因果不能丢：

```text
完整批次证明
→ 独立投影和门禁绑定
→ immutable version
→ 唯一 commit point
→ predecessor CAS
→ 可判定 crash recovery
→ 连续 switch history
→ pinned read
```

控制面可以换，证据面和语义边界不能降级。

---

## 十一、当前最值得做的三项改进

### 1. 让所有多文件消费者统一走 `PublicationView`

这是最直接消除业务层“半新半旧”风险的办法。根目录镜像继续保留兼容，但不再被内部新代码当成事务读取接口。

### 2. 提供只读 publication doctor / status

它应一次说清：

```text
当前 active 是谁
最新 attempt 是谁
有没有 prepared candidate
有没有 pending intent
若要恢复，应 RESTORE_PREVIOUS 还是 COMPLETE_PROPOSED
当前合法 rollback target 是谁
```

它只解释，不自行修改 authority。

### 3. 给 stored bundles 做可达性报告，再谈清理

当前 9 个 stored bundle 中只有 3 个进入正式历史。可以先做 dry-run：从 active、switch history、receipt index 和审计引用出发，列出真正不可达的 prepared-only 包。

默认只报告，绝不能直接按“非 active”删除；superseded 前驱仍可能是合法 rollback 目标和历史证据。

## 结论

按当前实测，一个合理的工程预算是：

- **zero‑AI 公司，fresh SEC 数据**：约 **15–25 秒/公司（摊销）**。
- **Marriott 这种需要 B10、B11 两个 AI table task 的公司**：约 **50–70 秒**形成已校验指标结果，但尚未包含完整 formal publication。
- **十公司 lodging R3 批次**：无重试、SYSTEM review 自动通过时，预计约 **3–5 分钟**形成并发布最终 CSV。
- **financial table / AI text 公司**：目前不能诚实给出时间；前者仍有资源门阻断，后者尚未完成正式实现和 qualification。

最重要的口径是：系统不允许按公司局部发布。因此某家公司虽然可能在一分钟内算完，它的结果仍要等整个批次闭合后才能出现在 active CSV 中。[Contract](../requirements/issue_15_v1/CONTRACT.md)

## 1. SEC raw data 获取

现有一次真实十公司 acquisition receipt 包含93次 SEC 请求，总耗时116.578秒

| 节点 | 十公司实测 | 摊销到每公司 |
|---|---:|---:|
| SEC 连通性检查 | 1.376 秒 | 0.14 秒，共享开销 |
| 公司/CIK、submissions 解析 | 12.399 秒 | 1.24 秒 |
| filing inventory 形成 | 0.309 秒 | 0.03 秒 |
| Company Facts 下载 | 22.508 秒 | 2.25 秒 |
| accession material 下载 | 79.986 秒 | 8.00 秒 |
| **合计** | **116.578 秒** | **11.66 秒/公司** |

所以 fresh acquisition 的实际预算建议取 **10–20秒/公司**。文件数量多、SEC响应慢或触发重试时会更长。

如果 raw bytes 已缓存并通过 immutable-attempt 校验，这一段基本可以跳过。

## 2. 单个 AI table 指标任务

用当前机器、当前代码和 Marriott 2.05 MB、67张表的真实 filing 做了无网络离线微基准：

| 节点 | 实测 |
|---|---:|
| HTML → 完整 expanded table-grid | 0.862 秒 |
| 构造 ReaderInputManifest | 0.323 秒 |
| compact payload + 单指标 task request | 1.881 秒 |
| 构造 provider envelope | 0.085 秒 |
| 真实受控 AI execution | 10.4–18.9 秒，中位数13.4秒 |
| Workflow 第二次机械 Evidence 重验 | 2.154 秒 |
| 指标计算 Result/Trace | 0.35 毫秒 |

因此：

> **一个 AI table task：约18–25秒，未计人工等待和完整 formal freeze。**

Marriott 要分别执行 B10 Occupancy 和 B11 RevPAR，所以两个任务顺序执行约 **36–50秒**；再加 SEC acquisition，约 **50–70秒**得到已校验的公司指标结果。
